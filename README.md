# Agent Memory

Долговременная память для ИИ-агентов на Go. Агент во время работы сохраняет атомарные
факты, события и процедуры, а в другой сессии — своей или чужой — запрашивает их обратно
по смыслу и получает компактный Markdown-бриф, обрезанный под бюджет токенов, а не сырую
выдачу top-k.

Хранилище по умолчанию — один файл SQLite (метаданные + полнотекстовый индекс FTS5 +
опциональный вектор через `sqlite-vec`). Для общей памяти на несколько разработчиков
тем же конфигом включается PostgreSQL + pgvector — см.
[переезд на PostgreSQL](#общая-база-команды-переезд-на-postgresql). Агент общается с
памятью через MCP по stdio.

## Зачем это

- Сохранил факт в одной сессии — достал по смыслу в другой, без ручного копирования в промпт.
- Recall отдаёт не сырьё, а ранжированный и обрезанный под токен-бюджет бриф.
- Память не превращается в свалку: дедупликация при записи, устаревание episodic-фактов,
  консолидация в semantic — фоновыми джобами.
- Работает локально: SQLite-файл, без обязательных внешних сервисов. Вектор (ollama) и
  суммаризация (DeepSeek) — опциональные слои: недоступны — recall деградирует до FTS5,
  а не падает.
- Растёт до команды: та же память переключается на общую базу PostgreSQL + pgvector
  одной секцией конфига, с переносом накопленного через `memo migrate`.
- Подключается к проекту одной командой (`memo init`), которая сама раскладывает
  MCP-конфиг и инструкцию для агента.

## Быстрый старт

Предпосылки:

- Go 1.26+
- C-компилятор (CGO обязателен — `mattn/go-sqlite3` собирается с тегом `sqlite_fts5`)
- опционально: [ollama](https://ollama.com) с моделью `bge-m3` для векторного поиска
- опционально: ключ DeepSeek (`DEEPSEEK_API_KEY`) для суммаризации и консолидации памяти

Без ollama и DeepSeek память тоже работает — на чистом FTS5, без суммаризации выдачи.

Собери и поставь бинарь себе в `~/.local/bin` (без sudo):

```sh
make install
```

Если `~/.local/bin` не в `PATH`, `make install` подскажет строку для `~/.zshrc`.

Подключи память к своему проекту — из корня проекта, куда её ставишь:

```sh
memo init
```

В интерактивном режиме спросит имя проекта, агентское приложение (`claude` или
`opencode`), адрес и модель ollama, путь к файлу БД и, по желанию, ключ DeepSeek — и
разложит:

- MCP-конфиг (`.mcp.json` для Claude Code или `opencode.json` для opencode);
- два скила — «Протокол работы с памятью» (`memo`) и разовый bootstrap
  «Первичная инициализация памяти» (`memo-bootstrap`), см. [раздел ниже](#скил-протокол-работы-с-памятью);
- `agentmemory.toml` со введёнными настройками;
- `.env` с ключом DeepSeek (если ввёл) — с правами `0600` и строкой в `.gitignore`.

Для неинтерактивного запуска (CI, скрипты) — флагами и `-no-input`:

```sh
memo init -project myproject -agent claude -no-input
```

После этого агентское приложение само поднимает `memo` как MCP-сервер `memo`.
Агенту в системный промпт/скил уже прописано: `memory_recall` — в начале задачи (подтянуть
контекст), `memory_save` — по ходу работы, когда появляется факт стоит запомнить.

Посмотреть, что накопилось, глазами — read-only web-морда:

```sh
memo web
```

и открыть `http://127.0.0.1:7070` — дашборд статистики, список записей с фильтрами по
scope/kind, карточка записи с соседями по графу и лексический поиск. Слушает только
localhost.

## Скил «Протокол работы с памятью»

Мало дать агенту четыре MCP-инструмента — он должен знать, когда их трогать. Поэтому
`memo init`, кроме конфига, кладёт в проект **два скила**. Главный — протокол работы с
памятью, файл `SKILL.md` с `name: memo`:

- Claude Code — `.claude/skills/memo/SKILL.md`
- opencode — `.opencode/skills/memo/SKILL.md`

Тело скила одно для всех приложений (различаются только путь файла и формат MCP-конфига),
и агентское приложение подхватывает его само — по полю `description` оно понимает, когда
протокол релевантен. Что внутри:

- **Когда звать.** `memory_recall` — в начале любой задачи, чтобы подтянуть решения и
  прогресс прошлых сессий. `memory_save` — по ходу и в конце, по одному атомарному факту
  (1–3 предложения) за вызов. `memory_update` — когда факт изменился. `memory_forget` —
  когда устарел или ошибочен (мягкое удаление).
- **Правила scope.** `save` без явного scope пишет в `project:<name>`; `recall` без scope
  ищет в `project:<name>` + `user:*`; явный scope перекрывает дефолт. Проектные
  факты, решения и грабли — в `project:<name>`; общие привычки пользователя — в `user:*`.
- **Если сервера нет.** Когда инструменты `memory_*` в сессии не видны (MCP-сервер не
  поднят или не одобрен приложением) или reasoner/embedder деградировали — продолжать
  задачу без долговременной памяти, предупредив об этом.

Этот скил — обобщённая версия того, по которому сам Agent Memory ведёт свою разработку
(`.claude/skills/dev`): проект хранит рабочую память в собственном `memo` и тем самым
проверяет себя на себе.

### Скил «Первичная инициализация памяти» (`memo-bootstrap`)

Второй скил, который кладёт `memo init`, — разовый bootstrap с `name: memo-bootstrap`,
рядом с `memo`:

- Claude Code — `.claude/skills/memo-bootstrap/SKILL.md`
- opencode — `.opencode/skills/memo-bootstrap/SKILL.md`

Протокол `memo` бесполезен, пока памяти нечего recall'ить, — в свежем проекте она пуста.
Bootstrap закрывает этот разрыв: запусти его **один раз** сразу после `memo init`, и агент
изучит проект (через `/graphify`, если доступен, иначе вручную — README, DESIGN, файлы
сборки, раскладка пакетов, ключевые исходники) и сохранит через `memory_save` ключевые
проектные факты: назначение, стек, архитектуру и границы модулей, конвенции, цели и
ограничения. Дальше память наполняет уже протокол `memo` по ходу работы.

Скил намеренно узкий и курирующий: сначала `memory_recall` (не дублировать, если факты
уже есть), сохранять только долговечное и неочевидное — архитектурные решения и их
причины, инварианты, договорённости, — а не то, что тривиально выводится из кода, README
или git-истории заново. Тело скила параметризуется именем проекта (`memo init` подставляет
его в заголовок, `description` и примеры scope).

## Использование

Бинарь `memo` — несколько режимов, различаются первым аргументом:

| Команда | Что делает |
|---|---|
| `memo [-config <path>] [-db <path>]` | MCP-сервер по stdio (режим по умолчанию) |
| `memo init [флаги]` | установщик: раскладывает MCP-конфиг, скил, `agentmemory.toml`, `.env` в проект |
| `memo web [флаги]` | HTTP-морда для просмотра памяти в браузере (read-only + мягкое удаление) |
| `memo doctor [флаги]` | read-only диагностика: в каком режиме реально работает память, ничего не пишет |
| `memo export [флаги]` | экспорт памяти в переносимый JSONL-бэкап (полный или по `-scopes`) |
| `memo import [флаги] file.jsonl` | восстановление из JSONL-бэкапа с сохранением id и таймстампов |

`memo --help` (`-h`/`help`) печатает сводку; `memo init -h`, `memo web -h`,
`memo doctor -h`, `memo export -h`, `memo import -h` и т.д. — флаги конкретной подкоманды.

Флаги режима сервера:

| Флаг | Значение |
|---|---|
| `-config <path>` | путь к TOML-конфигу (опционально) |
| `-db <path>` | путь к SQLite-файлу, переопределяет `store.path` из конфига |

Ключ DeepSeek берётся из `DEEPSEEK_API_KEY` в окружении или из `.env` рядом с конфигом.

Флаги `memo init`:

| Флаг | Значение |
|---|---|
| `-project` | имя проекта (дефолт — базовое имя каталога `-dir`) |
| `-dir` | каталог, в который скаффолдить артефакты (дефолт `.`) |
| `-force` | перезаписывать существующие файлы скиллов SKILL.md (agentmemory.toml/mcp-конфиг всегда синхронизируются, `.env` всегда мержится — `-force` на них не влияет) |
| `-agent` | `claude` или `opencode` (дефолт `claude`) |
| `-ollama-url` | base URL ollama (дефолт `http://localhost:11434`) |
| `-ollama-model` | модель эмбеддингов ollama (дефолт `bge-m3`) |
| `-store` | путь к файлу SQLite (дефолт `~/.agentmemory/memory.db`) |
| `-deepseek-key` | ключ DeepSeek — пишется в `<dir>/.env` (попадёт в историю shell, если задан флагом) |
| `-no-input` | не спрашивать интерактивно — только флаги и дефолты |

Флаги `memo web`:

| Флаг | Значение |
|---|---|
| `-addr` | адрес прослушивания (дефолт `127.0.0.1:7070`) |
| `-config` | путь к TOML-конфигу (опционально) |
| `-db` | путь к SQLite-файлу, переопределяет `store.path` из конфига |

Флаги `memo doctor`:

| Флаг | Значение |
|---|---|
| `-config` | путь к TOML-конфигу (опционально) |
| `-db` | путь к SQLite-файлу, переопределяет `store.path` из конфига |
| `-json` | машиночитаемый JSON вместо человекочитаемого списка секций |
| `-live` | выполнить пробный запрос к DeepSeek (стоит денег; по умолчанию выключено) |

`memo doctor` отвечает на вопрос «в каком режиме реально работает память и всё ли
с ней хорошо» одной командой, строго read-only (не пишет в БД, не чинит): 7 секций
(конфиг, БД + `PRAGMA quick_check`, счётчики записей, векторный индекс vs конфиг
эмбеддера, живость embedder'а пробным эмбеддингом, наличие ключа/провайдера Reasoner,
итог), каждая помечена ✅/⚠️/❌. Полезно после смены модели эмбеддера, при подозрении
на остановленную ollama или просто чтобы понять, почему recall выглядит бедным.
Код выхода: `0` — здоров или деградирован (только ⚠️), `1` — есть хотя бы одна ❌
(скриптуемо, напр. в CI/крон-проверке).

### Бэкап и перенос

`memo export`/`memo import` — штатный способ забэкапить память, продиффать её или
перенести на другую машину/в другой проект: JSONL-файл не зависит от бэкенда. Для
переезда между хранилищами напрямую есть `memo migrate` (см.
[переезд на PostgreSQL](#общая-база-команды-переезд-на-postgresql)) — он не требует
промежуточного файла.

Флаги `memo export`:

| Флаг | Значение |
|---|---|
| `-config` | путь к TOML-конфигу (опционально) |
| `-db` | путь к SQLite-файлу, переопределяет `store.path` из конфига |
| `-o` | путь к выходному файлу (пусто — stdout, пайпабельно) |
| `-scopes` | пространства через запятую для частичного экспорта (пусто — вся БД) |

Флаги `memo import`:

| Флаг | Значение |
|---|---|
| `-config` | путь к TOML-конфигу (опционально) |
| `-db` | путь к SQLite-файлу, переопределяет `store.path` из конфига |
| `-dry-run` | только разобрать файл и напечатать отчёт; БД не открывается вовсе |
| `-overwrite` | заменять записи с конфликтующим id (по умолчанию — пропуск) |
| `-rescope` | перенос scope при импорте: `old=new` (напр. `project:a=project:b`) |

Формат — JSONL: первая строка заголовок (`format`/`version`/`exported_at`/`db`), дальше по
одной записи памяти на строку (`id`, `kind`, `scope`, `content`, `summary`, `importance`, все
таймстампы, `superseded_by`, `source`, `tags`, `links`) — стримится, диффается, `grep`ается.
Векторы **не экспортируются** — это производные данные; после импорта их досчитывает
фоновый reindex при следующем запуске `memo` (пустая `embed_meta` новой БД → полный
reindex). Тумстоуны (мягко забытые записи) экспортируются и импортируются как есть — история
переносится вместе с фактами. Импорт восстанавливает id и все таймстампы в точности (не через
обычный write-путь — без дедупликации/переклассификации): конфликт id по умолчанию
пропускается со счётчиком, `-overwrite` заменяет; ссылка на id, которого нет в целевом
хранилище, — предупреждение и пропуск ребра, остальной импорт продолжается. Итоговая строка:
`imported N, skipped M, links K (dropped L)`.

Типичный сценарий бэкапа/переноса:

```bash
memo export -o backup.jsonl                       # весь инстанс в файл
memo import -db ~/new-machine/memory.db backup.jsonl
```

MCP-инструменты, которые видит агент: `memory_save`, `memory_recall`, `memory_update`,
`memory_forget` — набор маленький намеренно, подробности по формату аргументов в
`DESIGN.md` §12.

### Общая база команды: переезд на PostgreSQL

По умолчанию память живёт в локальном файле SQLite — этого достаточно для одного
человека. Когда память нужна общая на несколько разработчиков, хранилище переключается
на PostgreSQL: те же данные и тот же recall, но одна база на всех и нормальная
конкурентная запись.

**Что нужно на сервере** — PostgreSQL 13+ с расширением [pgvector](https://github.com/pgvector/pgvector)
(на Debian/Ubuntu — пакеты `postgresql-<версия>` и `postgresql-<версия>-pgvector` из
репозитория [PGDG](https://wiki.postgresql.org/wiki/Apt)):

```sql
CREATE ROLE memo LOGIN PASSWORD '<пароль>';
CREATE DATABASE memo OWNER memo;
\c memo
CREATE EXTENSION IF NOT EXISTS vector;
```

Плюс сетевой доступ: `listen_addresses` в `postgresql.conf` и строка для вашей подсети
в `pg_hba.conf`. Схему таблиц создавать руками не нужно — `memo` применит её сам при
первом запуске.

**Шаг 1. Драйвер в конфиге.** Секция `[store]` вместо `path`:

```toml
[store]
driver  = "postgres"
host    = "postgres.example.lan"
port    = 5432
user    = "memo"
dbname  = "memo"
sslmode = "disable"        # require/verify-full, если база не в доверенной сети
```

Остальные секции не меняются. Без `driver` (или с `driver = "sqlite"`) всё работает
как раньше — старые конфиги трогать не надо.

**Шаг 2. Пароль.** В TOML он не пишется никогда — только `MEMO_POSTGRES_PASSWORD` в
окружении или в `.env` рядом с конфигом, ровно как `DEEPSEEK_API_KEY`:

```bash
echo 'MEMO_POSTGRES_PASSWORD=<пароль>' >> .env
```

**Шаг 3. Перенос накопленной памяти.** `memo migrate` переносит записи между бэкендами
в любую сторону — вместе с тегами, связями и тумстоунами:

```bash
memo migrate -dry-run "sqlite:$HOME/.agentmemory/memory.db" "postgres://memo@postgres.example.lan:5432/memo?sslmode=disable"
memo migrate         "sqlite:$HOME/.agentmemory/memory.db" "postgres://memo@postgres.example.lan:5432/memo?sslmode=disable"
```

Источник и приёмник задаются явно и позиционно — направление видно прямо в команде.
Пароль в URL не принимается (осел бы в истории шелла и в `ps`), берётся из
`MEMO_POSTGRES_PASSWORD`. Флаги:

| Флаг | Значение |
|---|---|
| `-dry-run` | посчитать источник и показать план; приёмник не открывается вовсе |
| `-overwrite` | заменять записи с конфликтующим id (по умолчанию — пропуск со счётчиком) |
| `-scopes` | пространства через запятую для частичного переноса (пусто — всё) |

Исходный SQLite-файл не изменяется — это копирование, а не перемещение, так что откат
это просто возврат `driver = "sqlite"` в конфиге. Повторный запуск идемпотентен:
уже перенесённые id пропускаются. После переноса команда сверяет, что все записи
источника доехали, и печатает расхождение, если нет.

**Шаг 4. Проверка.**

```bash
memo doctor -config agentmemory.toml
```

Строка «БД» должна показать `postgres://<хост>:5432/<база>`, «Записи» — перенесённые
количества по scope. Остальные разработчики повторяют шаги 1–2 у себя; шаг 3 делается
один раз, база уже общая.

**Про векторы.** Они не переносятся — это производные от текста и модели эмбеддера,
как и при `export`/`import`. Фоновый reindex досчитает их при следующем запуске `memo`
с доступным embedder'ом; до тех пор recall работает на полнотекстовом поиске — штатная
деградация, а не поломка.

**Отличие в поиске.** PostgreSQL стеммирует средствами СУБД (`tsvector` с конфигурацией
`russian`) и отбрасывает стоп-слова, тогда как SQLite стеммирует все слова подряд.
На запросах из знаменательных слов выдача обоих бэкендов совпадает; разойтись она может
только там, где значимая часть запроса — предлоги и союзы.

**Известное ограничение.** На общей базе scope `user:*` пока един для всех — личные
предпочтения разработчиков смешиваются. Разделение на `user:<login>` — отдельная задача
(`DESIGN.md` §14).

## Конфигурация

TOML-файл, секции `[store] [embedder] [reasoner] [recall] [maint] [scope]`. Пример со
всеми полями и комментариями — `config.example.toml`. Если конфиг не передан или в нём
чего-то не хватает, действуют дефолты из `internal/config.Default()` (эквивалент этапа
MVP: только SQLite+FTS5, без вектора и без LLM).

Коротко по секциям:

- `[store]` — бэкенд хранилища: `driver = "sqlite"` (дефолт) и `path` к файлу, либо
  `driver = "postgres"` и параметры подключения (`host`/`port`/`user`/`dbname`/`sslmode`);
  пароль PostgreSQL — **не в этом файле**, а в `MEMO_POSTGRES_PASSWORD`.
- `[embedder]` — `noop | ollama | openai`; при `ollama` `dim` определяется автоматически
  пробным эмбеддингом при старте, руками не задаётся.
- `[reasoner]` — `noop | deepseek`; ключ **не в этом файле**.
- `[recall]` — дефолтный токен-бюджет брифа и веса ранжирования (relevance/importance/recency/access).
- `[maint]` — интервалы фоновых джобов (decay, consolidation).
- `[scope]` — имя текущего проекта (мультипроектность через общий файл БД + scope) и
  список пространств, всегда добавляемых к recall (по умолчанию `["user:*"]`).

Секреты — только в окружении или в `.env` рядом с конфигом (`KEY=VALUE`, поддерживает
`#`-комментарии и кавычки); shell-env приоритетнее `.env`, в TOML они не пишутся
никогда. Это `DEEPSEEK_API_KEY` (Reasoner), `OPENAI_API_KEY` (embedder `openai`) и
`MEMO_POSTGRES_PASSWORD` (хранилище `postgres`).

## Как это устроено

```text
           Agent Memory · memo — один бинарник, три поверхности доступа

┌───────────────────────┐   ┌───────────────────────┐   ┌───────────────────────┐
│ MCP · internal/mcp    │   │ CLI · memo            │   │ Web · memo web        │
│ stdio → агенты        │   │ терминал · хуки       │   │ браузер · человек     │
│                       │   │                       │   │                       │
│ save · recall         │   │ recall · save         │   │ поиск: лексика+смысл  │
│ update · forget       │   │ hook (ambient)        │   │ PATCH метаданных      │
│ links · ttl           │   │ doctor · export       │   │ forget                │
│ explain · фильтры     │   │ import                │   │                       │
└───────────────────────┘   └───────────────────────┘   └───────────────────────┘
            │                           │                           │
            └───────────────────────────┼───────────────────────────┘
                                        │   вызовы → общая доменная логика
            ┌───────────────────────────┼───────────────────────────┐
            ▼                           ▼                           ▼
┌───────────────────────┐   ┌───────────────────────┐   ┌───────────────────────┐
│ Writer · write        │   │ Recall · recall       │   │ Maint · maint         │
│ (запись)              │   │ (поиск)               │   │ (фоновые джобы)       │
│                       │   │                       │   │                       │
│ дедуп по scope        │   │ FTS5 + вектор → RRF   │   │ expire (TTL)          │
│ supersede (мягко)     │   │ ранжирование          │   │ decay · dedup         │
│ links (rel) · ttl     │   │ фильтры · explain     │   │ consolidation         │
│ FTS5 (+ вектор)       │   │ бриф под бюджет       │   │ reindex               │
└───────────────────────┘   └───────────────────────┘   └───────────────────────┘
            │                           │                           │
┌───────────────────────────────────────────────────────────────────────────────┐
│ Store · SQLite (WAL) — единый файл, всё за интерфейсом Store                  │
│ memories · tags · links · memories_fts · memories_vec · embed_meta            │
│ expires_at · миграции (user_version) · superseded_by вместо DELETE            │
└───────────────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────────┐
│ Embedder (опц.): ollama·bge-m3  или  openai·/v1/embeddings                    │
│ Reasoner (опц.): DeepSeek chat  (суммаризация выдачи · консолидация)          │
│ оба деградируют, а не падают: без них — recall на FTS5, без сводок            │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **Три поверхности доступа** — один бинарь `memo`, одна доменная логика: MCP over
  stdio для агентов (`memory_save`/`recall`/`update`/`forget`), CLI и ambient-хуки
  харнесса для терминала (`recall`/`save`/`hook`/`doctor`/`export`/`import`) и web-морда
  для человека (`memo web` — поиск, карточка, правка метаданных).
- **Store** — единый SQLite-файл: таблица `memories` (+`expires_at`, TTL), FTS5-индекс
  (со стемминг-колонкой для русской морфологии), опциональная vec-таблица (`sqlite-vec`),
  миграции через `PRAGMA user_version`; всё за интерфейсом `Store`.
- **Writer** (`internal/memory/write`) — приём факта: дедуп по scope, обновление или
  пометка `superseded_by` вместо DELETE, типизированные связи (`rel`), TTL.
- **Recall** (`internal/memory/recall`) — гибридный поиск (FTS5 + вектор) → слияние через
  Reciprocal Rank Fusion → ранжирование по relevance/importance/свежести/частоте обращения
  → сборка Markdown-брифа под токен-бюджет; фильтры по scope/kind/тегам/датам, explain-трасса.
- **Maint** (`internal/memory/maint`) — фоновые джобы по расписанию: expire-sweep (TTL),
  decay episodic-записей, консолидация episodic→semantic через Reasoner, dedup-sweep,
  reindex при смене Embedder-модели.
- **Embedder / Reasoner** — за интерфейсами, оба опциональны и деградируют вместо падения:
  Embedder (ollama или openai-совместимый) недоступен → recall работает на чистом FTS5,
  без DeepSeek — без суммаризации и консолидации.

Подробности — модель данных, интерфейсы, write/read path, roadmap — в `DESIGN.md`.

## Разработка

```sh
make build   # CGO_ENABLED=1 go build -tags sqlite_fts5 ./...
make test    # CGO_ENABLED=1 go test -tags sqlite_fts5 ./...
make run     # CGO_ENABLED=1 go run -tags sqlite_fts5 ./cmd/memo — MCP-сервер из исходников
make web     # CGO_ENABLED=1 go run -tags sqlite_fts5 ./cmd/memo web — web-морда из исходников
```

Тег `sqlite_fts5` и `CGO_ENABLED=1` обязательны везде — без них FTS5 не соберётся.

Тесты PostgreSQL-бэкенда требуют живого сервера и потому по умолчанию пропускаются.
Чтобы прогнать и их, укажите тестовую базу (каждый прогон работает в своей временной
схеме и убирает её за собой):

```sh
MEMO_TEST_POSTGRES_DSN='postgres://memo:<пароль>@postgres.example.lan:5432/memo?sslmode=disable' make test
```

Код:

- `cmd/memo` — точка входа: сервер, `init`, `web`, `migrate`.
- `internal/memory` — домен: `types.go`, `store/` (интерфейс `Store` и две реализации —
  SQLite и PostgreSQL), `embed/` (Embedder), `reason/`
  (Reasoner), `write/` (ingest), `recall/` (поиск и бриф), `maint/` (фоновые джобы).
- `internal/mcp` — регистрация MCP-инструментов и роутинг.
- `internal/config` — загрузка TOML/env.

Архитектурные решения и границы пакетов — в `DESIGN.md`, читай перед изменениями.
