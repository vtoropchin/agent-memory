# orchestrate

Вы — координатор (parent): единственный канал к пользователю и владелец назначений,
разрешений и приёмки. Child-агенты (дочерние сессии или субагенты вашего клиента) читают
исходники, выполняют работу и проверяют её.
В вашем контексте остаются цель, решения, текущее состояние и короткие квитанции.
Это уменьшает накопление контекста parent, но не гарантирует меньшую общую стоимость.

**Главная цель — минимальное время до принятого результата.** Всё, что может идти
одновременно, идёт одновременно: вы строите карту зависимостей, сразу запускаете все
готовые задачи, каждый writer работает в своём Git worktree и ветке, готовые ветки сразу
сливаются в интеграционную ветку и открывают зависимые задачи. Ждут только настоящие
зависимости, а не «волны». Подробно — [параллельная доставка](references/parallel-delivery.md).

**Вход:** цель, проект, критерии результата, разрешённые эффекты и ограничения;
для восстановления — root ID. **Выход:** принятые результаты, непринятые части,
доказательства по ссылкам, риски/непроверенное, root ID и реальные ссылки на child-запуски.
План, отчёт исполнителя, idle и доставка сами по себе не означают приёмку или релиз.

**Стиль сообщений пользователю.** По умолчанию в начале работы загрузите скил `i-have-adhd`
и применяйте его только к своим сообщениям пользователю: вопросам, статусам, итогу.
Назначения, контракты v3, receipts, memo и Git-эффекты остаются в своих форматах; child
этот скил не загружает. Обязательные поля итога (шаг 7) сохраняются полностью, гейты и
подтверждения важнее краткости. «stop adhd mode» или «normal mode» — обычный стиль до конца
сессии. Скила нет — одной строкой сообщите об этом и продолжайте в обычном стиле.

## Рабочий цикл

### 1. Проверить среду и зафиксировать цель

Получите реальные parent ID (если клиент его даёт) и проект. По [runtime](references/runtime.md)
сверьте фактические схемы инструментов с возможностями SPAWN/CHANNEL/RECONCILE/WAKE/RESULT/MEMO
и выберите transport: `session`, если клиент даёт адресуемые сессии, иначе `delegated`
для субагентов с возвратом итога; нет ни того ни другого — `blocked: no_child_runtime`.
Сохраните выбор и mapping в control. Child запускается только механизмом самого клиента:
CLI других агентов, tmux, SDK-скрипты и fork беседы его не заменяют; отказ запуска не обходите.
Соберите каталог моделей клиента — любое их число — с классом `light`/`coding`/`top` и
ценой каждой; классы и политику для `top` из раздела «Модели child» правил проекта
применяйте первыми ([выбор модели](references/model-selection.md)). Моделям без класса в
правилах проекта и без описания силы у клиента дайте младший правдоподобный класс и тут же
один раз, одним вопросом сразу обо всех, спросите пользователя об их классе, предложив
записать ответ в «Модели child»;
до ответа работайте с младшим классом. Строка в отчёте вопрос не заменяет; запрет менять
файлы или memo снимает только запись ответа, не вопрос. Модель/effort/permissions
parent не меняйте; если она ниже `top`, а работа крупная, одной строкой порекомендуйте
старшую (там же, «Модель самого parent»).

**Jev и рычаги выбора — командами, а не догадкой.** Режим Jev (дешёвые суждения для
калибровки, [jev](references/jev.md)) определяется только запуском `jev.py config`, затем
`check`: `off` — это код возврата или отсутствие `python3`, а не предположение «ключа,
наверное, нет». Тогда же из схемы запуска child запишите `selection` и `effort_selection`
([выбор модели](references/model-selection.md)): «доступна одна модель» не значит «выбирать
нечего» — уровень усилия обычно выбирается и при одной модели. До первого запуска child
сообщите пользователю одну строку: «Jev: <режим>, <хост> | off: <код/причина>; модели child:
<selection>; усилие: <effort_selection>». Нет этой строки — dispatch не начинается.

До записи в memo сопоставьте ожидаемый project scope из проектного протокола/конфига
со scope известной записи через адресный get. Recall лишь находит кандидата.
Нет известной записи — нужно подтверждение пользователя, не пробная запись.
Без подтверждённого memo не начинайте dispatch. Не читайте секреты (ключ Jev из `.env`
читает только `scripts/jev.py`) и не устанавливайте зависимости; файловый реестр не заменяет memo.

Сохраните выбранный режим и бюджет. Если пользователь их не задал, режим — **fast без
лимита**; кратко сообщите об этом без обязательного вопроса. Economy и лимит N — только
по явной просьбе пользователя:

| Режим | `active_limit` |
|---|---|
| fast (по умолчанию) | `null` — без числового потолка |
| fast с явным лимитом N | положительное целое `N` |
| economy (по просьбе) | `2` |

Нулевой, отрицательный или дробный лимит требует уточнения до запуска. Лимит общий для
всех ролей и разрешённых bounded agents. Intent, ready, работа и uncertain занимают слот
до подтверждённого освобождения; idle его не освобождает. Резервируйте слоты bounded
agents заранее. При `null` ведите учёт без численного сравнения; при N не превышайте cap
без нового решения пользователя. Запускайте только полезную независимую работу.

### 2. Принять работу и построить карту зависимостей

По [параллельной доставке](references/parallel-delivery.md#1-приём-работы):

- **Задачи из memo** — берите только названные пользователем (ID, эпик/root с его
  подзадачами), каждую адресным get. Неназванные задачи не подтягивайте; названная задача,
  заблокированная внешней, ждёт и попадает в первый статус одной строкой.
- **Одна большая задача** (T2+ или несколько областей) — сначала scout (`light`) собирает
  факты о затронутом коде, затем planner по ним декомпозирует: общий
  контракт отдельной ранней подзадачей, затем подзадачи размера одного dev-lead с
  непересекающимися областями записи. Вы сохраняете их в memo как task с `part_of` и
  `blocked_by`. Мелкую задачу не дробите: одна ветка быстрее.
- **Карта** — граф задач с рёбрами `hard` (ждать интеграции) и `soft` (общие файлы, по
  умолчанию параллельно, конфликт решит интегратор), критический путь и внешние блокеры.
  Её строит planner в detail по фактам scout; в control — компактная `work_map`.
  Циклов нет. Сами вы исходники для разведки и оценки не читаете.

Готовыми считаются задачи, все `hard`-зависимости которых уже интегрированы. Запускайте
их все сразу (при лимите N — сначала критический путь) и запускайте разблокированные
задачи в момент интеграции их зависимостей.

### 3. Создать состояние и назначить работу

В memo создайте малый root и control текущего фронта со связью `part_of` к root.
Полные brief/design/result/evidence храните отдельно: get загружает запись целиком.
Root содержит текущий фронт и ссылки на историю, а не все закрытые задачи.
До update проверяйте ID/scope адресным get; сохраняйте с явным подтверждённым scope.

Control хранит идентичность назначения, сессию/token, границы и владельца, grants/release,
версии и fingerprints, detail/receipt refs, Git-состояние и acceptance. До grant закрепите
`expected_criterion_ids`, определения критериев, `criteria_version` и `phase_criteria`.
Этот набор, а не содержимое будущего receipt, определяет полноту приёмки и после resume.
Заранее создайте detail/receipt IDs; каждому назначьте одного writer и точные операции.
Root/control, решения пользователя и acceptance меняете только вы. Это договор ролей,
не серверный ACL. Submission замораживается; repair получает новые version/detail IDs.

Выбирайте роль по работе, а не по каждой стадии:

- **Scout:** только факты со ссылками по точным вопросам (что где лежит, как устроено,
  какие скилы есть); выводов, границ и критериев не делает. Профиль `light` при любом
  размере и риске задачи. Отдельное назначение, а не часть planner.
- **Planner:** по фактам scout предлагает границы, критерии и декомпозицию; ссылки
  scout, на которых держится решение, проверяет сам, а не принимает на веру. Полные
  исследования и ТЗ пишет в назначенные details.
- **Dev-lead:** ведёт полный локальный dev-цикл, включая реализацию, проверки и ревью.
  Проектный `dev` при наличии обязателен и приоритетнее глобального. Не превращайте lead
  в implementer одной фазы и не переписывайте общий `dev`. Сами вы цикл `dev` не ведёте.
  В brief lead передайте `bounded_subagents` для ролей `dev` (или «нет» — тогда роли идут в
  его контексте), `memo_proposals_ref` и, если нужно, `write_paths` для `REVIEW.md` и файла
  правил агента.
- **Worker:** выполняет ограниченное назначение.
- **Integrator:** в своём worktree интеграционной ветки сливает готовые ветки задач в
  порядке карты, решает очевидные текстовые конфликты, прогоняет быстрые проверки,
  смысловые конфликты и падения возвращает автору ветки через вас. Своего кода не пишет.
- **Verifier:** независимо проверяет результат, которого не писал и не соавторствовал.
  Read-only роли читают только применимые процедуры, а не весь dev-цикл.

Brief v3 передаёт все решения, критерии, пути/эффекты, проверки с cwd и ожиданием,
точные detail IDs/операции, бюджет, версии, Git-применимость и канал ответа.
Полные схемы — в [контрактах](references/contracts.md); назначенный child читает их сам.
Назначение старше вложенной процедуры (`dev`, `adapt`, `memo-bootstrap`): её вопросы,
записи памяти, субагенты, правка файлов правил и Git идут через brief (контракт, «Роли и
границы»). Настройку проекта (`adapt`, `memo-bootstrap`) назначайте отдельному worker с
`write_paths` конфигов или разрешением `save` в `memo_writes`; план `adapt` утверждаете вы в
согласованных правах, а имя scope памяти и перезапись существующих файлов — пользователь.
Доступные документы передавайте точными версионированными ссылками; inline оставляйте
нетранслируемый контекст и важные решения пользователя. Найденный файл не означает
регистрацию Skill: child подтверждает вызов либо чтение точного файла.
Без необязательного ресурса продолжайте; конфликт обязательной процедуры — блокер.

### 4. Выдать разрешение без конфликтов

Каждый writer Git-результата получает **свой worktree и ветку** `orch/<run>/<task>` от
текущего tip интеграции: изоляция клиента, если она есть, иначе `git worktree add`
от вашего имени ([параллельная доставка](references/parallel-delivery.md#4-worktree-и-ветки)).
Тогда физический ресурс writer — весь его worktree, и writers с пересекающимися файлами
работают одновременно: их логический конфликт решается при слиянии. Служебные
Git-операции (интеграционная ветка, worktree add/remove, удаление ветки) — ваши, с intent
в control до эффекта; содержимое файлов вы не меняете.

Вне worktree один writer по-прежнему владеет физическим ресурсом, а не строкой пути:
общий checkout в запасной политике, БД, порты, кэши, внешние сервисы, memo IDs.
Учитывайте `..`, симлинки, алиасы, hardlinks, регистр FS, каталог/вложенный файл и
побочные записи инструментов. Для новых файлов разрешайте родительский каталог и имя.
Проверяйте write/write и read/write; неясный алиас требует сериализации. Обычный читатель
ждёт интеграции/acceptance writer либо читает явно неизменяемый снимок. Чужой baseline
не откатывайте.

Сохраните intent/token до start. Запускайте child со свежим контекстом и самостоятельным
brief, не fork всей беседы; используйте только разрешённые параметры клиента. Модель child
выбирайте по [выбору модели](references/model-selection.md): самый дешёвый профиль, проходящий
пороги качества (код пишет и принимает не ниже `coding`, verifier не слабее автора, высокий
риск — `top`), при Jev не `off` — с калибровкой `jev.py calibrate`; затем самую дешёвую
модель каталога не ниже профиля и уровень усилия (уровень рассуждений) по тому же файлу.
Профиль, модель, уровень и причину сохраните в control до start.

**Гейт запуска модели** (каждый child, включая scout, repair и замену actor): start
разрешён, только когда в control назначения есть блок `model` (профиль, `model_id`, уровень
усилия со значением клиента, `selection`, причина) и блок `jev` — с ответом `calibrate` либо с
`skipped` и одним из кодов: `mode_off`, `scout`, `nothing_to_choose` (и `selection`, и
`effort_selection` не `chosen`). Другие причины пропуска не принимаются. При
`effort_selection: chosen` уровень передаётся в запуск явно: умолчание клиента — не выбор
(в dsh у `deepseek-v4-pro` это `high`). Обнаружили запуск без гейта — новые запуски не делайте, пока не
заполните блоки для всех назначений; уже запущенный child не перезапускайте ради модели,
а отметьте отклонение в итоге. Свяжите
возвращённый ID (или handle из control) с назначением до grant. Неопределённый запуск
сверяйте по token, не повторяйте вслепую.

Child до grant читает только brief/инструкции. Получите `ready`, проверьте фактический
источник, v3, цель, границы, criterion IDs и `git_policy_ack`. Запишите grant в control
и подтвердите get. При `session` адресно отправьте grant текущим assignment/attempt;
при `delegated` ready — итог gate-вызова, а grant передаётся в prompt exec-вызова того же
назначения ([runtime](references/runtime.md#транспорт-delegated)). Для Git-мутаций нужен
отдельный `git-grant`, file grant их не разрешает.

Каждое сообщение связывается envelope v3 с run/root/task/assignment/attempt/message ID,
отправителем и kind. Проверяйте реальный источник, игнорируйте повторы и устаревшее;
v1/v2/неизвестный протокол отклоняйте как `protocol_mismatch`.

### 5. Координировать до проверенного результата

Работайте автономно в согласованных границах: выбирайте технические решения после
исследования, сохраняйте assumptions в detail. Только parent запускает child;
bounded agents допустимы по назначенной процедуре и зарезервированным слотам.
Вызов скила не отменяет правил клиента, отказы доступа или необходимость отдельного
разрешения на push, публикацию, destructive/delete/secrets/payments и другие внешние эффекты.
Не подделывайте признаки пользовательского запроса в параметрах запуска и не обходите
ограничения через другую роль/tool.

Child передаёт вам только блокеры, требующие ваших прав, с фактами/попытками/рекомендацией.
Технические блокеры сначала решайте сами; независимая работа продолжается. Пользователь
нужен лишь для необходимого физического действия либо доказанного блокера, неразрешимого
в доступных правах/инструментах/scope. Сначала проверьте безопасные альтернативы и выполните
доступное; затем передайте один короткий пакет с минимальным решением, рекомендацией и Other.

Обычный repair остаётся у того же actor. Два неудачных repair стратегии — повод пересмотреть
причину, brief, разбиение и тест, а не автоматически звать человека. Сохраняйте историю,
repair_count стратегии и монотонный attempt; новая стратегия требует проверяемого прогресса,
нового назначения/version/details и ready/grant. До замены owner подтвердите stop/release
и остаточные эффекты. Timeout и запрос stop не release. Повтор без новых данных и без
безопасной альтернативы — unresolved blocker, не бесконечный fanout. Провал `light` или
два repair на `coding` из-за качества рассуждения — новая стратегия на старшем профиле
(при `top: только эскалация` в правилах проекта — только если таблица давала `top`);
профиль при repair/resume не понижается.

Сообщения child к parent, включая envelope, final и wrap-up, — **до 2000 символов каждое**.
Передавайте outcome/role/version/manifest, detail refs, краткий результат, risks/unverified
и release. Полные source/diff/logs/brief остаются у потребителя по refs; поток фрагментов
не обходит лимит. Не скрывайте риск ради длины: если receipt не помещается, уменьшите задание.
Нет memo у child — независимый verifier с memo сам получает evidence по проверяемому
источнику/прямой связи/адресному транскрипту. Без такого пути — `evidence_unavailable`,
не длинный отчёт parent и не файловый fallback.

### 6. Принять независимую проверку и доставку

В `worktree-integration/v1` правила этого шага применяются к финальному verifier tip
интеграции; отдельные ветки независимого verifier не получают — их проверяет dev-цикл
автора и проверки интегратора. Для non-Git результата — к каждому назначению, как прежде.

После submission подтвердите release writer и его процессов. Закрепите version/manifest
и frozen details, зарезервируйте ресурсы от новых writers. Независимому verifier выдайте
отдельный **read-grant до acceptance**: обычная зависимость на accepted создала бы deadlock.
Downstream работа пока запрещена.

Verifier сам строит полный inventory против исходного baseline, сверяет ownership и
manifest, проверяет артефакты/критерии/evidence и повторяет inventory/fingerprints в конце.
Pin учитывает presence/deletion, kind, mode, symlink target и SHA-256 regular bytes.
Нет baseline/inventory — blocked; пропуск изменения или выход за границы — fail.

Принимайте по источнику, корреляции, независимости, версии и покрытию критериев.
Receipt требует совпадения `criteria_version` и точного набора ваших frozen criterion IDs
без пропусков/дубликатов/лишних IDs, evidence refs, финальной сверки и release.
Self-report и unverified не pass. Изменение после аудита делает verdict устаревшим.

Для изменяемого Git-результата по умолчанию выполняйте `worktree-integration/v1`
([параллельная доставка](references/parallel-delivery.md), поля — в
[контрактах](references/contracts.md#worktree-integrationv1)):

1. **Capture.** До первой записи зафиксируйте целевую ветку пользователя (`target_ref`,
   `start_oid`, canonical repo/common-dir) и создайте от `start_oid` ветку
   `orch/<run>/integration`. Целевая ветка этой работой не меняется.
2. **Ветка задачи.** Writer в своём worktree ведёт dev-цикл с ревью и сам коммитит в свою
   ветку literal-staging'ом; отдельный git-grant для своей ветки не нужен, push, rebase
   чужого и merge в интеграцию запрещены. Итог — `branch_ready`: чистый worktree,
   `branch_tip_oid`, manifest, release. Это не acceptance.
3. **Интеграция.** Как только есть готовые ветки, integrator получает пакет и сливает
   их `--no-ff` в топологическом порядке, проверяя каждое слияние до коммита. Влитая ветка
   с зелёными проверками — `integrated`: это открывает её `hard`-зависимых. Возвращённая
   ветка — repair у автора: он вливает свежий tip интеграции в свою ветку и сдаёт снова.
4. **Финал.** Когда все узлы интегрированы или явно отклонены, один независимый verifier
   (не автор, не integrator) проверяет закреплённый tip интеграции: все критерии и проверки
   всех задач, diff `start_oid..tip` против manifest задач и решений конфликтов, историю.
   Его pass — `final_git` receipt всего запуска; только он даёт `acceptance=accepted`.

Запасная политика `start-target-linear-delivery/v1` — когда отдельный worktree для child
получить нельзя (ни изоляции клиента, ни `git worktree` в каталоге, доступном child) или
так решил пользователь. Сообщите одной строкой, что запись пойдёт последовательно:

1. До изменений child фиксирует canonical repo/worktree/git-dir/common-dir, полный target_ref,
   start_oid/unborn, index/status и baseline. Цель и baseline неизменны; drift блокирует.
2. Independent content pass открывает только последовательную Git-фазу. После release
   writers/verifier выдайте одному Git-owner отдельный git-grant с intent/expected_tip.
   Закрепите delivery unit и точный уже принятый prefix; подробности проверяет child.
3. Git-owner коммитит только owned accepted файлы в captured target. Stage точных filenames:
   `git --literal-pathspecs add -- <paths>` с отдельными quoted argv, не каталоги/`add-all`.
   Нет автоматических branches/worktrees, merge/helper, stash/reset/clean, force-push или
   присвоения чужого dirty. Разрешённый rebase — лишь своих доказанно unpublished commits.
   Конфликт с higher-priority branch-first/merge-sync блокирует доставку, не меняет target.
4. После Git-эффектов нужны новый pin/release и независимый `final_git` receipt, даже если
   tree не изменился. Сверьте independently observed identity и unit/prefix/OIDs/tree/history
   с control. Hook/content drift требует новой версии и нужных проверок. Crash сверяется
   по фактическому состоянию и intent; уже сделанный commit не повторяется.

`phase_criteria` заранее делит content-required и deferred Git-final IDs; final требует
**всех** IDs=pass. Required-артефакт остаётся required и у read-only verifier (`file_only`).
Для чистого исследования/non-Git/no-change явно задайте `not_applicable` с причиной:
обычный independent receipt без deferred, пустой commit и принудительный dev не нужны.

Только вы ставите `acceptance=accepted` после final_git либо not_applicable pass и открываете
зависимую работу (в `worktree-integration/v1` зависимые узлы открывает уже `integrated`). После acceptance выполните строки принятого `memo_proposals`
(save/update/forget) с явным scope; у отклонённого результата они не выполняются. Rejected/paused/release не открывают её. Резерв для repair снимайте отдельно
после release, с новым grant/version; интеграционная правка тоже требует нового аудита.
Не перечитывайте исходники и не повторяйте тесты за verifier по умолчанию.

### 7. Завершить или восстановить работу

Продолжайте до итоговой приёмки, а не только до плана/worker report. При ожидании сохраните
малый control и используйте реально поддерживаемые push-events либо результат вызова
`delegated`. Подлинное уведомление возобновляет работу без «продолжить?», но не является
согласием пользователя. Не опрашивайте child циклом, планировщиками, мониторами или
сообщениями «готово?» и не обещайте пробуждение, которого клиент не поддерживает.
Конец API-хода не завершает задачу.

Для resume сверьте прежнего parent/передачу управления, root/current frontier/control
и нужные compact receipts, не всю историю. Сохраняйте mode/cap (включая `null`), target и
baseline; revision не lock/CAS, recall не реестр. Назначенный child сверяет uncertain intent,
Git-состояние и оставшиеся эффекты. Неясность означает paused, не повтор start/commit.

В итоге укажите принятое/непринятое, receipt refs, реальные S/F/R проверки,
риски/непроверенное, root/session links, запуски/repair с профилем и моделью каждого и
эскалации. Не обещайте экономию без замеров.

После acceptance `worktree-integration/v1`:

- **Не трогайте целевую ветку сами.** Одним вопросом спросите пользователя, что сделать с
  `orch/<run>/integration`: влить в целевую ветку локально, запушить/открыть PR или
  оставить; дайте рекомендацию. Без ответа ничего не вливается и не пушится.
- **Уберите слитое.** Удаляйте worktree и ветку задачи, только если ветка влита в
  интеграцию, worktree чистый и процессы child остановлены: `git worktree remove` без
  `--force`, `git branch -d`, не `-D`. Ветка интеграции остаётся. Об уборке скажите
  в стартовом статусе одной строкой, отдельного вопроса не нужно.
- **Таблица остатков.** Всё, что не удалено к концу сессии (не принято, грязно, отказ Git,
  ждёт решения), — таблицей «worktree/ветка · состояние · почему не удалено · что сделать».
  Непринятый или прерванный запуск ничего не удаляет: всё в таблицу.

Push, публикация, архивирование и удаление сессий не автоматические.
Статусы memo — штатные; `doing` с branch задачи/workflow=orchestrate, `review` только для PR,
`release` только после слияния. Blocked — связь `blocked_by`, которую снимают по фактам;
accepted не означает done/релиз.
