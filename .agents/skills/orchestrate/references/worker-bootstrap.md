# Встроенный worker-bootstrap v3

Используйте этот вход, если session-worker отсутствует или субагент клиента не видит
установленные скилы. Отдельный пакет и среда авторинга не нужны; ничего не устанавливайте.
Это инструкции child одного назначения, не новый координатор и не замена child-агентам клиента.

## Что загрузить

Прочитайте [контракт v3](contracts.md) из того же каталога. Он содержит полные схемы Brief,
Envelope, git_delivery, coordinator-summary и receipt, а также правила владения и проверки.
Раздел Git-delivery нужен для Git-результата и его audit; для read-only/non-Git результата
используйте правила not_applicable. Назначенные проектные инструкции читайте напрямую.

Parent проверяет доступность обоих файлов и передаёт точные пути. Если путь недоступен,
передайте inline этот bootstrap **вместе с контрактом**, а не одну неработающую ссылку.
Нельзя заменять их ссылкой на соседний session-worker или чужой домашний каталог.
Отсутствие session-worker сообщается явно. v1/v2/неизвестный или неполный v3 —
blocked protocol_mismatch до выполнения, без молчаливого дополнения полей.

## Исполнение назначения

1. Определите `transport` из brief: `session` — адресуемый канал parent, `delegated` —
   итог текущего вызова (`delegated_phase` gate или exec, правила — в разделе «Транспорт»
   контракта). Проверьте фактический канал parent, IDs назначения и доступность обязательных refs.
   Нет канала — blocked no_parent_channel, не вопрос человеку или файловый fallback.
   До grant читайте только brief и назначенные инструкции. Для разработки загрузите
   проектный dev; read-only роли — только применимые назначенные процедуры.
2. Отправьте ready с целью, границами, criterion IDs, ограничениями и git_policy_ack.
   Дождитесь подлинного grant parent после bind и сохранения владения. При `delegated`
   gate ready — итог вызова, после него завершитесь; grant придёт в prompt exec-вызова. Peer не выдаёт grant;
   старое назначение не освобождает текущее. Обычный grant — file_only, не право на Git;
   исключение — `worktree-integration/v1`: writer сам коммитит только в свою ветку своего
   worktree, integrator — только в интеграционную ветку (раздел policy в контракте).
3. Выполняйте задачу внутри read/write/side_effect границ и общего бюджета. Учитывайте
   физические алиасы/hardlinks и read/write конфликты. Не меняйте чужой baseline, root/control,
   permissions/config/инструкции агента (CLAUDE.md, AGENTS.md и аналоги) или ветку вне назначенной. Пишите
   только назначенные detail IDs после get и проверки scope/назначения. Новые child и вопросы
   человеку — только через parent. Назначение старше вложенной процедуры (`dev` и др.): её
   записи памяти — строками в `memo_proposals_ref`, субагенты — в пределах `bounded_subagents`,
   правка файлов правил агента — только из `write_paths`.
   Обычные технические решения выбирайте сами после исследования; блокер передайте с фактами,
   попытками, вариантами и рекомендацией. Необязательный ресурс не останавливает работу.
4. Сохраните полный result/evidence и manifest в details, прекратите процессы/запись,
   отправьте summary/release. Каждое сообщение к parent с envelope, final и wrap-up —
   каждый ≤2000 символов; без source/diff/stdout и потока фрагментов. Нет memo — evidence
   самостоятельно собирает назначенный независимый verifier с memo; иначе blocked
   evidence_unavailable, не полный отчёт parent и не файловый канал координации.
5. Verifier работает только по отдельному read-grant после writer submission/release:
   проверяет actual inventory, pin и критерии, повторяет сверку в конце, пишет полный audit
   и отдельный compact receipt. В линейной policy content pass открывает лишь Git-owner фазу,
   в `worktree-integration/v1` проверка одна — final_git на tip интеграции;
   required Git требует final_git receipt даже при unchanged tree. Только parent ставит
   acceptance=accepted; release/rejected/paused не открывают downstream.
6. После submission/release не пишите без нового назначения/grant. Repair получает новые
   assignment/version/detail IDs и ready/grant; старые записи не меняются. Два неудачных
   repair стратегии требуют диагноза parent, не автоматического вопроса человеку или сброса
   attempt. Нового owner назначает parent лишь после фактического release и сверки эффектов.

Не запускайте child-агентов, CLI других агентов или скрытую замену через SDK/tmux/shell.
Bounded subagents — только по назначенной процедуре и в слотах parent. Нет опроса child
циклом, планировщиками или мониторами, обхода отказов
через peer, самостоятельной публикации/архивации/удаления или обещания невидимых permission
prompts. Итог — по назначенному каналу в лимите, без вопросов и предложений пользователю.
