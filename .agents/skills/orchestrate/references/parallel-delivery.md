# Параллельная доставка: карта работ, worktree и интеграция

Читайте при старте работы с Git-результатом: перед разбором задач, построением карты
и первым dispatch. Цель — **минимальное время до принятого результата**: всё, что может
идти одновременно, идёт одновременно; ждут только настоящие зависимости.
Схемы полей и правила child — в [контрактах](contracts.md#worktree-integrationv1).

## Почему так

Общий checkout заставляет сериализовать любые записи: один index, один HEAD, один
Git-owner. Отдельный worktree у каждого writer убирает физические конфликты файлов и
index: writers работают одновременно и коммитят в свои ветки. Логические конфликты
переезжают в одну точку — слияние, где их решает один интегратор и где один независимый
verifier проверяет итог целиком. Исходная ветка пользователя не меняется до его решения.

## 1. Приём работы

Работа приходит одним из двух путей; оба заканчиваются одинаковым набором memo-задач.

**A. Задачи из memo.** Берите **только задачи, которые назвал пользователь**: ID, эпик
или root. Для эпика/root включайте его подзадачи (`part_of`). Каждую получите адресным get;
читайте summary/критерии/связи, не всю историю. Задачи в `done`/`release` пропустите и
перечислите в итоге. Не подтягивайте неназванные задачи, даже если названная от них
`blocked_by`: такая задача остаётся заблокированной, а в первом статусе пользователю
одной строкой — чем и почему (например, «#12 ждёт #7, она вне выбранного набора»).

**B. Одна большая задача.** Сначала оцените: если это T0–T1 и одна область кода — одна
ветка, декомпозиция только замедлит. Иначе назначьте planner (профиль по
[выбору модели](model-selection.md); T2–T3 — `top`). Planner возвращает в свой detail:

- **контракт первым:** общие интерфейсы, схемы, типы, от которых зависят остальные,
  выделяются в отдельную раннюю подзадачу — так остальные могут стартовать сразу после неё;
- **подзадачи** размера одного dev-lead (T1–T2), каждая с целью, критериями, проверками,
  предполагаемыми областями записи и явными зависимостями;
- **непересекающиеся области записи** там, где это возможно; общие точки (реестр модулей,
  индекс экспорта, changelog, lockfile) — названы явно;
- **ожидаемые точки конфликтов** и как их снять (порядок, отдельная задача-«клей»).

Parent проверяет разбиение (покрытие цели, нет циклов, каждая подзадача проверяема) и
сохраняет подзадачи в memo как task с `part_of` к большой задаче и `blocked_by` по
зависимостям. Записи проекта создаёт parent; planner только предлагает. Дальше подзадачи
идут тем же путём, что и в варианте A.

## 2. Карта зависимостей

Карта — граф: узлы = задачи, рёбра = «B нельзя начинать до интеграции A». Её строит
planner по фактам scout (`light`) по всему набору сразу, в detail карты;
parent хранит в control только компактную форму:

```yaml
work_map:
  version: 1
  nodes:
    - {task: T1, size: T1, risk: low, areas: [src/billing/], est: S}
  edges:
    - {from: T1, to: T3, kind: hard, reason: "T3 вызывает API из T1"}
    - {from: T2, to: T4, kind: soft, reason: "общий src/registry.ts"}
  critical_path: [T1, T3, T5]
  blocked_outside: [{task: T6, by: "#7", reason: "вне выбранного набора"}]
```

| Ребро | Откуда | Что значит |
|---|---|---|
| `hard` | `blocked_by` в memo; B использует код/контракт/данные A; B меняет то, что создаёт A | B стартует от tip интеграции, уже содержащего A |
| `soft` | Пересечение областей записи без смысловой зависимости | По умолчанию **параллельно**: конфликт решит интегратор. Сериализуйте, только если обе задачи переписывают одну и ту же логику — тогда слияние дороже ожидания |

Проверки карты: нет циклов (цикл — planner делит или объединяет задачи; не получилось —
blocker); каждая выбранная задача есть в узлах; внешние блокеры перечислены.
Слишком мелкие задачи (T0) в одной области объедините в одно назначение: у каждого child
есть цена холодного старта. Карта меняется только новой версией; repair не перестраивает
её молча.

Общие ресурсы вне Git worktree не изолированы: БД, фиксированные порты тестов, глобальные
кэши, внешние сервисы, общие memo IDs. Для них по-прежнему один writer — либо
уникальный ресурс на worktree (отдельная БД/порт), либо сериализация через ребро `hard`.

## 3. Планирование и запуск

Режим по умолчанию — **fast без лимита** (`active_limit: null`). Economy или fast с N —
только по явной просьбе пользователя; тогда они соблюдаются точно.

1. **Готов** = все входящие `hard` рёбра интегрированы (статус `integrated`, см. ниже).
2. Запускайте **все готовые узлы сразу**, не дожидаясь «волны». При лимите N первыми
   идут узлы критического пути, затем узлы с наибольшим числом зависимых.
3. Как только узел интегрирован — сразу запускайте узлы, которые он разблокировал.
4. Каждому writer — dev-lead (или worker для не-кода), свой worktree, своя ветка от
   **текущего tip интеграции** (`base_oid`). Профиль — по [выбору модели](model-selection.md).
5. Пока writers работают, planner/scout может готовить brief следующих узлов: это тоже
   параллельная работа.

## 4. Worktree и ветки

Имена (`<run>` — короткий ID root, `<task>` — ID задачи; только `a-z0-9-`):

| Что | Ref | Где |
|---|---|---|
| Интеграция | `refs/heads/orch/<run>/integration` от `start_oid` целевой ветки | worktree интегратора |
| Задача | `refs/heads/orch/<run>/<task>` от `base_oid` | worktree writer |
| Повтор после repair | та же ветка задачи, новые коммиты | тот же worktree |

Как получить worktree, в порядке предпочтения:

1. **Изоляция клиента** (worktree-режим субагента или сессии). Child первым делом
   проверяет, что его worktree отдельный (свой git-dir, общий common-dir), и делает
   `git switch -c orch/<run>/<task> <base_oid>` — если клиент создал worktree от другой
   точки, ветка всё равно начинается от `base_oid`.
2. **Parent создаёт сам** через Git CLI, если клиент изоляции не даёт, но child может
   работать в указанном каталоге:
   `git worktree add -b orch/<run>/<task> <path> <base_oid>`. `<path>` — вне рабочего
   дерева проекта, например `<родитель проекта>/<repo>.orch/<run>/<task>`; путь передаётся
   в brief как `worktree.path`, child работает только там.
3. **Нельзя ни так, ни так** — worktree-integration недоступна: используйте запасную
   политику `start-target-linear-delivery/v1` (writers по очереди в общем checkout) и
   одной строкой сообщите пользователю, что параллельной записи не будет и почему.

Создание интеграционной ветки, worktree и их удаление — служебные Git-операции parent.
До каждой сохраните intent в control (что, где, ожидаемый OID), после — фактический
результат. Содержимое файлов parent не меняет и не коммитит.

## 5. Непрерывная интеграция

Writer завершает работу так: dev-цикл с ревью пройден, все изменения закоммичены в ветку
задачи, worktree чистый, процессы остановлены, summary с `branch_tip_oid` и release.
Это `branch_ready`, не acceptance.

Интегратор — отдельный child (`role: integrator`, не автор этих веток), профиль не ниже
`coding`, высокий риск — `top`. Он владеет worktree интеграционной ветки и получает
**пакет** готовых веток в топологическом порядке карты. Запускайте его, как только
появилась первая готовая ветка, а не когда готовы все: ранняя интеграция открывает
зависимые узлы и находит конфликты, пока авторы ещё помнят контекст.

Для каждой ветки пакета интегратор:

1. сверяет tip ветки с `branch_tip_oid` из summary (сдвиг — blocked);
2. `git merge --no-ff --no-commit <branch_tip_oid>` в интеграционную ветку;
3. текстовый конфликт решает сам, если решение очевидно из обеих сторон (оба добавили
   строку в реестр, независимые правки рядом); смысловой конфликт — `git merge --abort`
   и возврат ветки автору;
4. прогоняет быстрые проверки из brief на ещё не закоммиченном слиянии; зелёные —
   `git commit --no-edit`; падение из-за ветки — `git merge --abort` и возврат ветки
   автору с фактами. Так в интеграции не остаётся сломанных коммитов и не нужен reset;
5. фиксирует в detail: OID до/после, решённые конфликты (файлы и суть решения), проверки.

Итог пакета parent: какие ветки `integrated` с OID, какие возвращены и почему, новый tip.
Возвращённая ветка — repair у того же автора в его worktree: автор вливает текущий tip
интеграции в свою ветку (`git merge <integration_tip>`), снимает конфликт по смыслу,
повторяет проверки и снова сдаёт `branch_ready`. Это обычный repair со счётчиком.

Статус узла `integrated` (ветка влита, проверки после слияния зелёные) открывает зависимые
узлы. Это сознательный компромисс скорости: полная независимая проверка — одна, в конце.

## 6. Финальная проверка и решение пользователя

Когда все узлы `integrated` (или явно отклонены), parent назначает независимого verifier
(не автор, не интегратор, не соавтор; профиль не ниже самого сильного автора) на
закреплённый tip интеграции. Verifier:

- прогоняет все проверки и все критерии всех задач на tip интеграции;
- сверяет diff `start_oid..tip` с объединением manifest задач и решений конфликтов:
  лишнее или потерянное — fail;
- проверяет историю: первый родитель ведёт к `start_oid`, каждая принятая ветка влита
  ровно один раз, чужих коммитов нет;
- проверяет, что исходная целевая ветка не сдвинута этой работой.

Pass → parent ставит `acceptance=accepted` для всего запуска и выполняет `memo_proposals`.
Fail → repair у виновной ветки (через интеграцию заново) или у интегратора.

После acceptance исходная ветка **не меняется автоматически**. Parent одним сообщением
сообщает итог и спрашивает пользователя, что делать с `orch/<run>/integration`:

- влить в исходную ветку локально (fast-forward, если исходная не ушла вперёд; иначе
  merge — его выполняет Git-owner child по `git-grant` и проверяет verifier);
- запушить ветку интеграции и/или открыть PR;
- оставить как есть.

Рекомендация — по ситуации, обычно «запушить и открыть PR», если у проекта есть remote.

## 7. Уборка и таблица остатков

После acceptance удаляйте то, что гарантированно ничего не теряет. Удаление объявите
пользователю в стартовом статусе одной строкой («после приёмки уберу слитые worktree и
ветки задач»), отдельного вопроса не нужно.

Удаляется worktree/ветка задачи, если **все** условия верны:

- ветка влита: `git merge-base --is-ancestor <branch_tip> <integration_tip>`;
- worktree чистый: `git -C <path> status --porcelain` пуст, нет незавершённой операции;
- ни один процесс child не работает в нём (release подтверждён).

Команды без принуждения: `git worktree remove <path>` (без `--force`), затем
`git branch -d orch/<run>/<task>` (`-d`, не `-D`). Отказ Git — не повод добавить force:
объект остаётся и попадает в таблицу. Worktree интеграции удаляется так же, если он
чистый; **ветка интеграции остаётся** — это результат. Worktree, которые клиент создал и
убирает сам, не трогайте, только проверьте и отметьте.

Если в конце сессии что-то не удалено, итог содержит таблицу:

| Worktree / ветка | Состояние | Почему не удалено | Что сделать |
|---|---|---|---|
| `../app.orch/r7/t4` / `orch/r7/t4` | 2 коммита не влиты | Задача T4 отклонена после 2 repair | Решить: доработать или удалить вручную |
| `../app.orch/r7/t2` | Изменённые файлы вне коммита | Child остановился с blocked | Посмотреть diff, затем `git worktree remove` |
| `orch/r7/integration` | Результат | Ждёт вашего решения о слиянии/PR | См. вопрос выше |

Не принятый или прерванный запуск ничего не удаляет: все worktree и ветки идут в таблицу.

## Пример

Пользователь: «Сделай задачи #21, #22, #23, #24 из memo». В memo #23 `blocked_by` #21;
planner нашёл, что #22 и #24 оба правят `src/routes/index.ts` (soft).

- t=0: создать `orch/r9/integration` от HEAD `main`; запустить #21, #22, #24 одновременно,
  каждый в своём worktree от `start_oid`.
- #22 готова первой → интегратор влил её; #21 готова → влил, #23 сразу стартует от нового
  tip; #24 готова → конфликт в `index.ts` (обе добавили маршрут) — интегратор решил сам.
- #23 готова → влита. Независимый verifier проверил tip интеграции → accepted.
- Parent: итог, вопрос «влить `orch/r9/integration` в `main` / PR / оставить», три worktree
  и ветки задач удалены, таблица остатков пуста.
