# Тестируемость как свойство архитектуры

Тестируемость — не задача QA и не «покрытие». Это следствие того, как проведены границы.
Граница между «легко тестируемым» и «трудно тестируемым» почти всегда совпадает с
архитектурной границей.

Точные формулировки — `references/book-digest.md` скила `clean-architecture` (гл. 4, 23, 28), если он установлен рядом.

## Тесты — часть системы

Тесты — самый внешний круг архитектуры: **от тестов не зависит ничто, тесты зависят от всего**.
Они развёртываются независимо и не попадают в продакшн, но проектируются с тем же вниманием,
что и остальной код. Плохо спроектированные тесты делают систему **жёсткой**: разработчики
начинают избегать изменений, потому что «сломается тысяча тестов».

Философская основа (структурное программирование): тестированием нельзя доказать правильность,
можно только опровергнуть. Поэтому архитектор строит **модули, неправильность которых легко
доказать** — то есть модули, которые можно исполнить изолированно и быстро.

## Шаблон «Скромный объект» (Humble Object)

Разделить поведение на два модуля:
- **скромный** — всё, что трудно тестировать, сведённое до предела (никакой логики);
- **тестируемый** — всё остальное.

Канонические применения:

| Граница | Скромный объект (без логики) | Тестируемый объект |
|---|---|---|
| UI | View: перенос готовых значений на экран | Presenter: форматирование, флаги, подписи, таблицы строк → ViewModel |
| Хранилище | реализация шлюза (SQL, ORM, файлы) | интерактор + порт со смыслом приложения |
| ORM | преобразователь данных (маппинг) | доменные типы |
| Внешние службы | клиент/слушатель службы: сериализация и транспорт | код, работающий с простыми структурами |
| Оборудование/ОС | драйвер, HAL/OSAL | политика поверх абстракции |

Правило: **вся логика уходит на тестируемую сторону**. Если в скромном объекте появился `if`
или вычисление — граница нарушена.

## Проблема хрупких тестов

Причины хрупкости, по убыванию вреда:
1. **Тесты бизнес-правил через UI**: изменение страницы авторизации или навигации ломает
   сотни тестов.
2. **Структурная связанность**: тестовый класс на каждый прикладной класс, тестовый метод на
   каждый метод. Любой рефакторинг ломает тесты; код становится жёстким.
3. **Тесты через реальную инфраструктуру**: БД, сеть, файлы — медленно, нестабильно, требует
   окружения.
4. **Тесты, знающие внутренние детали** (приватные поля, порядок вызовов, точную структуру SQL).

Первое правило проектирования ПО — **«не зависьте от изменчивого» (Don't depend on volatile
things)**, и оно одно и то же для тестируемости и для всего остального. GUI изменчив, значит
набор тестов, работающий через GUI, обречён быть хрупким. Значит, бизнес-правила должны
проверяться **без UI**.

## Программный интерфейс для тестирования (тестовый API)

Отдельный интерфейс, через который тесты работают с системой:
- надмножество операций интеракторов и адаптеров, которыми пользуется UI;
- скрывает **структуру** приложения от тестов (не только UI);
- позволяет обходить дорогие ресурсы и ограничения безопасности, приводить систему в нужные
  состояния;
- даёт коду и тестам развиваться независимо: тесты со временем становятся конкретнее, код —
  абстрактнее.

Безопасность: если тестовый API опасен в продакшне, он и его небезопасные реализации живут в
**отдельном компоненте**, устанавливаемом независимо и не попадающем в производственную сборку.

## Практическая пирамида для чистой архитектуры

| Уровень | Что проверяет | Зависимости | Скорость |
|---|---|---|---|
| Тесты сущностей | критические бизнес-правила | нет | микросекунды |
| Тесты вариантов использования | сценарии приложения, порты подменены | нет инфраструктуры | миллисекунды |
| Тесты адаптеров | маппинг, SQL-запросы, сериализация, презентаторы | реальная технология, узко | десятки мс |
| Сквозные тесты | сборка целиком, критичные пути | всё | секунды, единицы штук |

Ориентир: набор тестов ядра выполняется **секунды**. Если минуты — граница с инфраструктурой
не проведена.

## Что подменять и чем

- Подменяем **порты, объявленные в ядре**, — это спроектированные швы.
- Не подменяем то, что не является границей: внутренние функции, приватные хелперы, сущности.
- Стабильную платформу (стандартная библиотека, коллекции) не подменяем.
- Время, случайность, идентификаторы, окружение — это I/O: выводить в порты (`Clock`,
  `IdGenerator`, `RandomSource`), иначе тесты недетерминированы.
- Предпочитать простые ручные реализации портов (in-memory, fake) моковым фреймворкам с
  проверкой порядка вызовов: моки, проверяющие взаимодействия, воспроизводят структуру кода в
  тестах и делают их хрупкими.

Хороший индикатор дизайна: **in-memory реализация порта пишется за 20 строк**. Если нет — порт
сформулирован в терминах технологии, а не приложения.

## Процедура: сделать нетестируемый код тестируемым

1. Найти в модуле все обращения к внешнему миру (I/O, время, случайность, глобальное
   состояние, синглтоны, статические вызовы фреймворка).
2. Для каждого — ввести порт в терминах приложения.
3. Вынести конкретную реализацию наружу, сделать её скромной (без логики).
4. Перенести всю логику в тестируемую часть.
5. Перенести связывание в `Main`/composition root.
6. Написать тест варианта использования с in-memory портами.
7. Оставить один узкий тест на реальную реализацию порта (что SQL действительно работает).
8. Удалить сквозные тесты, дублирующие проверку бизнес-правил через UI.

## Точки адаптации к языку

- механизм подмены: конструктор/параметры функции (предпочтительно), интерфейсы, замыкания,
  модульные подстановки;
- инструменты изоляции времени и случайности;
- фреймворк тестов, соглашения об именовании и организации тестового дерева;
- как исключить тестовый API из производственной сборки (профили сборки, отдельный артефакт,
  флаги компиляции);
- инструменты для архитектурных тестов (проверка направления импортов).

## Признаки проблем

- тест требует запущенной БД, брокера, сети или браузера ради проверки бизнес-правила;
- в тесте настраивается 6+ моков, чтобы вызвать одну операцию;
- изменение имени приватного метода ломает тесты;
- тесты падают «иногда» (время, порядок, параллелизм, реальные часы);
- каждый рефакторинг сопровождается массовой правкой тестов;
- команда отказывается от улучшения кода, потому что «поедут тесты» — это уже архитектурный
  дефект, а не тестовый.
