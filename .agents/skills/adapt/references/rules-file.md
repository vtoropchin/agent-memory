# Блок «Архитектура» в файле правил проекта

Главный продукт адаптации: набор языко-независим, и всё, что зависит от стека, живёт здесь.

## Какой файл правил

Файл правил — то, что клиент агента читает в начале каждой сессии:

| Клиенты проекта | Куда писать блок |
|---|---|
| только Claude Code | `CLAUDE.md` |
| только клиенты, читающие `AGENTS.md` (DeepSeek Harness, Hermes Agent, Codex и др.) | `AGENTS.md` |
| Claude Code и другие | `AGENTS.md`; в `CLAUDE.md` — строка импорта `@AGENTS.md` (Claude Code подставит файл), если её нет |
| клиент читает другой файл | файл, который клиент читает по своей документации |

Уже есть `AGENTS.md` или `CLAUDE.md` с правилами проекта — писать туда, где правила уже живут,
и только связать второй файл. Не дублировать блок в двух файлах: копии расходятся. Ниже
«`AGENTS.md`/`CLAUDE.md`» означает выбранный файл правил.

## Граница по времени жизни записи

- **`AGENTS.md`/`CLAUDE.md` — стабильные правила**: структура каталогов, что публично, команды проверки,
  правила зависимостей, целевое время прогона тестов. Меняются редко, нужны в каждой задаче,
  дешевле всего читаются из файла.
- **`memo` — решения, контекст, история**: что отложено и до каких пор, какой компромисс принят и
  при каком условии пересматривается, какая граница проведена и почему. Растут с каждой задачей,
  нужны выборочно, ищутся по смыслу. См. `references/decisions-in-memo.md` скила `dev`.

Смешение двух категорий — самая частая ошибка адаптации: список компромиссов в `AGENTS.md`/`CLAUDE.md` растёт,
перестаёт читаться, и ревьюер раз за разом сообщает об уже принятом решении.

## Шаблон

Заполняется фактическими значениями фазы 1. Ни одного `<плейсхолдера>` в результате остаться не
должно; пункт, к которому в проекте нет ответа, — удаляется, а не оставляется пустым.

```markdown
## Архитектура

Дисциплина: чистая архитектура (набор скилов в `<каталог скилов>`, точка входа — скил `dev`).

**Соответствия понятий в этом проекте**

| Понятие | Реализация здесь |
|---|---|
| Компонент (единица развёртывания) | <пакет/модуль/крейт/таргет> |
| Порт | <интерфейс/протокол/трейт/Protocol> |
| Структура через границу | <record/struct/dataclass/DTO> |
| Composition root (`Main`) | <файл/функция> |
| Ограничение видимости | <механизм> |
| Подмена в тестах | <механизм> |
| Изоляция времени и случайности | <порты Clock/IdGenerator/Random> |

**Структура**

- Ядро: `<пути>` — сущности и варианты использования. Зависит только от стандартной библиотеки
  и `<явный белый список>`.
- Порты объявляются в ядре и именуются на языке предметной области.
- Адаптеры: `<пути>`. Composition root: `<путь>`; варианты сборки: dev / test / prod.
- Публичны только точки входа компонентов; реализации портов непубличны.
- Генерируемый код: `<каталоги>` — под правила зависимостей не подпадает.

**Проверка**

- Тесты: `<дословная команда>`; линт/стиль: `<дословная команда>`; типы: `<команда>`.
- Правило зависимостей проверяется: `<команда>`. Текущая базовая линия нарушений: `<N>`.
- Тесты ядра идут без БД, сети и UI; целевое время прогона: `<N с>`.

**Отложенные решения**

Категории, которые обязаны оставаться заменяемыми без правки ядра: `<БД, транспорт, фреймворк,
режим развёртывания, целевое железо>`. Конкретные отложенные решения, компромиссы и проведённые
границы хранятся в памяти проекта (`memo`), а не в этом файле: recall в начале задачи, запись по
ходу.

**Идиомы языка (не считать нарушениями)**

- <например: интерфейсы объявляются потребителем — идиома Go, не нарушение DIP>
- <например: порты выражены структурной типизацией; отдельные объявления не требуются>
```

Раздел «Идиомы языка» заполняется по итогам фазы 7 — из реальных ложных срабатываний, а не
превентивно. Пустой раздел лучше выдуманного: каждая строка в нём ослабляет ревью.

## Слияние с существующим `AGENTS.md`/`CLAUDE.md`

1. Файла нет → создать с одним этим блоком, ничего не придумывая сверх.
2. Файл есть, раздела «Архитектура» нет → добавить блок в конец, чужие разделы не трогать.
3. Раздел есть → дополнить недостающими пунктами, сохранив формулировки проекта. Стиль проекта
   важнее стиля шаблона.
4. **Противоречие** (в проекте записано правило, несовместимое с блоком: другое расположение
   ядра, другой запрет, другая команда) → не переписывать. Показать оба варианта и спросить.
5. Уже существующие в проекте команды и конвенции переносятся дословно, включая неочевидные
   различия («check прогоняет только стиль, тесты запускаются отдельной командой») — именно на
   таких деталях агенты чаще всего ошибаются.

## Проверка результата

- Ни одного `<плейсхолдера>`.
- Каждая команда скопирована из проекта и хотя бы раз запущена.
- Пути ядра и адаптеров существуют в дереве.
- В блоке нет решений, компромиссов и истории — только правила.
