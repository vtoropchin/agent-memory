# Адаптация набора под конкретный язык и проект

Скилы и агенты языко-независимы. Всё, что зависит от стека, заполняется один раз здесь и
переносится в `AGENTS.md`/`CLAUDE.md` проекта. После заполнения агенты перестают гадать об идиомах и
начинают говорить на языке вашего проекта.

> Этот документ — ручной путь и справочник. Автоматический путь: установить набор в проект
> (`make install PROJECT=/путь/к/проекту` из репозитория скилов или стандартным skills CLI), затем
> в самом проекте запустить скил `adapt`. Он проходит те же шаги (его фазы 1, 5–7), плюс подключает набор
> к клиентам агента (агенты, память `memo`) и закрепляет имя проекта в памяти. Обновление набора —
> снова установка тем же способом и `adapt` в режиме обновления: `REVIEW.md` и
> `AGENTS.md`/`CLAUDE.md` не перезаписываются. Профили стеков и средства принуждения по языкам —
> `references/` скила `adapt`.

## Шаг 1. Заполнить таблицу соответствий

| Понятие набора | Чем реализуется в вашем языке | Пример заполнения |
|---|---|---|
| Компонент (единица развёртывания) | ? | пакет / модуль сборки / библиотека / крейт / workspace-проект |
| Порт (абстракция) | ? | интерфейс / протокол / трейт / абстрактный класс / тип функции |
| Структура пересечения границы | ? | record / struct / dataclass / frozen-объект |
| Сущность | ? | класс / структура + функции / модуль |
| Composition root (`Main`) | ? | функция `main` / модуль запуска / фабрика приложения |
| Ограничение видимости | ? | `private` / `internal` / `pub(crate)` / список экспорта модуля |
| Подмена в тестах | ? | передача аргументом / интерфейс / замыкание / подстановка модуля |
| Проверка направления импортов | ? | архитектурный тест / линтер импортов / границы модулей сборки |
| Анализ графа зависимостей | ? | инструмент / скрипт по импортам |
| Изоляция времени и случайности | ? | порт `Clock`, `IdGenerator`, `RandomSource` |

## Шаг 2. Зафиксировать структуру проекта

Опишите фактическое дерево и назначение каталогов. Ориентир — `code-organization`:

```
<домен>/                  ← компонент, кричит о предметной области
    <точка входа>         ← единственный публичный интерфейс компонента
    entities/
    usecases/
    adapters/
delivery/                 ← http / cli / ui
main/                     ← composition root: dev, test, prod
tests/
```

Запишите: что публично, что скрыто, где граница между ядром и инфраструктурой, сколько единиц
сборки.

## Шаг 3. Настроить принуждение

Минимальный набор правил, которые должны проверяться автоматически:

1. Ядро (`entities`, `usecases`) не импортирует инфраструктуру и сторонние фреймворки.
   Белый список исключений: `<перечислить>`.
2. Адаптеры не импортируют друг друга (веб не зовёт хранилище напрямую).
3. Нет циклов между компонентами.
4. Конкретные реализации портов создаются только в `main/`.
5. Аннотации/атрибуты фреймворков не встречаются в ядре.

Порядок предпочтения средств: система модулей и видимость → границы сборки → архитектурный тест
→ линтер → ревью. Первые три дают обратную связь до мержа.

Заготовка архитектурного теста (псевдокод, переведите в свой фреймворк):

```
test "ядро не зависит от инфраструктуры":
    for file in sources("<домен>/entities/**", "<домен>/usecases/**"):
        for imp in imports(file):
            assert not matches(imp, ["infrastructure/**", "http/**", "<фреймворки>"]),
                   "{file} импортирует {imp}"
```

## Шаг 4. Записать правила в `AGENTS.md`/`CLAUDE.md` проекта

Граница проходит по времени жизни записи:

- **`AGENTS.md`/`CLAUDE.md` — стабильные правила проекта**: структура каталогов, что публично, команды
  проверки, правила зависимостей, целевое время прогона тестов. Меняются редко, нужны в каждой
  задаче, дешевле всего читаться из файла.
- **`memo` (долговременная память) — решения, контекст и история**: что отложено и до каких пор,
  какой компромисс принят и при каком условии пересматривается, какая граница проведена и
  почему. Растут с каждой задачей, нужны выборочно, ищутся по смыслу — файл для этого плохое
  место. См. `dev/references/decisions-in-memo.md`.

Шаблон блока:

```markdown
## Архитектура

Дисциплина: чистая архитектура (набор скилов в `<каталог скилов>`).

- Ядро: `<пути>` — сущности и варианты использования. Не зависит ни от чего, кроме
  стандартной библиотеки.
- Порты объявляются в ядре, именуются на языке предметной области.
- Адаптеры: `<пути>`. Composition root: `<путь>`, варианты: dev/test/prod.
- Видимость: публичны только точки входа компонентов; реализации портов непубличны.
- Правило зависимостей проверяется: `<команда>`.
- Тесты ядра выполняются без БД, сети и UI; целевое время прогона: `<N с>`.
- Категории решений, которые остаются отложенными (менять можно без правки ядра):
  `<БД, транспорт, фреймворк, режим развёртывания>`.
- Конкретные отложенные решения, компромиссы и границы — в памяти проекта (`memo`),
  не здесь: recall в начале задачи, запись по ходу.
```

Последний пункт важен: без него ревьюер будет раз за разом сообщать об уже принятом решении.
Он же и причина не вести их в этом файле: список компромиссов растёт, а читается выборочно —
поиск по смыслу задачи дешевле, чем перечитывание раздела, который со временем перестают
открывать.

## Шаг 5. Проверить адаптацию на одном сценарии

1. Возьмите один реальный вариант использования проекта.
2. Прогоните `use-case-designer` — получите сущности, порты, модели I/O.
3. Реализуйте по шаблонам из
   `use-cases-and-entities/references/templates.md`.
4. Прогоните `architecture-reviewer` — убедитесь, что находки осмысленны и не состоят из
   ложных срабатываний, вызванных идиомами языка.
5. Что оказалось ложным — уточните в `AGENTS.md`/`CLAUDE.md` (например: «в этом языке структурная
   типизация, отдельные объявления портов не требуются»).

## Шаг 6. Завести `REVIEW.md`

`REVIEW.md` в корне проекта говорит ревью на баги (фаза 5а `dev`), где изменение рискованно,
где нужно ревью безопасности и что не ревьюить. По его путям `dev` определяет риск: высокий —
задет путь из «Высокий риск», низкий — все пути из «Низкий риск», иначе средний; от риска
зависит уровень ревью на баги. Шаблон с разделами и правилами заполнения —
`references/review-template.md`.

- Заголовки разделов — строго как в шаблоне: по ним `dev` находит разделы.
- В пути рисков — только то, что есть в дереве; «Как здесь выглядит сбой» — 3–8 конкретных
  пунктов про этот продукт, а не общие слова.
- Файл ведёт сессия, работающая в проекте: находка ревью, повторившаяся второй раз и не
  превращаемая в автоматическую проверку, переносится правилом с glob-якорем в «Повторяющиеся
  находки» (не больше 15; снятые — в архив памяти). Обновление набора файл не перезаписывает.
- Сам `REVIEW.md` и `.gitattributes` — в «Высокий риск»; понижать риск — только по согласию.
  В `.gitattributes` — строка `REVIEW.md merge=union`.
- Форму и гигиену проверяет `sh <dev>/scripts/review-lint.sh` (`--help`);
  тест скрипта — `review-lint.test.sh` рядом.

## Типичные особенности по типам языков

Это подсказки для заполнения, а не готовые ответы.

- **Статически типизированные с явными интерфейсами** — набор применим буквально; сильнее
  всего работает принуждение через видимость и единицы сборки; метрика A осмысленна.
- **Динамически типизированные** — порты часто существуют как соглашение о вызове; A занижена,
  опирайтесь на ADP/SDP и на организацию модулей; принуждение — через линтер импортов и тесты.
- **Функциональные** — порт = набор функций или запись функций, передаваемая аргументом;
  `Main` = композиция функций; неизменяемость снимает часть проблем конкурентности, но правило
  зависимостей действует так же.
- **Системные/встраиваемые** — добавляются слои HAL и OSAL (см. `details-and-deferral`);
  критерий успеха — сборка и тесты вне целевого оборудования; условная компиляция заменяется
  подстановкой реализаций.
- **Языки с богатыми фреймворками (веб, ORM, DI)** — главный риск: аннотации и базовые классы
  фреймворка в ядре. Явно запишите в `AGENTS.md`/`CLAUDE.md`, что домен и persistence-модель — разные типы.

## Чего не нужно делать при адаптации

- Не переписывайте скилы под язык — они общие; всё специфичное живёт в `AGENTS.md`/`CLAUDE.md` проекта.
- Не вводите все границы сразу: начните с одной — вокруг I/O — и добавляйте по мере трения.
- Не превращайте метрики I/A/D в цель разработки; это индикаторы для разговора.
- Не оставляйте правило зависимостей на честном слове: без автоматической проверки оно
  исчезнет к первому дедлайну.
