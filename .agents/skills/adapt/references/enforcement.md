# Принуждение правила зависимостей

Правило, которое не проверяется автоматически, исчезает к первому дедлайну. Задача фазы 6 —
получить **одну команду**, которая падает, когда зависимость направлена наружу.

## Порядок предпочтения средств

1. **Система модулей и видимость** — компилятор запрещает нарушение, обратная связь мгновенная и
   бесплатная. Всегда первый выбор: `internal/` в Go, `pub(crate)` в Rust, `internal` в C#/Kotlin,
   `private_constant` в Ruby, экспорт только из `index.ts`.
2. **Границы единиц сборки** — ядро в отдельном модуле/крейте/пакете, который просто не видит
   инфраструктуру: нарушение невозможно выразить, потому что зависимости нет в манифесте.
3. **Архитектурный тест** — часть обычного прогона тестов, ломается там же, где остальное.
4. **Линтер импортов** — отдельная команда и отдельная конфигурация, легко отключается.
5. **Ревью** — последний рубеж, на него нельзя опираться.

Первые три дают обратную связь до мержа. Если стек позволяет 1 или 2 — не вводить 4 «в
дополнение»: лишняя конфигурация, которую никто не поддерживает.

## Минимальный набор правил

Начинать ровно с этого, расширять по мере трения:

1. Ядро (`entities`, `usecases`) не импортирует инфраструктуру и сторонние фреймворки.
   Белый список исключений перечисляется явно.
2. Адаптеры не импортируют друг друга (веб не зовёт хранилище напрямую).
3. Между компонентами нет циклов.
4. Конкретные реализации портов создаются только в `Main`.
5. Аннотации и базовые классы фреймворков в ядре не встречаются.

## Средства по стекам

| Стек | Средство | Форма правила |
|---|---|---|
| Go | `go-arch-lint` (`.go-arch-lint.yml`); `depguard` в `golangci-lint`; каталог `internal/` | компоненты по путям + список разрешённых зависимостей |
| Python | `import-linter` (`.importlinter`) — контракты `layers` и `forbidden` | слои сверху вниз, запрет импорта пакетов инфраструктуры из ядра |
| TypeScript/JS | `dependency-cruiser` (`.dependency-cruiser.js`) или `eslint-plugin-boundaries`; `no-restricted-imports` | `forbidden`-правила `from: core → to: infra`, детект циклов |
| Java | ArchUnit-тест в обычном тестовом прогоне; JPMS `module-info.java` | `noClasses().that().resideInAPackage("..domain..").should().dependOnClassesThat()...` |
| Kotlin | ArchUnit или Konsist; gradle-модули | то же |
| C# | NetArchTest / ArchUnitNET в тестах; ссылки проектов | `Types.InGlobalNamespace().That().ResideInNamespace("Domain").ShouldNot().HaveDependencyOn("Infrastructure")` |
| PHP | `deptrac` (`deptrac.yaml`), `phparkitect`, `phpat` | слои по regex путей + матрица разрешённых переходов |
| Rust | границы крейтов workspace (компилятор), `cargo tree` для проверки графа | ядро — крейт без зависимостей на инфраструктурные крейты |
| Swift | таргеты SPM; тест/скрипт, сканирующий `import` в файлах ядра | ядро-таргет не зависит от UI/сетевых таргетов |
| C/C++ | таргеты CMake с явными `target_link_libraries`, разделение `include/` и `src/`, `include-what-you-use` | ядро-библиотека линкуется без HAL/драйверов |
| Ruby | `packwerk` (`package.yml` на pack) | зависимости packs объявляются явно, `packwerk check` в CI |
| Elixir | библиотека `boundary`, `mix xref graph --fail-above` | `boundary` deps/exports на контекстах |

Конфигурацию и синтаксис конкретного инструмента брать через `context7`, а не по памяти: форматы
меняются между мажорными версиями.

## Универсальная заготовка (когда инструмента нет или он не окупается)

Обычный тест на языке проекта, который читает исходники и проверяет импорты:

```
test "ядро не зависит от инфраструктуры":
    for file in sources("<ядро>/**"):
        for imp in imports(file):
            assert not matches(imp, ["<инфраструктура>/**", "<фреймворки>"]),
                   "{file} импортирует {imp}"
```

Требования к такой заготовке, иначе она бесполезна:

- список запрещённого — **белый список разрешённого наоборот**: перечисляются разрешённые
  зависимости ядра (стандартная библиотека + свои модули), всё прочее запрещено. Чёрный список
  устаревает при добавлении новой библиотеки;
- сообщение об ошибке называет файл и импорт, а не «нарушение архитектуры»;
- тест лежит в обычном тестовом каталоге и идёт в обычном прогоне;
- время работы — доли секунды: чтение файлов, без сборки графа.

## Легаси-база: базовая линия вместо зелёного

На существующем проекте первый прогон почти всегда красный. Правильная реакция:

1. Зафиксировать текущее число нарушений как **базовую линию** и запретить её рост (тест падает
   при N+1). Списка исключений с конкретными файлами достаточно, если он не растёт.
2. Записать это в память проекта как техдолг (`kind: debt`): что нарушено, почему отложено,
   критерий закрытия.
3. **Не ослаблять правила под текущий код** — это превращает проверку в декорацию.
4. Дальнейшее сокращение линии — отдельная работа, планируется агентом `legacy-decoupler`, а не
   делается в рамках адаптации.

## Интеграция

- Команда проверки записывается в `AGENTS.md`/`CLAUDE.md` (раздел «Архитектура», строка «Правило зависимостей
  проверяется: `<команда>`»).
- Если в проекте есть CI — предложить шаг; добавлять только с согласия пользователя.
- Если проверка встроена в существующую агрегирующую команду проекта (`make check`,
  `composer app:check-build`, `npm run verify`) — включать в неё, а не заводить параллельный вход.
