# Главный компонент (composition root)

## Роль

`Main` — конечная деталь, политика самого низкого уровня, точка входа в систему.
От `Main` не зависит ничто, кроме факта работоспособности системы. Его задача:

1. прочитать конфигурацию и окружение;
2. создать конкретные реализации портов (фабрики, стратегии, соединения, клиенты);
3. собрать граф объектов и внедрить зависимости;
4. передать управление высокоуровневым абстракциям;
5. корректно завершить работу (освобождение ресурсов, graceful shutdown).

`Main` — самый грязный компонент системы. Это нормально: нарушения DIP концентрируются здесь,
а не размазываются по коду.

## `Main` как плагин

`Main` — плагин к приложению. Их может быть несколько:

| Вариант | Отличия |
|---|---|
| dev | in-memory хранилище, фейковые интеграции, подробное логирование |
| test / e2e | тестовые дублёры, детерминированные `Clock` и `IdGenerator`, тестовый API |
| prod | реальные БД, очереди, метрики, секреты из хранилища |
| по клиенту / стране / юрисдикции | другие правила комплектации, локали, интеграции |
| по конфигурации оборудования | другой HAL/драйверы (встраиваемые системы) |

Приложение не знает, какой `Main` его запустил. Именно поэтому конфигурационные различия
перестают быть ветвлениями внутри бизнес-логики.

## Шаблон

```
module Main:

    function main(argv):
        config = loadConfig(argv, environment)

        // 1. Инфраструктура (внешний круг)
        db        = openDatabase(config.dsn)
        mailer    = SmtpMailer(config.smtp)
        clock     = SystemClock()
        ids       = UuidGenerator()

        // 2. Адаптеры портов
        orders    = SqlOrders(db)
        customers = SqlCustomers(db)
        notify    = MailNotifier(mailer)

        // 3. Презентаторы (реализации портов вывода)
        presenter = HttpOrderPresenter()

        // 4. Ядро (внутренний круг) — получает только порты
        placeOrder = PlaceOrderInteractor(orders, customers, notify, clock, ids, presenter)
        cancelOrder = CancelOrderInteractor(orders, clock, presenter)

        // 5. Доставка
        api = HttpApi()
        api.route("POST /orders",          HttpPlaceOrderController(placeOrder).handle)
        api.route("DELETE /orders/{id}",   HttpCancelOrderController(cancelOrder).handle)

        // 6. Запуск и завершение
        onShutdown(() => { api.stop(); db.close() })
        api.listen(config.port)
```

Читается сверху вниз как список решений о деталях. Если в `Main` появляется `if` по бизнес-
условию — это правило уехало не туда.

## Правила

1. **Только `Main` знает конкретные типы.** Все `new`/конструкторы адаптеров — здесь.
2. **Ядро не знает о существовании `Main`.** Никаких обратных вызовов «спросить у контейнера».
3. **DI-фреймворк допустим только в `Main`.** Аннотации внедрения не должны попадать на
   сущности и интеракторы. Дальше зависимости распространяются обычной передачей аргументов.
4. **Конфигурация читается в `Main`** и передаётся вниз в виде простых значений/структур —
   ядро не читает переменные окружения и файлы конфигурации.
5. **Строки, ключи, URI, имена таблиц, секреты** — в `Main` или в его конфигурации, не в ядре.
6. Если конкретный тип должен создаваться во время выполнения — ядро использует **абстрактную
   фабрику**, реализация фабрики создаётся в `Main`.
7. `Main` может быть «грязным» по стилю, но обязан быть **тонким**: только сборка, никакой
   бизнес-логики.

## Антипаттерны

| Антипаттерн | Последствие | Исправление |
|---|---|---|
| Service locator / глобальный контейнер, доступный из ядра | зависимости скрыты, тестирование через глобальное состояние | явная передача портов через конструктор/аргументы |
| Аннотации внедрения на сущностях | фреймворк во внутреннем круге, неудаляем | связывание только в `Main` |
| Чтение переменных окружения в интеракторе | скрытый I/O, недетерминированные тесты | конфигурация как аргумент |
| Синглтоны конкретных адаптеров | невозможна подстановка, скрытое состояние между тестами | создание в `Main`, передача явно |
| Бизнес-условия в `Main` (`if country == ...` вокруг правил) | политика уехала в грязный компонент | отдельный `Main` на конфигурацию либо стратегия в ядре |
| `Main` на 2000 строк | нечитаемая сборка | разбить на функции сборки по компонентам: `buildOrders(db)`, `buildBilling(db)` |

## Проверки

- [ ] Ни один модуль ядра не импортирует `Main`.
- [ ] Все конкретные реализации портов создаются только в `Main` (проверяемо архитектурным тестом).
- [ ] Есть отдельный `Main` (или его вариант) для тестов, собирающий систему с дублёрами.
- [ ] Замена БД/транспорта/уведомлений затрагивает `Main` и один адаптер — и ничего больше.
- [ ] В `Main` нет бизнес-правил.
- [ ] Конфигурация валидируется на старте, а не при первом использовании глубоко внутри.
