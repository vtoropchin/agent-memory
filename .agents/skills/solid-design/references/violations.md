# Каталог нарушений SOLID: признак → последствие → исправление

Языко-независимо. Псевдокод условный.

---

## SRP-1. Класс обслуживает нескольких акторов

**Признак**
```
class Employee {
    calculatePay()   // заказывает бухгалтерия
    reportHours()    // заказывает отдел персонала
    save()           // заказывают администраторы БД
    regularHours()   // общий приватный алгоритм
}
```

**Последствие.** Правка `regularHours()` ради бухгалтерии молча меняет отчёты HR. Ошибка
обнаруживается через месяцы и стоит денег. Плюс постоянные конфликты слияния.

**Исправление.** Данные отделяются от функций: общая структура `EmployeeData` + три независимых
модуля (`PayCalculator`, `HourReporter`, `EmployeeSaver`). Общий алгоритм **дублируется
намеренно**, если у акторов разные причины его менять (это ложное дублирование). Для удобства
вызова — фасад `EmployeeFacade`, содержащий только делегирование.

## SRP-2. «Сервисный» класс-свалка

**Признак.** `UserService` с 40 методами: регистрация, рассылка писем, экспорт в CSV, миграция,
кэш, отчёты.

**Последствие.** Любое изменение требует чтения всего файла; тесты тянут все зависимости;
изменения нескольких команд сталкиваются.

**Исправление.** Разбить по акторам и вариантам использования: один вариант использования —
один модуль с одной операцией. Общая инфраструктура — за портами.

---

## OCP-1. Расширение через правку switch/if

**Признак**
```
function format(report, kind) {
    if (kind == "web")   { ... }
    else if (kind == "pdf") { ... }
    else if (kind == "csv") { ... }   // растёт с каждым требованием
}
```

**Последствие.** Каждое новое требование правит проверенный код; риск регрессии; несколько
команд правят одно место.

**Исправление.** Полиморфный порт `ReportPresenter` + по реализации на формат; выбор реализации
— в `Main`/фабрике. Ядро закрывается для изменения и открывается для расширения.

Оговорка: если множество вариантов фиксировано и по природе закрыто (например, три состояния
протокола), `switch` в одном месте лучше пяти классов. Признак «нужен полиморфизм» — рост
множества вариантов от требований.

## OCP-2. Защита направлена не туда

**Признак.** Интерактор (бизнес-правила) импортирует презентатор, контроллер или модель
представления.

**Последствие.** Косметическое изменение экрана вынуждает пересобирать и перетестировать ядро.

**Исправление.** Развернуть стрелку: интерактор объявляет порт вывода, презентатор его
реализует. Правило: **защищаемый компонент не зависит ни от кого; от него зависят все.**

## LSP-1. Подтип ломает контракт

**Признак.** `Square extends Rectangle`, `setWidth` меняет и высоту; потребитель
`r.setW(5); r.setH(2); assert(area == 10)` падает.

**Последствие.** Потребитель обязан знать конкретный тип → проверки типа расползаются.

**Исправление.** Нет отношения «является» — нет наследования. Общий контракт — `Shape.area()`;
изменяемость размеров — отдельные типы или неизменяемые значения.

---

## LSP-2. Несовместимые реализации внешнего контракта

**Признак**
```
if (driver.dispatchUri().startsWith("acme.com")) { ...особый формат... }
```

**Последствие.** Слово «acme» в бизнес-логике; при слиянии компаний добавляется ещё одно
условие; дыра в безопасности; ветвление размножается по всей системе.

**Исправление.** Вынести различия в данные, а не в код: таблица соответствия
`URI → формат команды` в конфигурации + один адаптер, строящий команду по шаблону. Бизнес-логика
не знает о вендорах.

## ISP-1. Толстый интерфейс

**Признак.** `OPS { op1(); op2(); op3() }`, где `User1` использует только `op1`.

**Последствие.** Изменение `op2` вынуждает пересобирать/передеплоить `User1`; в тестах
приходится реализовывать заглушки для неиспользуемых операций.

**Исправление.** Разделить на `U1Ops`, `U2Ops`, `U3Ops` по потребителям; реализация может
по-прежнему быть одна.

---

## ISP-2. Транзитивная зависимость от ненужного

**Признак.** Система S зависит от фреймворка F, который жёстко тянет БД D, не используемую S.

**Последствие.** Ошибка в неиспользуемой части D ломает S; релизы D вызывают передеплой S.

**Исправление.** Обёртка/адаптер вокруг F в отдельном компоненте; выбор более узкой библиотеки;
явное разделение зависимостей сборки на ядро и инфраструктуру.

---

## DIP-1. Ядро импортирует конкретику

**Признак.** `import orm.Session` внутри варианта использования; аннотации таблицы на сущности;
`@Autowired`/атрибуты контейнера в бизнес-объектах.

**Последствие.** Ядро нельзя протестировать без инфраструктуры; смена ORM/фреймворка = переписать
домен; фреймворк проник во внутренний круг и не удаляется.

**Исправление.** Порт в ядре (`Orders.findByCustomer(...)`), адаптер снаружи; отдельные
persistence-модели; связывание в `Main`. Аннотации фреймворка — только на адаптерах.

---

## DIP-2. Создание конкретных объектов внутри ядра

**Признак.** `new SmtpMailer()` внутри варианта использования.

**Последствие.** Скрытая зависимость, невозможность подстановки, тест шлёт настоящую почту.

**Исправление.** Порт `NotifyCustomer` + абстрактная фабрика при необходимости создания в
рантайме; конкретика — в `Main`. Нарушения DIP допускаются, но концентрируются в одном грязном
компоненте.

---

## DIP-3. Инверсия ради инверсии

**Признак.** Интерфейс `IStringHelper`, обёртка над стандартной коллекцией, «порт» с единственной
реализацией и без границы.

**Последствие.** Зона бесполезности: абстракции без потребителей, лишний код, ложное ощущение
гибкости.

**Исправление.** Инвертировать только **изменчивое конкретное**. Стабильную платформу
(стандартная библиотека, примитивы языка) использовать напрямую.

---

## Быстрый опросник для ревью

1. Кто закажет изменение каждого публичного метода этого модуля? (SRP)
2. Что произойдёт со списком файлов при следующем требовании того же класса? (OCP)
3. Есть ли в коде проверка конкретного типа/вендора/флага реализации? (LSP)
4. Использует ли каждый потребитель интерфейса все его операции? (ISP)
5. Есть ли в ядре импорт изменчивого конкретного модуля или `new` конкретной инфраструктуры? (DIP)
