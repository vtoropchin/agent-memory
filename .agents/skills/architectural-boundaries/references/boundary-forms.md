# Формы границ: реализация, цена, деградация

## 1. Полная граница

**Состав**
- порт ввода (интерфейс, через который внешний код вызывает внутренний);
- порт вывода (интерфейс, который внутренний код вызывает, а внешний реализует);
- структуры ввода/вывода (DTO), принадлежащие внутренней стороне;
- две независимые единицы сборки/развёртывания;
- связывание в `Main`.

**Схема**
```
[внешний компонент]                     [внутренний компонент]
Controller ──вызывает──▶ InputPort  ◀──реализует── Interactor
Presenter  ──реализует─▶ OutputPort ◀──вызывает─── Interactor
StorageAdapter ─реализует▶ StoragePort ◀─вызывает─ Interactor
```
Все стрелки зависимости исходного кода — внутрь.

**Когда**: ось изменения реальна и подтверждена; стороны развиваются разными командами или с
разной скоростью; нужна независимость развёртывания или замены технологии.

**Цена**: две единицы сборки, версионирование, парные интерфейсы, преобразование данных.

---

## 2. «Пропущен последний шаг»

Сделано всё, что нужно для полной границы (интерфейсы, DTO, дисциплина зависимостей), но
компонент остаётся один — без разделения на единицы сборки.

**Когда**: цена сопровождения нескольких артефактов пока не оправдана; хочется сохранить
однофайловую поставку («скачал и запустил»); граница вероятна, но не подтверждена.

**Деградация**: со временем, если разделение так и не понадобилось, грань размывается —
появляются зависимости в обратную сторону, и разделить становится очень сложно (так произошло
с веб-компонентом FitNesse).

**Профилактика**: автоматическая проверка направления зависимостей внутри компонента
(по каталогам/пакетам), даже если артефакт один.

---

## 3. Одномерная граница («Стратегия»)

```
Client ──▶ ServiceBoundary (интерфейс)
                 ▲
                 └── ServiceImpl
```

Инверсия есть, парных интерфейсов нет: обратный поток (из реализации к клиенту) ничем не
регламентирован.

**Когда**: нужно зарезервировать место под будущую границу дёшево; один поток управления;
одна вероятная точка подстановки.

**Деградация**: `ServiceImpl` начинает знать о клиенте (обратная зависимость), и граница
исчезает. Удерживается только дисциплиной и проверками.

---

## 4. Фасад

```
Client ──▶ Facade ──▶ ServiceA, ServiceB, ServiceC
```

Инверсии нет. Клиент имеет транзитивную зависимость от всех служб; в статически типизированных
языках изменение служб вызывает пересборку клиента.

**Когда**: нужно просто упорядочить доступ и обозначить намерение; цена любой другой формы
не оправдана.

**Деградация**: обход фасада напрямую — тривиален, если типы служб публичны. Сужайте видимость.

---

## 5. Отсутствие границы (осознанно)

Правильное решение для маленьких систем, прототипов и стабильных участков.
Фиксируйте решение и признаки, при которых его следует пересмотреть:
«если появится второй канал доставки / второе хранилище / вторая команда — вводим границу».

## Цена пересечения границы во время выполнения

| Механизм | Порядок задержки | Чем платим | Ограничения на трафик |
|---|---|---|---|
| Вызов функции (монолит) | наносекунды | ничем | практически нет |
| Динамическая библиотека / сборка | наносекунды + загрузка | загрузка при старте | практически нет |
| Локальный процесс (IPC, сокет) | микросекунды–миллисекунды | маршалинг, переключение контекста | ограничивать количество вызовов |
| Служба по сети | миллисекунды–секунды | сериализация, сеть, отказы, ретраи | минимизировать; проектировать под задержки и частичные отказы |

Ошибка, стоящая дороже всего: выбрать самый дорогой механизм заранее «ради масштабирования»,
которое не наступит. Механизм всегда можно усилить позже, если границы существуют в исходном
коде.

## Матрица выбора

| Ситуация | Форма границы | Механизм |
|---|---|---|
| Хранилище может смениться, ядро должно тестироваться без него | полная | вызов функции |
| Второй канал доставки (веб + CLI) вероятен | полная (порт ввода/вывода) | вызов функции |
| Возможна замена внешнего провайдера интеграции | полная + антикоррупционный адаптер | сеть внутри адаптера |
| Функция может стать отдельным сервисом «когда-нибудь» | «пропущен последний шаг» | вызов функции |
| Один алгоритм, вероятны альтернативы | стратегия | вызов функции |
| Нужно скрыть беспорядок легаси на время | фасад | вызов функции |
| Разные команды, разные релизные циклы, разная нагрузка | полная | компонент развёртывания или служба |
| Требуется независимое масштабирование по нагрузке | полная | служба |

## Проверка качества существующей границы

1. Кому принадлежит интерфейс — потребителю (правильно) или реализации (неправильно)?
2. Что пересекает границу — простые структуры (правильно) или типы фреймворка/записи БД
   (неправильно)?
3. Есть ли зависимости в обратную сторону (имена, конфигурация, «временный» импорт)?
4. Можно ли собрать и протестировать внутреннюю сторону без внешней?
5. Соответствует ли частота пересечений выбранному механизму (сотни сетевых вызовов на
   операцию — признак неверной формы)?
6. Проверяется ли направление зависимостей автоматически?
