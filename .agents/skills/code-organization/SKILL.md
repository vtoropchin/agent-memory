# Организация кода и принуждение к архитектуре

Самые лучшие проектные намерения уничтожаются деталями реализации. Этот скил — про то, как
дизайн отображается в структуру исходников и как заставить **компилятор и сборку** охранять
архитектуру вместо ревью и договорённостей.

Точные формулировки — `references/book-digest.md` скила `clean-architecture` (гл. 21, 34), если он установлен рядом.

## Ключевой факт

**Если все типы объявлены публичными, все стили организации кода становятся синтаксически
неотличимыми.** Пакеты превращаются в папки, инкапсуляция теряется, «архитектура» существует
только в презентации. Стрелки между типами перестают зависеть от выбранного стиля.

Отсюда первое правило: **публичность — осознанное решение, а не рефлекс.**

## Четыре стиля организации

### 1. Упаковка по уровням (`web/`, `services/`, `data/`)
Горизонтальные пакеты по техническому признаку.
- Плюс: быстрый старт, знакомо всем.
- Минус: не кричит о предметной области (две системы из разных доменов выглядят одинаково);
  плохо масштабируется; изменение одной функции размазано по всем пакетам;
  «нестрогая многоуровневость» — контроллер напрямую зовёт хранилище в обход бизнес-логики.

### 2. Упаковка по особенностям (`orders/`, `billing/`)
Вертикальные срезы по предметным понятиям.
- Плюс: кричит о домене; изменение локально; простой рефакторинг из стиля 1.
- Минус: без внутренней дисциплины уровней внутри среза снова получается каша.

### 3. Порты и адаптеры (`domain/` внутри, `infrastructure/` снаружи)
- Плюс: явное разделение «внутри/снаружи», зависимости направлены внутрь; ядро тестируемо.
- Минус: **антишаблон «Périphérique»** (Браун назвал его по парижской окружной дороге:
  инфраструктуру можно объехать по кольцу, не заезжая в центр) — если вся инфраструктура лежит
  в одном дереве исходников, веб-код может напрямую вызвать код БД, минуя домен. Порты
  именуются на языке домена (`Orders`, а не `OrdersRepository`).

### 4. Упаковка по компонентам (`orders/` как компонент с одной точкой входа)
Вся ответственность за область (бизнес-логика + доступ к данным) внутри одного компонента с
чистым публичным интерфейсом; UI отделён.
- Плюс: минимум публичных типов, компилятор охраняет границу, шаг к службам без их стоимости.
- Минус: требует дисциплины видимости и языковой поддержки инкапсуляции.

**Рекомендация по умолчанию:** организация по предметным областям/компонентам (3 или 4) с
явными портами и минимальной видимостью. Внутри компонента — деление на сущности, варианты
использования, адаптеры.

## Скелет проекта (нейтральный)

```
<домен-1>/                     ← компонент: кричит о предметной области
    <точка входа компонента>   ← единственный публичный интерфейс
    entities/                  ← критические правила и данные   (скрыто)
    usecases/                  ← интеракторы, порты, модели I/O  (порты видны внутри компонента)
    adapters/                  ← реализации портов этого компонента (скрыто)
<домен-2>/
shared-kernel/                 ← только действительно общее и стабильное
delivery/                      ← http, cli, ui — потребители компонентов
main/                          ← composition root, по одному на конфигурацию
tests/
```

Проверка скелета: по каталогам верхнего уровня видно, **что система делает**, и не видно,
**чем она это делает**.

## Правила видимости

1. Публичен только тип, у которого есть потребитель **за пределами** его компонента.
2. У компонента — одна точка входа; всё остальное скрыто.
3. Реализации портов не публичны никогда (их создаёт только `Main`).
4. Модели ввода/вывода публичны ровно настолько, насколько нужно вызывающему адаптеру.
5. Сущности не публикуются наружу компонента как контракт.
6. Тесты не должны требовать расширения видимости: если тест «не видит» нужного — тестируется
   не тот уровень.

## Принуждение: порядок предпочтения

1. **Язык и система модулей** — модификаторы доступа, экспорт модуля, `internal`/`pub(crate)`,
   явные списки экспорта. Самая быстрая обратная связь: не собирается.
2. **Границы сборки** — отдельные модули/проекты/крейты для ядра и инфраструктуры; ядро
   физически не может зависеть от инфраструктуры, потому что не объявляет её в зависимостях.
3. **Архитектурный тест** — тест, падающий при запрещённом импорте (правило вида «`domain/**`
   не импортирует `infrastructure/**`, `http/**`, сторонние фреймворки»). Пишется за час на
   любом языке через разбор импортов.
4. **Линтер импортов / конфигурация зависимостей** — грубее, но лучше, чем ничего.
5. **Ревью и дисциплина** — последняя линия. Работает ровно до дедлайна.

Минимальный набор правил для автоматизации:
- ядро не импортирует инфраструктуру и фреймворки (белый список исключений);
- адаптеры не импортируют друг друга;
- никаких циклов между компонентами;
- конкретные реализации инстанцируются только в `main/`.

## Именование

- Каталоги и модули — предметные понятия и варианты использования, не технические роли.
- Порты — на языке предметной области (`Orders`, `NotifyCustomer`, `Clock`).
- Адаптеры — с указанием технологии (`SqlOrders`, `HttpOrderController`, `SmtpNotifier`):
  технология видна там, где она уместна, — снаружи.
- Избегать `utils`, `common`, `core`, `helpers` как свалок: они мгновенно попадают в зону боли
  (устойчивые и конкретные) и связывают всё со всем.

## Процедура: навести порядок в существующем дереве

1. Составить список вариантов использования — они станут ориентиром для каталогов.
2. Найти всё, что относится к одной предметной области, и собрать в один компонент.
3. Выделить внутри компонента ядро (сущности + варианты использования) и адаптеры.
4. Сузить видимость: всё, что не имеет внешних потребителей, — скрыть. Начать с реализаций.
5. Ввести единственную точку входа в компонент.
6. Перенести создание конкретных объектов в `main/`.
7. Добавить архитектурный тест на направления импортов — до дальнейших правок.
8. Разбираться с оставшимися нарушениями по одному, каждый раз ужесточая правило теста.

## Точки адаптации к языку

- как выражается компонент (пакет, модуль, сборка, крейт, workspace-проект, каталог с
  манифестом);
- какие модификаторы видимости доступны и есть ли «видимость для подпакетов»;
- как объявляется публичный API модуля (списки экспорта, индексные файлы, интерфейсные файлы);
- чем проверяются импорты автоматически;
- как организовать несколько единиц сборки без чрезмерного усложнения.

## Компромиссы

Разделение на множество единиц сборки даёт лучшее принуждение, но повышает сложность сборки и
время цикла. Прагматичный минимум: **два дерева** — ядро (домен + варианты использования) и
инфраструктура/доставка. Этого достаточно, чтобы компилятор запретил самое опасное направление,
а остальное покрывается видимостью внутри компонентов и архитектурным тестом.
