# Архитектурные решения — в памяти проекта

Решения цикла `dev` **не ведутся в файлах проекта**: они хранятся в долговременной памяти
(MCP-сервер `memo`). Протокол вызовов (`memory_recall`/`memory_save`/`memory_update`/
`memory_forget`, scope, режим хуков) описан один раз — в скиле `memo`; здесь
только то, **что** записывать и **как формулировать**.

Смысл прежний: решение, принятое осознанно и записанное, перестаёт быть долгом и перестаёт
обсуждаться заново на каждом ревью. Память лучше файла по стоимости будущих обращений: она
ищется по смыслу задачи, а не по тому, вспомнил ли кто-то открыть нужный документ.

Одна запись — **одно решение** (1–3 предложения). Три вида записей.

## Вид 1. Отложенное решение

Технология или структура, выбор которой сознательно не сделан.

```
ОТЛОЖЕНО: выбор СУБД для хранилища заказов. Сейчас — файловая реализация порта `Orders`;
отложить можно, потому что ядро работает через порт и ни один вариант использования не требует
запросов по содержимому. Пересмотр: объём > ~1 млн заказов либо отчёты по произвольным срезам.
Стоимость поздней смены: один адаптер (~200 строк) + миграция; ядро не затрагивается.
```

## Вид 2. Сознательный компромисс

Нарушение дисциплины, принятое с открытыми глазами. Сохраняется с `kind: debt` — долг сам не
затухает и требует явного закрытия.

```
КОМПРОМИСС: ORM-модель используется как сущность в модуле биллинга — фреймворк во внутреннем
круге, правило зависимостей нарушено. Принято потому, что модуль в заморозке, а вынос стоит
~3 дней. Цена: любое изменение правил расчёта потребует работы с ORM, тесты требуют БД (12 с).
Пересмотр: первое же требование, меняющее правила расчёта, либо смена версии ORM.
```

Запись компромисса не делает его нормой. Отсутствие записи делает его невидимым — и через
полгода он воспринимается как замысел.

## Вид 3. Проведённая (или сознательно не проведённая) граница

```
ГРАНИЦА: уведомления — полная граница, порт `NotifyCustomer` в ядре, адаптеры снаружи, вызов
функции в монолите. Ось изменения: канал доставки (почта → мессенджер → push) меняется
независимо от правил заказа. Удешевляет: добавление канала = новый адаптер + строка в `Main`.
```

```
ГРАНИЦЫ НЕТ: отчётность — код остаётся в компоненте `orders`. Отчёты меняются часто, но одной
командой и вместе с правилами заказа. Пересмотр: вторая команда или второй потребитель отчётов.
```

## Правила ведения

1. Пишется **в момент принятия**, а не постфактум: цикл `dev` делает это на фазах 2, 5 и 6.
2. Каждая запись обязана содержать **условие пересмотра** — иначе это не решение, а забывание.
3. Формулировки — про будущие изменения и их стоимость, а не про «правильность».
4. Записи **не удаляются**. Решение пересмотрено или уточнено → `memory_update` той же записи
   (дописать, чем оно закрыто и когда), а не `memory_forget`. Исключение одно: компромисс с
   `kind: debt`, который действительно устранён в коде, закрывается по протоколу `memo` —
   `memory_forget(id, replaced_by=<id записи о новом решении>)`.
5. Ревьюер (`architecture-reviewer`) делает recall перед выводами: то, что записано как
   компромисс с условием пересмотра, не сообщается как находка повторно.

## Как формулировать, чтобы запись нашлась через recall

Recall ищет по смыслу задачи, а не по точному слову, — запись должна содержать те же слова,
которыми через полгода будет сформулирована задача, её задевающая.

- **Начинать с маркера вида** (`ОТЛОЖЕНО:`, `КОМПРОМИСС:`, `ГРАНИЦА:`, `ГРАНИЦЫ НЕТ:`) и
  **имени затрагиваемой области** — компонента, порта, варианта использования так, как они
  называются в коде. «Хранилище заказов, порт `Orders`» найдётся, «вопрос персистентности» — нет.
- Называть **технологию и альтернативу** явно (`MySQL`, `ORM`, `push`): по ним и придёт запрос.
- Условие пересмотра формулировать как **наблюдаемое событие** («появится второй потребитель»,
  «сменится версия ORM»), а не как «если станет плохо».
- Теги — вид записи и область: `решение`, `граница`, `компромисс`, `отложено` + имя компонента.
  Они позволяют собрать все решения по модулю одним recall с фильтром `tags`.
- Для T1-задач достаточно одной фразы того же формата: `ЛОЖНОЕ ДУБЛИРОВАНИЕ: валидация формата
  телефона в веб- и CLI-адаптере не объединяется. Пересмотр: появится третий канал.`
