# Техническое задание агенту-исполнителю: шаблон и гейт

Справочник к `SKILL.md`, раздел «Режим исполнения». Применяется, когда код пишет агент
`implementer`, а не основная модель. Одно ТЗ — один шаг фазы 3 (сущности, варианты
использования, адаптер одной технологии, `Main`, доставка).

Смысл ТЗ: агент стартует с чистым контекстом и знает о задаче ровно то, что здесь написано.
Всё, что основная модель поняла на фазах 1–2, но не записала, для агента не существует.
Ошибка понимания должна быть поймана на тексте ТЗ, а не в коде.

## Гейт ТЗ: перед отправкой агенту

ТЗ готово, если на каждый вопрос ответ «да». Ответ «нет» — дописать, а не «агент разберётся».

| Вопрос | Ответ «нет» означает |
|---|---|
| Каждый файл назван путём, с действием (новый / изменить) и содержимым на уровне имён типов и функций? | агент будет угадывать структуру и разложит код по-своему |
| Каждый тест назван условием и ожиданием, а не «покрыть тестами»? | тесты будут написаны под получившийся код, а не наоборот |
| Порты названы вместе с владельцем и тестовой подменой? | появится новый порт-дубль или прямое обращение к инфраструктуре |
| Команды проверки выписаны дословно? | агент запустит часть или другое |
| Решения из памяти и договорённости сессии, которые касаются шага, перенесены текстом? | агент их не видит и не выполнит; файлы правил он видит сам |
| В ТЗ нет слов «по аналогии», «как обычно», «см. существующий код», «и т. п.»? | это места, где основная модель сама не решила |
| Шаг выполним без решений о границах и без выбора технологии? | это фаза 2, а не фаза 3; решить до ТЗ |
| Объём шага — один слой, один пакет или одна технология? | шаг слишком крупный, разрезать |

## Приёмка результата

Отчёт агента — заявление, не доказательство. Приёмка делается основной моделью по факту:

1. `git diff --stat` и чтение диффа целиком: совпадает ли список файлов с таблицей ТЗ;
   каждое отклонение либо объяснено в отчёте, либо это находка.
2. Тесты из списка ТЗ существуют и проверяют названное условие, а не факт вызова.
3. Проверки из ТЗ запущены **основной моделью повторно**, результат совпал с отчётом. В
   отчёте агента у каждой проверки есть хвост вывода; проверка без вывода считается
   незапущенной.
4. Сравнение с ТЗ по правилам предметной области: каждое правило видно в коде или тесте.
5. **Ревью на баги по риску** — фаза 5а `SKILL.md` на diff этого шага: риск по путям шага,
   ревью на баги уровня из таблицы фазы 0 (по уровню задачи и риску), целью — файлы шага;
   ревью безопасности — один раз по всему diff на фазе 5а, не на каждом шаге. Находки разбираются на Important / Nit / Pre-existing по
   правилам `REVIEW.md`; агенту уходят только Important, Nit и Pre-existing основная модель
   оставляет себе (отчёт, задачи в памяти).
6. Красное, пропущенное, отклонения без объяснения и Important ревью → возврат тому же агенту
   **одним** дополнением к ТЗ (продолжение, а не новый агент: у него контекст правок).

Правила сходимости — общие для находок приёмки и ревью:

- круг правок — одно продолжение агента со всеми находками сразу; не более двух кругов на
  шаг: третий означает, что плохо ТЗ, а не агент, — вернуться к фазе 2 или перекалибровать
  уровень (если назначение `orchestrate` или `AGENTS.md`/`CLAUDE.md` проекта задаёт другой канал для вопросов — вопрос туда);
- в находке назван **класс** ошибки, и агент исправляет его во всех вхождениях в изменении,
  а не одну строку;
- повторная приёмка и повторное ревью — только по diff правок; выданное в прошлом круге не
  повторяется.

Только после приёмки шаг считается сделанным и пишется ТЗ следующего.
