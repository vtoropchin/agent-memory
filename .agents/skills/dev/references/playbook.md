# Плейбук цикла разработки: гейты, ветвления, типовые ситуации

Справочник к `SKILL.md`. Здесь — то, что нужно на исполнении, а не при обзоре.

---

## Карта цикла

```
[0] Калибровка ──▶ [1] Понять ──▶ [2] Спроектировать ──▶ [3] Реализовать ──▶ [4] Проверить
 уровень + риск                            ▲                    ▲                 │
      ▲                                    │                    │                 ▼
      │                                    │                    ├─ Important ── [5а] Ревью на баги
      │                                    └─ третий круг правок ┘                │
      │                                                         │                 ▼
      └──── перекалибровка ◀── изменилось требование            └─ нет границы ─ [5б] Ревью архитектуры
                                                                                  │
                                                                                  ▼
                                                                            [6] Закрыть
```

Возврат назад — нормальная часть цикла, а не провал. Ненормально — двигаться вперёд с
непройденным гейтом.

---

## Гейты: формулировки для самопроверки

| Гейт | Вопрос | Ответ «нет» означает |
|---|---|---|
| 1 | Могу ли я записать сценарий как «ввод → обработка → вывод» без UI, HTTP и таблиц? | требование не понято, идти к пользователю или к коду |
| 2 | Каждая ли новая абстракция удешевляет **названное** будущее изменение? | преждевременное усложнение, вычеркнуть |
| 3 | Проходит ли сценарий тестами без БД, сети и UI? Сделан ли рефакторинг? | граница не проведена / долг уже создан |
| 4 | Все ли тесты и архитектурные проверки зелёные — по факту запуска? Есть ли у каждой команда и хвост вывода? | нельзя отчитываться о готовности |
| 5а | Исправлены ли все Important, а Nit и Pre-existing перечислены (Pre-existing — задачами в памяти)? | правка тем же циклом; после второго круга — фаза 2 |
| 5б | Есть ли блокирующие нарушения? Записаны ли сознательные компромиссы? | правка немедленно / запись в память |
| 6 | Знает ли пользователь, что сделано, что проверено и что не сделано? Есть ли строки «Риск / Ревью / Откат»? | отчёт неполон |

## Кого звать и когда

| Ситуация | Инструмент |
|---|---|
| Что уже решено по этой области: границы, отложенные технологии, компромиссы | recall из памяти (скил `memo`) |
| Большая или незнакомая база: как устроен проект, что с чем связано, где живёт политика | скил `graphify` — устойчивый граф знаний; при наличии `graphify-out/` вопрос о структуре сначала адресуется графу |
| Разовый точечный поиск: где лежит конкретное имя, какие файлы задеты | поисковый субагент клиента или обычный поиск (граф строить дороже, чем оно того стоит) |
| В работе появилась конкретная библиотека, фреймворк, SDK, API, CLI | документация: `context7`, если подключён, иначе официальная — только на уровне адаптеров и `Main`, не при проектировании ядра |
| Новая система, подсистема, компонент, смена режима развёртывания | `boundary-architect` |
| Требование → варианты использования, сущности, порты | `use-case-designer` |
| Правила погребены в контроллерах/ORM/SQL; предлагается переписать с нуля | `legacy-decoupler` |
| Тесты медленные, хрупкие, требуют окружения; непонятно, что подменять | `test-architect` |
| Изменения сделаны, нужно ревью на баги | ревью на баги в свежем контексте с уровнем из таблицы фазы 0 — встроенной командой клиента или субагентом (`runtime.md`) |
| Diff задевает пути раздела «Безопасность» `REVIEW.md` | ревью безопасности — встроенной командой клиента или субагентом (`runtime.md`) |
| Правка `REVIEW.md` или конец задачи в проекте, где он есть | `sh <dev>/scripts/review-lint.sh` — форма, якоря, пути рисков, потолок, сроки |
| Изменения сделаны и прошли ревью на баги, нужно архитектурное ревью | `architecture-reviewer` |
| Медленная сборка, спутанные модули, подозрение на циклы | `dependency-auditor` |
| Режим делегирования (`SKILL.md`): код шага фазы 3 по письменному ТЗ | роль `implementer` на сильной модели для кода; ТЗ и приёмка — `brief.md` |
| Субагентов в клиенте нет | файл роли `agents/<роль>.md` и соответствующий скил напрямую, в основном контексте |

Правило вызова: агент получает **контекст задачи и ссылку на файлы**, а не пересказ; его вывод
— вход следующей фазы, а не украшение отчёта. Исполнитель — исключение: он получает не ссылку,
а полное ТЗ, потому что стартует с чистым контекстом: файлы правил у него есть, разговора
и решений фаз 1–2 нет.

## Порядок реализации: почему изнутри наружу

| Шаг | Что появляется | Что становится возможным | Чего ещё нет |
|---|---|---|---|
| 1. Сущности | критические правила и данные | тесты правил за микросекунды | приложения |
| 2. Варианты использования + порты | сценарии на заглушках/in-memory | вся функция работает и тестируется | БД, сети, UI |
| 3. Адаптеры | SQL, HTTP, сериализация, презентаторы | реальные данные и транспорт | сборки |
| 4. `Main` | связывание, конфигурация | запуск | — |
| 5. Доставка | маршруты, команды, экраны | пользователь видит результат | — |

Обратный порядок (от контроллера к домену) почти всегда даёт зависимости ядра от
инфраструктуры: то, что написано первым, диктует форму тому, что написано вторым.

## Типовые ситуации и решения

**Требование сформулировано в терминах UI** («добавь кнопку, чтобы менеджер видел просрочки»).
Переформулируйте в сценарий: актор — менеджер; ввод — период; обработка — выбрать заказы с
просрочкой на дату; вывод — список с суммами. Кнопка — деталь доставки, последний шаг.

**Требование сформулировано в терминах БД** («добавь таблицу и CRUD»). Спросите, какой
сценарий это обслуживает (если назначение `orchestrate` или `AGENTS.md`/`CLAUDE.md` проекта задаёт другой канал для вопросов — например,
режим исполнителя оркестратора, — спрашивайте там). CRUD без сценария — признак того, что
политика ещё не найдена.

**Нужна технология, которой в проекте нет.** Не тащите её в ядро: порт в терминах приложения →
адаптер → выбор технологии внутри адаптера (её API — из `context7`, а не по памяти) → запись
решения в память с условием пересмотра.
Проверьте, можно ли отложить: заглушка/файл/память часто закрывают месяцы разработки.

**Функция похожа на существующую.** Прежде чем обобщать — проверьте, истинное ли это
дублирование (изменения обязаны идти вместе) или ложное (разойдутся). Ложное не объединять:
разделять потом дороже.

**По ходу выясняется, что нет границы, куда положить код.** Возврат на фазу 2. «Пристроить
временно» — механизм, которым создаётся легаси.

**Тест невозможно написать.** Это диагноз кода, а не тестов: не хватает шва. `test-architect`
или самостоятельно — вынести обращение к внешнему миру в порт.

**Пользователь просит «просто быстро».** Уровень T0/T1 — законная скорость. Но ядро и границы
не приносятся в жертву: быстро = меньше объём, а не хуже структура. Если быстро требует
нарушения — назовите цену и сохраните компромисс в память.

**Агент-исполнитель вернул вопросы вместо кода.** Это правильное поведение, а не сбой: ТЗ
читалось двумя способами. Ответить дополнением к ТЗ и продолжить того же агента; если вопросы
о границах или технологии — это фаза 2, вернуться туда.

**Отчёт агента зелёный, а повторный прогон красный.** Верить прогону. Вернуть агенту красный
вывод дословно; если расхождение повторяется — агент менял тесты или запускал не то, и это
блокер для приёмки.

**Ревью на баги нашло ошибку в коде, который задача не меняла.** Это Pre-existing: не чинить
в этой задаче, завести задачу в памяти проекта и назвать её id в отчёте. Починка «заодно»
расширяет объём и смешивает в одном diff два риска.

**Второй круг правок, а ревью снова находит Important.** Не начинать третий: исправляли
строки, а не класс ошибки, или не понята сама задача. Вернуться на фазу 2 (или вопросом в
канал, который задаёт назначение `orchestrate` или `AGENTS.md`/`CLAUDE.md` проекта).

**Ревью находит то же, что в прошлой задаче.** Это повторяющаяся находка. На фазе 6 сначала
вопрос: можно ли поймать её тестом, архитектурным тестом или линтером? Можно — делается
проверка. Нельзя — правило с glob-якорем в «Повторяющиеся находки» `REVIEW.md` (потолок 15:
занят — слить похожие). Молча исправлять ещё раз — значит встретить её в третий.

**Правило `REVIEW.md` срабатывает не по делу.** Каждая отклонённая находка со ссылкой на
правило — эпизод памяти `ложная-находка`. Второй такой — правило переписать или снять в архив
памяти (`review-архив`). Редкие срабатывания поводом для снятия не являются.

**Хочется убрать путь из «Высокий риск» или «Безопасность».** Это понижение риска: только с
согласия по каналу вопросов проекта, до правки. Мёртвый путь (каталог переименован) правится
на актуальный, а не удаляется.

**Сроки горят, дисциплина «мешает».** Аргумент из книги, не из вкуса: грязный код замедляет
уже в пределах текущей задачи, а не когда-то потом. Единственная законная экономия —
сокращение объёма работы.

## Definition of Done по уровням

| | T0 | T1 | T2 | T3 |
|---|---|---|---|---|
| Тесты на изменение | если есть, куда | да | да, уровня вариантов использования | да, + адаптеры |
| Полный прогон тестов | да | да | да | да |
| Доказательства проверок в отчёте | да | да | да | да |
| Ревью на баги | только при высоком риске: `high` | `low`; высокий риск — `high` | `medium`; высокий риск — `high` | `high` |
| Ревью безопасности | если задеты пути «Безопасность» | так же | так же | так же |
| Сверка diff с «Повторяющимися находками» | вместе с ревью на баги | да | да | да |
| `review-lint`, если в проекте есть `REVIEW.md` | да | да | да | да |
| Архитектурная проверка | — | самопроверка (раздел A) | `architecture-reviewer` | + `dependency-auditor` |
| Запись решений в память | — | если есть компромисс | да | да |
| Обновление `AGENTS.md`/`CLAUDE.md` | — | если изменились стабильные правила | если изменилась структура | да |
| Ручная проверка в приложении | если пользовательская | да | да | да |
| Режим делегирования | сама | `implementer` по ТЗ на шаг | `implementer` по ТЗ на шаг | `implementer` по ТЗ на шаг |

## Форма финального отчёта

```
Сделано: <что именно, файлы со ссылками>
Проверено: <команда дословно → хвост вывода, время; архитектурная проверка; для UI — снимок штатным способом>
Риск: низкий|средний|высокий (совпавшие пути REVIEW.md)
Ревью: на баги <уровень, чем> — N Important исправлено, M Nit, K Pre-existing → задачи <id>; безопасность — <итог или не требовалось>
Откат: <как откатить>
Отложено/не сделано: <что и почему; что для этого нужно>
Решения: <отложенные технологии, сознательные компромиссы — что сохранено в память проекта; правила, перенесённые в REVIEW.md>
Замечено: <новые оси изменения, кандидаты в границы; предложение, а не действие>
```

Nit перечисляются под строкой «Ревью» (не больше трёх). Нет `REVIEW.md` — после строки «Риск»
отдельная строка «REVIEW.md нет — риск принят средним».

Запреты в отчёте: «должно работать», «скорее всего проходит», «проверено» без вывода, молчание
о пропущенном шаге или пропущенном ревью, объявление готовности при красных тестах.
