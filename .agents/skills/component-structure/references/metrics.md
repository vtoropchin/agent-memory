# Метрики компонентов и процедура аудита графа зависимостей

## Определения

| Метрика | Формула | Смысл | Ориентир |
|---|---|---|---|
| Fan-in | число классов **вне** компонента, зависящих от классов **внутри** него | ответственность | — |
| Fan-out | число классов **внутри** компонента, зависящих от классов **снаружи** | зависимость | — |
| I (нестабильность) | `Fan-out / (Fan-in + Fan-out)` | лёгкость изменения | убывает по стрелке |
| A (абстрактность) | `Na / Nc` | доля абстракций | растёт с падением I |
| D (расстояние) | `abs(A + I − 1)` | удалённость от главной последовательности | ≈ 0 |

`I = 0` — максимально устойчив (ответствен и независим). `I = 1` — максимально неустойчив
(безответствен и зависим).

Обе метрики связности считаются **в классах/модулях/файлах**, а не в компонентах: Fan-out — не
«сколько компонентов я использую», а «сколько моих классов ссылается наружу». В C++ это
`#include`, в Java — `import` и полные квалифицированные имена.

## Зоны на графике A/I

```
A=1 |  (0,1) идеал:                        зона бесполезности (1,1)
    |  абстрактный и устойчивый            мёртвые абстракции
    |        \
    |          \  главная последовательность
    |            \
    |              \
A=0 |  зона боли (0,0)                     идеал (1,0):
    |  устойчивый и конкретный             конкретный и неустойчивый
    +--------------------------------------------------------------
      I=0                                                        I=1
```

- **Зона боли (0,0)**: жёсткий компонент — менять тяжело (много зависящих), расширять нельзя
  (нет абстракций). Типичные обитатели: схема БД, широко используемые конкретные утилиты,
  «общий core». Безопасен, только если практически не изменяется.
- **Зона бесполезности (1,1)**: абстракции без потребителей. Обычно остатки незавершённых
  рефакторингов.
- Изменчивость — неявная третья ось: изменчивый компонент в зоне боли максимально болезненен.

## Процедура аудита

1. **Определить единицу компонента** для данного проекта (пакет / модуль сборки / библиотека).
2. **Построить граф**: узлы — компоненты, рёбра — зависимости исходного кода (импорты, ссылки
   сборки). Зависимости на стандартную библиотеку и стабильную платформу можно исключить.
3. **Найти циклы** (ADP). Любой цикл — blocker. Для каждого предложить механизм разрыва:
   инверсия через интерфейс в потребителе или выделение третьего компонента.
4. **Посчитать I** для каждого компонента и проверить каждое ребро: `I(источник) ≥ I(цель)`.
   Нарушения — ребра, направленные «вверх по устойчивости», перечислить.
5. **Посчитать A** и `D = |A + I − 1|`. Отсортировать по D по убыванию.
6. **Классифицировать выбросы**: зона боли / зона бесполезности / просто отклонение.
   Для зоны боли уточнить изменчивость (частота коммитов в компонент за период) — это
   определяет приоритет.
7. **Проверить связность** каждого крупного компонента: есть ли внутри группы модулей,
   меняющиеся по разным причинам (CCP) или используемые разными потребителями по отдельности
   (CRP).
8. **Отчёт**: таблица компонентов (Fan-in, Fan-out, I, A, D, изменчивость), список циклов,
   список нарушений SDP, топ-5 кандидатов на реструктуризацию с обоснованием.

## Шаблон отчёта

```
## Циклы (blocker)
1. A → B → C → A
   Разрыв: интерфейс XPort объявить в A, реализовать в C. Обоснование: A — высокоуровневый.

## Нарушения SDP (major)
1. Stable(I=0.1) → Flexible(I=0.9)
   Последствие: Flexible проектировался изменяемым, но теперь заморожен зависимостью.
   Исправление: интерфейс US в новом компоненте UServer (I=0), реализация в Flexible.
```

## Практика вычисления

- Считать зависимости **исходного кода**, а не рантайма: важно, что вынуждает пересборку и
  повторное развёртывание.
- Абстрактным считать тип, который нельзя инстанцировать и который объявляет контракт:
  интерфейс, протокол, трейт, абстрактный класс, сигнатура функции без реализации.
- В динамических языках A часто занижена — там «абстракция» задаётся соглашением о вызове.
  Тогда используйте D как ориентир, не как приговор, и опирайтесь сильнее на ADP/SDP.
- Тренд важнее абсолюта: график D по релизам показывает, куда съезжает дизайн. Порог
  (например, D > 0.1) выбирается эмпирически и служит триггером разбора, а не запрета.

## Что делать с результатами

| Диагноз | Действие |
|---|---|
| Цикл | разорвать немедленно (DIP или новый компонент) |
| Нарушение SDP | инвертировать зависимость через абстрактный компонент |
| Зона боли + высокая изменчивость | выделить абстракцию, спрятать конкретику за портом |
| Зона боли + нулевая изменчивость | оставить, зафиксировать как осознанный компромисс |
| Зона бесполезности | удалить или найти потребителя |
| Нарушение CCP (разные акторы внутри) | разделить компонент |
| Нарушение CRP (потребители используют части) | разделить компонент по потребителям |
