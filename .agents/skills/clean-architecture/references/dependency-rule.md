# Правило зависимостей: как применять и как проверять

## Формулировка

> Зависимости в исходном коде должны быть направлены внутрь, в сторону высокоуровневых политик.
> Ничто во внутреннем круге не знает ничего о внешних кругах.

Запрещено во внутреннем круге упоминать имена внешнего круга: классы, функции, переменные,
аннотации, константы, форматы данных, схемы, URI, ключи конфигурации.

## Как определить уровень модуля

Уровень = удалённость от ввода и вывода.

```
уровень(модуль) = длина кратчайшего пути от модуля до любого I/O
                  (сеть, диск, экран, консоль, датчик, часы, генератор случайных чисел)
```

Практические следствия:
- модуль, вызывающий часы или ГСЧ напрямую, — низкоуровневый, что бы ни было написано в его
  имени; вынесите время и случайность в порты;
- «сервис», который строит SQL, — низкоуровневый;
- модуль, который нельзя запустить без сети, — низкоуровневый.

## Разворот зависимости (когда поток управления идёт наружу)

Проблема: вариант использования обязан отдать результат презентатору / записать в БД / послать
сообщение — то есть управление течёт наружу, а зависимость наружу запрещена.

Решение (DIP):
1. Объявить интерфейс (порт) **во внутреннем круге**, в терминах внутреннего круга.
2. Реализовать его во внешнем круге (адаптер).
3. Связать их в `Main` (composition root).

```
внутренний круг                    | внешний круг
-----------------------------------|-----------------------------------
interface OrderPresenterPort       | class HttpOrderPresenter implements OrderPresenterPort
   present(OrderOutput): void      |
interface OrderStoragePort         | class SqlOrderStorage implements OrderStoragePort
   findByCustomer(CustomerId)      |
```

Именование портов — в языке предметной области, а не инфраструктуры: `Orders`, а не
`OrdersRepositoryJdbc`; `NotifyCustomer`, а не `SendGridClient`.

## Что пересекает границу

Только простые изолированные структуры данных (DTO), в форме, удобной **внутреннему** кругу.

Запрещено передавать через границу внутрь:
- строки/курсоры/записи ORM и результаты запросов;
- объекты запроса/ответа HTTP, сессии, заголовки;
- типы фреймворка (контексты, конфиги, контейнеры);
- сами сущности наружу как публичный контракт API (иначе внешние потребители диктуют
  эволюцию ядра).

Не помещать ссылки на сущности внутрь моделей запросов/ответов: у них разные причины
изменения (SRP/CCP).

## Матрица разрешённых зависимостей

| Из \ В | Сущности | Варианты использования | Адаптеры | Фреймворки/Main |
|---|---|---|---|---|
| Сущности | — | ✗ | ✗ | ✗ |
| Варианты использования | ✓ | — | ✗ | ✗ |
| Адаптеры | ✓ | ✓ | — | ✗ |
| Фреймворки/Main | ✓ | ✓ | ✓ | — |
| Тесты | ✓ | ✓ | ✓ | ✓ |

Тесты — самый внешний круг: они зависят от всего, от них не зависит ничто.

## Автоматическая проверка (обязательна, ревью недостаточно)

Порядок предпочтения:
1. **Компилятор/система модулей**: минимальная видимость типов, одна точка входа в компонент,
   отдельные единицы сборки для ядра и инфраструктуры.
2. **Архитектурный тест**: тест, падающий при запрещённом импорте (ArchUnit-подобный подход
   существует практически на каждом языке; при отсутствии — 30 строк скрипта по AST/импортам).
3. **Линтер импортов / конфигурация сборки** (запрет зависимостей между каталогами/пакетами).
4. Договорённость и ревью — последняя линия, а не первая.

Минимальный набор правил для проверки:
- ядро не импортирует ничего из инфраструктуры и сторонних фреймворков (кроме стандартной
  библиотеки и явно разрешённого списка);
- адаптеры не импортируют друг друга (веб не зовёт БД напрямую — антишаблон «Périphérique»);
- нет циклов между компонентами;
- `Main` — единственное место, где встречаются конкретные реализации.

## Проверочные вопросы к любому pull request

1. Появился ли новый импорт наружу из ядра? Если да — почему не порт?
2. Появилась ли аннотация/атрибут фреймворка на сущности или варианте использования?
3. Проходит ли структура фреймворка через границу?
4. Можно ли выполнить новый код в тесте без сети, БД, файлов и UI?
5. Знает ли высокоуровневый модуль имя, URI или ключ конфигурации низкоуровневого?
