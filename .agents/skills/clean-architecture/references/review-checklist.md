# Чек-лист архитектурного ревью

Порядок: сначала блокирующие нарушения (правило зависимостей), потом структурные, потом
эволюционные. Каждое замечание формулируется как «нарушение → последствие → минимальное
исправление».

## A. Правило зависимостей (блокирующее)

- [ ] Ядро (сущности + варианты использования) не импортирует фреймворки, ORM, HTTP, драйверы,
      DI-контейнер, логгеры конкретных вендоров.
- [ ] На сущностях и вариантах использования нет аннотаций/атрибутов инфраструктуры.
- [ ] Типы фреймворка и записи БД не пересекают границу внутрь.
- [ ] Порты объявлены во внутреннем круге и названы на языке предметной области.
- [ ] Высокоуровневые модули не содержат имён, URI, путей, ключей конфигурации низкоуровневых.
- [ ] Конкретные реализации собираются только в `Main`/composition root.

## B. Ответственности и границы

- [ ] Модуль обслуживает одного актора (SRP); нет классов, где методы принадлежат бухгалтерии,
      HR и DBA одновременно.
- [ ] Границы проведены по осям изменения (разная скорость и причины изменений).
- [ ] Для каждой границы понятно, полная она, неполная (стратегия / фасад / «пропущен последний
      шаг») или сознательно отсутствует.
- [ ] Форма пересечения границы адекватна цене: вызовы функций в монолите, а не сериализация
      ради сериализации.
- [ ] Нет «ложного дублирования», объединённого преждевременно, и нет истинного дублирования,
      размазанного по компонентам.

## C. Компоненты и зависимости

- [ ] Граф зависимостей компонентов ациклический (ADP).
- [ ] Зависимости направлены в сторону устойчивости: I убывает по направлению стрелок (SDP).
- [ ] Устойчивые компоненты абстрактны, неустойчивые конкретны (SAP).
- [ ] Нет изменчивых компонентов в «зоне боли» (устойчивый + конкретный) и мёртвых абстракций
      в «зоне бесполезности».
- [ ] Состав компонентов отражает CCP (вместе меняется — вместе лежит) и CRP (не тащим ненужное).

## D. Варианты использования и модель

- [ ] Варианты использования читаются как бизнес-сценарии, а не как «CRUD над таблицами».
- [ ] Модели ввода/вывода — простые структуры без зависимостей и без ссылок на сущности.
- [ ] Критические бизнес-правила лежат в сущностях, а не размазаны по контроллерам и SQL.
- [ ] Сущности не знают о вариантах использования.

## E. Тестируемость

- [ ] Все варианты использования тестируются без сети, БД, UI, фреймворка.
- [ ] Трудно тестируемое сведено к «скромным объектам» (View, шлюзы, драйверы).
- [ ] Тесты не повторяют структуру приложения «класс в класс, метод в метод».
- [ ] Тесты не ходят через UI ради проверки бизнес-правил.
- [ ] Время прогона тестов ядра — секунды, а не минуты.

## F. Организация кода и принуждение

- [ ] Верхний уровень дерева исходников кричит о предметной области, а не о фреймворке.
- [ ] Публичны только те типы, у которых есть внешние потребители; остальное — минимальная
      видимость.
- [ ] У компонента одна точка входа.
- [ ] Правило зависимостей проверяется автоматически (тест/линтер/сборка), а не только ревью.

## G. Эволюция и открытые варианты

- [ ] Решения о БД, вебе, фреймворках, режиме развёртывания можно изменить без переписывания ядра.
- [ ] Режим разделения (исходный код / развёртывание / службы) обратим.
- [ ] `Main` можно заменить/размножить под окружения и клиентов.
- [ ] Нет преждевременных решений, не обусловленных вариантами использования.

## Формат вывода замечания

```
[severity: blocker|major|minor] <файл:строка>
Нарушение: <какое правило нарушено>
Последствие: <какая конкретная будущая правка станет дорогой или опасной>
Исправление: <минимальный шаг, обычно ввод порта, перенос типа или сужение видимости>
```

Severity:
- **blocker** — нарушено правило зависимостей или цикл между компонентами;
- **major** — граница отсутствует там, где уже есть трение (частые совместные правки, хрупкие
  тесты, невозможность тестировать без инфраструктуры);
- **minor** — стилистика организации, именование портов, избыточная публичность.
