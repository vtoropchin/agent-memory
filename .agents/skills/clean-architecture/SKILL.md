# Чистая архитектура: ядро дисциплины

Скил задаёт единую систему координат для всех остальных скилов набора
(`solid-design`, `component-structure`, `architectural-boundaries`,
`use-cases-and-entities`, `testable-architecture`, `code-organization`,
`details-and-deferral`).

Первоисточник с точными формулировками: `references/book-digest.md`.
Быстрая проверка решения: `references/dependency-rule.md`.
Чек-лист ревью: `references/review-checklist.md`.

## Единственная цель

**Архитектура существует, чтобы уменьшить человеческие трудозатраты на создание и
сопровождение системы.** Не «красота», не «слои ради слоёв», не «правильные паттерны».
Если трудозатраты на версию N+1 выше, чем на N, — архитектура проигрывает, чем бы она себя
ни называла.

Из этого следуют два рабочих критерия для любого решения:
1. Стоимость изменения должна быть пропорциональна **масштабу** изменения, а не его **форме**.
2. Хороший архитектор **максимизирует количество непринятых решений** — как можно дольше
   сохраняет как можно больше открытых вариантов.

## Модель системы: политика и детали

- **Политика** — бизнес-правила и процедуры. Это и есть ценность системы.
- **Детали** — всё, что позволяет людям, системам и программистам взаимодействовать с
  политикой, не влияя на её поведение: БД, веб, UI, фреймворки, протоколы, устройства,
  ОС, оборудование, DI-контейнеры, форматы сериализации.

**Уровень = удалённость от ввода и вывода.** Чем дальше от I/O, тем выше уровень, тем реже
и по более важным причинам меняется код. Уровень — это не «слой в папке», а измеримое
свойство: посчитайте, сколько шагов от кода до ближайшего I/O.

## Правило зависимостей (не подлежит нарушению)

> Зависимости в исходном коде направлены только внутрь — в сторону высокоуровневых политик.

Практическое следствие: **имена, типы, аннотации, форматы данных и константы внешнего круга
не должны упоминаться во внутреннем**. Ни импортом, ни строкой, ни аннотацией, ни
конфигурацией, ни «просто DTO из фреймворка».

Круги (их может быть больше четырёх, важна не цифра, а правило):

| Круг | Содержимое | Знает о |
|---|---|---|
| 1. Сущности | критические бизнес-правила + критические бизнес-данные | ни о чём |
| 2. Варианты использования | правила, специфичные для приложения; порты ввода/вывода | о сущностях |
| 3. Адаптеры интерфейсов | контроллеры, презентаторы, ViewModel, шлюзы, SQL, мапперы | о 1–2 |
| 4. Фреймворки и драйверы | веб, БД, UI, ОС, устройства, `Main` | о 1–3 |

Поток управления и направление зависимостей **не совпадают**. Когда управление идёт наружу
(вариант использования должен что-то отдать презентатору или БД), зависимость разворачивается
через порт: интерфейс объявлен во внутреннем круге, реализация — во внешнем.
**API принадлежит потребителю, а не реализующему.**

## Процедура проектирования (новая система или новая крупная функция)

1. **Выявить акторов.** Кто (какие группы людей/ролей) будут заказывать изменения? Акторы —
   главные оси изменения (SRP). Код разных акторов не должен жить вместе.
2. **Выписать варианты использования** в форме «ввод → обработка → вывод», без единого слова
   о UI, HTTP, таблицах. Абстрактные варианты использования выделять только там, где сходство
   действительно неслучайно.
3. **Найти критические бизнес-правила и данные** → сущности. Проверка: правило осталось бы
   верным, если бы систему исполняли вручную на бумаге.
4. **Наметить границы** по осям изменения (см. `architectural-boundaries`): что меняется с
   иной скоростью и по иным причинам — разделяется.
5. **Развернуть зависимости** так, чтобы все стрелки указывали внутрь; для каждого пересечения
   границы против потока управления определить порт (интерфейс) во внутреннем круге.
6. **Определить структуры пересечения границ** — простые изолированные DTO, в форме, удобной
   внутреннему кругу.
7. **Выбрать режим разделения** (исходный код / развёртывание / службы) — по умолчанию самый
   дешёвый, с сохранением возможности перейти к более дорогому.
8. **Собрать `Main`** — самый грязный компонент: создаёт конкретные реализации, внедряет
   зависимости и передаёт управление внутрь.
9. **Проверить тестируемость**: варианты использования должны прогоняться без веба, БД, UI и
   фреймворка. Если нельзя — граница не проведена.

## Экспресс-проверки (применять постоянно)

- Если открыть верхний уровень дерева исходников, что он кричит: предметную область или имя
  фреймворка? Должен кричать предметную область.
- Можно ли удалить веб-слой и запустить все варианты использования из тестов/CLI? Должно быть «да».
- Импортирует ли хоть один модуль ядра что-то из фреймворка, ORM, HTTP, драйвера? Должно быть «нет».
- Проходит ли строка/структура БД или объект запроса HTTP внутрь ядра? Должно быть «нет».
- Знает ли высокоуровневый код имена, URI, адреса, ключи конфигурации низкоуровневых модулей?
  Должно быть «нет» — только `Main` знает.
- Пропорциональна ли стоимость типичного изменения его масштабу? Если добавление поля требует
  правок в 8 местах — граница проведена неверно или продублирована зря.

## Типичные ошибки (все — из книги, все встречаются в реальных проектах)

- **Преждевременные решения**: трёхуровневая топология, микрослужбы, корпоративная SOA, выбор
  БД и фреймворка «на старте». Это не архитектура, это топология и инструменты; они удорожают
  разработку на годы вперёд.
- **Ложное дублирование**: два похожих экрана / похожие DTO объединены «чтобы не дублировать»,
  а потом расходятся. Истинное дублирование — то, где изменение обязано быть синхронным.
  Всё остальное объединять нельзя, разделять потом дороже.
- **Утечка деталей внутрь**: аннотации ORM/DI на сущностях, `HttpRequest` в вариантах
  использования, SQL в бизнес-логике, тип фреймворка в сигнатуре порта.
- **Службы как архитектура**: разбиение на сервисы по функциям без внутренней компонентной
  структуры. Сквозная фича задевает все службы сразу.
- **Публичность по умолчанию**: если все типы публичны, любой стиль организации кода
  вырождается в слоёный монолит (см. `code-organization`).
- **Тесты через UI и по структуре классов**: хрупкие тесты делают систему жёсткой
  (см. `testable-architecture`).

## Точки адаптации к языку/стеку

Это языко-независимый скил. При переносе в конкретный проект зафиксируйте в его `AGENTS.md`/`CLAUDE.md`:
- чем реализуется «порт» (интерфейс, протокол, трейт, абстрактный класс, тип-функция,
  структурная типизация);
- чем реализуется «компонент» (модуль, пакет, сборка, crate, gem, jar, workspace-проект);
- как язык ограничивает видимость (private/internal/pub(crate)/экспорт модуля/`__all__`);
- чем проверяется правило зависимостей автоматически (линтер импортов, границы модулей,
  ArchUnit-подобный тест, конфигурация сборки);
- где живёт `Main`/composition root и какие его варианты нужны (dev/test/prod/клиент).

## Когда НЕ применять

Полная реализация всех границ дорога. Для скрипта, разовой утилиты, прототипа с горизонтом
жизни в недели — достаточно правила «политика не знает о деталях» и одной границы вокруг I/O.
Границу вводят **в точке перегиба**: когда её реализация становится дешевле, чем продолжение
жизни без неё. За этой точкой нужно следить, а не угадывать её один раз на старте.
