# Задача 9.1 — Подкоманда `memo doctor`: диагностика здоровья памяти

**Статус:** ✅ выполнена
**Этап:** 9 (Ops и модель данных) · **Область:** `cmd/memo` (новая подкоманда)
**Зависимости:** нет (все нужные read-методы Store есть: `Stats`, `EmbedMeta`,
`ListMissingVectors`).

## Контекст

Система построена на принципе «деградация, а не падение» (§15) — обратная сторона:
memo может **молча** работать в урезанном режиме (ollama лежит → recall без
вектора; ключ DeepSeek не подхватился → без сводок; embed_meta от другой модели →
reindex ещё не добежал), и понять это можно только выковыривая предупреждения из
stderr MCP-процесса. Нужна одна команда, отвечающая на вопрос «в каком режиме
реально работает память и всё ли с ней хорошо».

## Что сделать

Новый файл `cmd/memo/doctor.go` (+ тест). `memo doctor [-config path] [-json]`.

Секции проверки (каждая: ✅ / ⚠️ / ❌ + одна строка деталей; человекочитаемый вывод
на русском, `-json` — машиночитаемый для скриптов):

1. **Конфиг** — `config.Load`: путь к файлу, валидность; `[scope]` project задан?
   (пусто → ⚠️ «мультипроектность выключена»).
2. **БД** — файл существует, размер; `store.Open`; `PRAGMA quick_check` (быстрая
   целостность, не полный integrity_check); режим WAL.
3. **Записи** — `Stats`: всего, по kind, по scope, живых/superseded (тумстоуны).
4. **Векторный слой** — `EmbedMeta` (модель+dim в БД) vs `[embedder]` из конфига:
   совпадает / расходится (⚠️ «reindex перегонит при следующем старте») / индекса
   нет; `ListMissingVectors` → «N записей ждут вектора».
5. **Embedder (живость)** — provider=ollama/openai: пробный эмбеддинг (тот же путь,
   что конструкторы) с таймаутом ~5s → ✅ модель+dim / ❌ причина + «recall работает
   на чистом FTS5». provider=noop → строка «векторный слой выключен конфигом».
6. **Reasoner** — ключ в env/.env найден? provider известен? Живой запрос к DeepSeek
   **не делать** по умолчанию (стоит денег) — только флаг `-live` включает пробный
   минимальный запрос.
7. **Итог** — одна строка: `здоров` / `деградирован (N предупреждений)` / `сломан`.

Exit-код: 0 — здоров или деградирован (⚠️), 1 — есть ❌ (скриптуемость). Ничего не
чинить и не писать в БД — doctor строго read-only (единственные сетевые вызовы —
пробы живости).

Переиспользование: фабрики `newEmbedder`/`newReasoner` НЕ подходят как есть (они
глотают ошибку в Noop — doctor'у нужна причина); проверить, можно ли из них выделить
общий probe-хелпер, не ломая сигнатуры; иначе — прямые вызовы конструкторов
`embed.NewOllama`/`reason.*` с разбором ошибки.

## Границы

- Только `cmd/memo` (+ регистрация в роутинге подкоманд и `--help`). Если для
  quick_check/WAL не хватает read-метода в store — допускается ОДИН новый метод
  `store.Health(ctx) (HealthInfo, error)` (зафиксировать в отчёте); остальные
  internal-пакеты не трогать.
- Никаких write-операций и никакого автопочинки («doctor советует, не лечит»).

## Тесты

`doctor_test.go`: на scratch-БД с записями — все секции ✅, итог «здоров»; embed_meta
от другой модели → ⚠️ в секции 4; недоступная ollama (httptest закрыт) → ❌ секция 5,
но exit-логика по спеке; отсутствующий файл БД → ❌; `-json` — валидный JSON со всеми
секциями; doctor не изменил mtime/содержимое БД (read-only инвариант).

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- Живой прогон на реальной БД проекта: `bin/memo doctor` показывает фактическое
  состояние (bge-m3/1024, N записей, ollama жив/нет) и совпадает с реальностью при
  остановленной ollama.
