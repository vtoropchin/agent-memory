# Задача 14.1 — Сущность «задача» (`kind = "task"`)

**Статус:** ✅ выполнена
**Этап:** 14 (Задачи агента как тип памяти, DESIGN.md §14 Этап 14) · **Область:**
`internal/memory` (`types.go`), `internal/memory/write`, `internal/memory/recall`,
`internal/memory/store` (sqlite + postgres), `internal/memory/maint` (dedup),
`internal/mcp` (`schema.go`, `get.go`, `instructions.go`), `cmd/memo`
(`cli.go`, `export.go`, `import.go`, `web.go`, генерируемые скиллы), `cmd/memo/web`
**Зависимости:** нет.

## Контекст

Раньше ИИ-агент вёл задачи файлами (`tasks/*.md` в этом же репозитории): их не
видно из памяти, они не ищутся вместе с остальным контекстом и живут вне scope.
Решение (согласовано с пользователем): задачи хранятся в `memo` наравне с
остальной памятью — новый `kind = "task"`, пятый рядом с
`semantic`/`episodic`/`procedural`/`debt`.

Ключевые решения (развилки, выбранные пользователем, отмечены ✱):

- ✱ **Состояние — отдельное поле `status`**, а не теги и не «живая запись =
  открыта» (как у `debt`): у задачи есть промежуточные состояния, и «взята в
  работу» ≠ «ещё не начата». Значения `todo|doing|blocked|done`, дефолт `todo`;
  поле применимо ТОЛЬКО к `kind=task` (у прочих — ошибка, а не молчаливое
  отбрасывание).
- ✱ **Задача — документ, а не заметка:** `content` — полный текст (что сделать,
  границы, критерий приёмки). Отсюда два следствия: `summary` (заголовок)
  обязателен — именно он идёт в бриф recall; и появляется `memory_get` — иначе
  задачу можно найти, но не прочитать.
- ✱ **Поверхности итерации:** ядро + MCP + web (как в 13.1). Отдельной
  подкоманды `memo task` нет.
- `done` — живая запись (история сделанного), но recall её по умолчанию скрывает:
  фильтр `Query.Statuses` с пустым значением означает «всё, кроме выполненных
  задач». Отмена задачи — обычный тумстоун `memory_forget`.
- Задачи не дедуплицируются (`write.SkipDedup`) — ни на вставке, ни в
  ретроактивном sweep: SimHash откалиброван на коротких фактах, а две разные
  задачи по одной подсистеме текстуально похожи; слитая задача — потерянная
  работа.
- Ранжирование не трогается: множитель `kind` для задач равен `1` (в отличие от
  `debt` с `debt_weight`) — задачи должны конкурировать с фактами на равных.

## Что сделано

### A — ядро

- `internal/memory/types.go`: `KindTask`, тип `Status` + константы
  `StatusTodo/Doing/Blocked/Done`, перечень `Statuses`, поле `Memory.Status`,
  поле `Query.Statuses`.
- `internal/memory/write`: `SaveInput.Status`, `UpdateInput.Status`,
  `normalizeStatus` (единая точка правила для Save/Update), ошибки
  `ErrUnknownStatus`, `ErrStatusNotApplicable`, `ErrTaskSummaryRequired`,
  экспорт `SkipDedup(kind)` + его применение в `Writer.dedup`.
- `internal/memory/recall`: секция брифа `Tasks (task)` между `How-to` и
  `Tech debt`; строка задачи с маркером состояния (`- [doing] Заголовок [★4]`).
- `internal/memory/maint/dedup.go`: `groupForDedup` пропускает `kind`, исключённые
  из дедупа (`write.SkipDedup`) — задачи не попадают и в `DedupResult.Scanned`.

### B — хранилище

- SQLite: миграция `2 → 3` (`migrateStatus`, идемпотентный `ALTER TABLE ... ADD
  COLUMN status TEXT`), колонка во всех SELECT/Put, `scanMemory`,
  `statusPredicate` в `metaFilters`.
- PostgreSQL: `status text` в `CREATE TABLE` + `ALTER TABLE ... ADD COLUMN IF NOT
  EXISTS` (тот же приём, что у `schema_version.triggers_checksum` — отдельный шаг
  `pgMigrations` не заводился), `statusPredicatePG` в `metaFiltersPG`, колонка в
  запросах и `Put`.
- Пустой статус хранится как SQL NULL, а не пустой строкой.

### C — MCP

- `schema.go`: `kindEnum` += `task`; `statusEnum` выводится из `memory.Statuses`;
  `status` в `saveInput`/`updateInput`, `statuses` в `recallInput`; в
  `memory_save` добавлено поле `summary` (раньше его там не было — задача без
  заголовка была бы невозможна).
- Новый инструмент **`memory_get`** (`get.go`): полный `content` + метаданные
  Markdown-ответом; без фильтров scope/статуса (id — точный адрес) и без `Touch`.
- `instructions.go`: конвенция `kind=task`, ведение статуса, `statuses` в recall,
  `memory_get`.

### D — доставка

- `cmd/memo/web.go` + `web/app.js`: `status` в `memoryDTO`, бейдж kind `task`,
  чип состояния в списке и в карточке (read-only); `make web-css` пересобран.
- `cmd/memo/export.go`/`import.go`: аддитивное поле `status` (omitempty,
  `exportVersion` не менялся — старые бэкапы читаются как записи без статуса).
- `cmd/memo/cli.go`: `-kind task`, новые `-summary`/`-status` у `memo save`,
  `-statuses` у `memo recall`.
- Генерируемые `memo init` скиллы (`skill.go`, `bootstrap_skill.go`): раздел про
  задачи и `memory_get`.

## Тесты

- `internal/memory/write/task_test.go`: дефолт `todo`, явный статус, обязательный
  summary, неизвестный статус, статус у не-task, «две одинаковые задачи не
  сливаются, а те же тексты как semantic — сливаются», переходы статуса и
  валидация в `Update`.
- `internal/memory/recall/task_test.go`: порядок секций, строка со статусом и
  заголовком (полный текст в бриф не попадает), скрытие `done` по умолчанию +
  явный `statuses: ["done"]`.
- `internal/memory/store/task_status_test.go`: round-trip статуса и NULL для
  прочих kind, фильтр `SearchLexical`, миграция `2 → 3` на воспроизведённой
  legacy-схеме (данные целы, поиск работает, новые задачи пишутся).
- `internal/memory/maint/dedup_test.go`: `TestSweepSkipsTasks`.
- `internal/mcp/task_test.go`: схемы принимают `task`/`status`/`statuses` и
  отвергают неизвестный статус; полный цикл задачи через инструменты
  (save → recall → get → update(done) → recall → recall(statuses=[done]));
  `memory_get` на несуществующем id.

## Проверено

- `CGO_ENABLED=1 go build/vet/test -tags sqlite_fts5 -count=1 ./...` — зелёное
  (11 пакетов).
- e2e через ЖИВОЙ бинарь `bin/memo` по MCP stdio (noop-embedder/reasoner):
  `tools/list` = 5 инструментов включая `memory_get`; задача сохранена и видна в
  секции `Tasks (task)` со статусом `[todo]`; вторая задача с идентичным текстом
  НЕ слита дедупом; `memory_get` вернул полный текст; три ошибки валидации
  (нет summary / неизвестный статус / статус у semantic) читаемы; после
  `memory_update(status=done)` задача исчезла из дефолтного брифа и нашлась по
  `statuses: ["done"]`; stdout — чистый JSON-RPC.

## Отложено осознанно

- Подкоманда `memo task` в CLI (список/смена статуса отдельной командой).
- Смена статуса из web-морды — write-инвариант морды (курирование метаданных, но
  не содержания) сохранён.
- Собственный вес `kind=task` в ранжировании (`task_weight`) — задачи и должны
  конкурировать с фактами на равных.
- Эмбеддинг длинной задачи считается по всему `content`: при документе длиннее
  контекста модели (bge-m3 — 8192 токена) вектор строится по усечённому тексту.
  Лексический поиск и summary при этом работают полностью.
