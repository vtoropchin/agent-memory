# Задача 15.4 — Блокировка задач задачами: `blocked_by`, `unlinks`, правило пост-состояния

**Статус:** ⬜ ожидает
**Этап:** 15 (Kanban-доска задач, DESIGN.md §14 Этап 15) · **Область:**
`internal/memory` (`types.go`, `graph.go`), `internal/memory/write`,
`internal/memory/recall`, `internal/memory/store` (sqlite + postgres: `GetMany`),
`internal/mcp` (`schema.go`, `update.go`, `save.go`, `get.go`, `instructions.go`),
`cmd/memo` (`cli.go`, `skill.go`, `bootstrap_skill.go`), `.claude/skills/memo/SKILL.md`
**Зависимости:** 15.1 (стадии без `blocked`), 15.3 (`Neighbors` с Links, хелперы
графа). Желательно после 15.2 (чтобы инструкции правились поверх новых).

## Контекст

Любую задачу можно заблокировать другой задачей (✱ решение пользователя):
блокировка — не стадия, а **вычисляемое свойство**, которое снимается само,
когда блокер закрыт (`done`) или отменён (тумстоун). Никаких «ждём решения
человека» — если нужно решение, оно оформляется задачей-блокером. Полная
формулировка — DESIGN.md §14 Этап 15, пункт «`blocked` — не стадия».

Ключевые решения:

- Одно каноническое значение связи — `rel=blocked_by` **от заблокированной
  задачи к блокеру** («на этой карточке — кем заблокирована»); зеркального
  `blocks` нет; «что блокирует эта задача» — обратный обход через `Neighbors`.
- Правило «жив и не `done`» — одна чистая функция сущностного уровня
  `memory.LiveBlockers(task, byID)` без I/O; потребители поставляют карту.
- Правило write path — **валидация пост-состояния**, не перехода: после
  применения всех полей `status ∉ {backlog, todo} ∧ LiveBlockers ≠ ∅` →
  `ErrTaskBlocked` с перечнем блокеров. Проверяется и в `Save`, и в `Update` —
  иначе `memory_save(status: doing, links: [blocked_by X])` не проверялся бы
  вовсе, а `Update` зависел бы от порядка веток.
- `links` аддитивны (Этап 5.1) → появляется симметричное `unlinks` (общее для
  всех `rel`), удаление ребра существует в коде один раз —
  `write.UpdateInput.Unlinks`.
- Кросс-scope блокировка поддерживается: блокеры резолвятся по id, не по scope.
- В брифе recall заблокированная задача помечается `⛔` с именем блокера; в
  `memory_get` — секции «Заблокирована:» и «Блокирует:».

## Что сделать

### A — ядро

- `types.go`: константа `RelBlockedBy = "blocked_by"` рядом с остальными `Rel*`;
  годок `Status`: «`backlog`/`todo` — единственные стадии, допустимые у
  заблокированной задачи».
- `graph.go`: `BlockerIDs(m Memory) []string` — `Dst` всех `Link{Rel:
  RelBlockedBy}`; `LiveBlockers(m Memory, byID map[string]Memory) []Memory` —
  блокеры из карты, у которых `SupersededBy == nil && Status != StatusDone`.
  Функция чистая: id, отсутствующий в карте, пропускается (поставщик обязан
  загрузить всех `BlockerIDs`; висячие ссылки `resolveLinks` и так не
  пропускает, а запись, удалённая из БД физически, блокировать не может).
  `BlockedBy(id, neighbors)` — соседи с ребром `{Dst: id, Rel: RelBlockedBy}`
  («что блокирует эта задача»).
- `StatusAllowsBlocked(s Status) bool` — `backlog`/`todo` (единственное место
  этого правила).

### B — write path

- `UpdateInput.Unlinks []LinkInput` — пары `(Dst, Rel)` к удалению (пустой
  `Rel` → `related`, как в `resolveLinks`); реализация — фильтр `m.Links` перед
  `Put` (Put переписывает links записи целиком — новых методов store не нужно).
  `Unlinks` применяются после `Links` (одна операция может заменить ребро).
- `SaveInput`/`UpdateInput` без новых полей для блокировки: связь задаётся
  обычным `Links: [{Dst, Rel: blocked_by}]`.
- Валидация пост-состояния в конце `Save` и `Update` (для `Kind == KindTask`):
  `ids := BlockerIDs(m)`; если `len(ids) > 0 && !StatusAllowsBlocked(m.Status)`
  — загрузить блокеров (`Store.Get` по каждому — их единицы; или `GetMany`,
  см. C), `live := LiveBlockers(m, byID)`; `len(live) > 0` → новая ошибка
  `ErrTaskBlocked` (тип с полем `Blockers []memory.Memory` и `Error()` вида
  «write: задача заблокирована: <summary> (<id>), …», `errors.Is` через
  сентинел). Блокер, который не `kind=task`, — допустим? Нет: `resolveLinks`
  для `Rel == RelBlockedBy` требует `Dst.Kind == KindTask`, иначе
  `ErrBlockerNotTask` (единственное правило про `rel`, которое write проверяет
  по типу цели).
- Self-link `blocked_by` на себя — уже отсекается общим guard'ом `Dst == id`.

### C — store: `GetMany`

- `Store.GetMany(ctx, ids []string) ([]memory.Memory, error)` — записи по
  списку id (живые и тумстоуны — вызывающий сам фильтрует по `SupersededBy`),
  с Tags и Links (батчами, не N+1), порядок не гарантируется, отсутствующие
  id молча пропускаются. SQLite + PostgreSQL. Нужен recall (D) и доске (15.5).
- `write` может использовать `GetMany` вместо цикла `Get` — на усмотрение,
  главное без N+1 на доске/recall.

### D — recall: маркер блокировки

- После отбора записей в бриф (до сборки Markdown): собрать `BlockerIDs` по
  всем задачам брифа → один `GetMany` → карта; `formatLine` для задачи с
  `LiveBlockers ≠ ∅`: `- [todo] ⛔ Заголовок (ждёт: <summary блокера>[, …]) [★4]`
  (первые два блокера, далее `+n`). Ошибка `GetMany` → маркер не выводится, лог
  в stderr (§15 деградация). Recall-кандидаты из `SearchLexical` Links не несут —
  проверить и при необходимости догружать Links только для задач брифа тем же
  `GetMany` по их id (второй батч), а не менять `Search*`.

### E — MCP, CLI, инструкции, скиллы

- `schema.go`: enum `rel` в `links` += `blocked_by`; `updateInput.Unlinks
  []linkInput` (описание: «связи к удалению; пары id+rel; единственный способ
  снять блокировку»). Маппинг `ErrTaskBlocked`/`ErrBlockerNotTask` в текст
  ошибки инструмента с перечнем блокеров.
- `get.go`: секции «Заблокирована (ждёт):» (живые блокеры, по `LiveBlockers`)
  и «Блокирует:» (по `BlockedBy(id, Neighbors)`), каждая строка `- [status]
  Заголовок (id)`.
- `instructions.go`, `skill.go`, `bootstrap_skill.go`, `.claude/skills/memo/
  SKILL.md`: конвенция — блокировать через `links:[{id:<блокер>,
  rel:"blocked_by"}]` на заблокированной задаче; заблокированную нельзя взять
  в `doing` (сервер вернёт ошибку с перечнем); снимается сама по `done`
  блокера; вручную — `unlinks`. Убрать остатки про статус `blocked`.
- `cli.go`: `memo save`/`recall` — без новых флагов (links в CLI не задаются и
  сейчас — проверить; если задаются, добавить `-unlink`).

## Границы

- НЕ трогать `board`/`web` (15.5/15.6 используют `LiveBlockers`/`GetMany`),
  `maint`, `config`, схему БД (миграций нет — `rel` TEXT без CHECK).
- Не вводить зеркальный `blocks`, не вводить статус блокировки в БД.
- Не менять семантику `part_of`/`causes`.
