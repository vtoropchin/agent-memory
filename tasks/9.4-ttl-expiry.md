# Задача 9.4 — TTL: явное время жизни записи (`expires_at`)

**Статус:** ✅ выполнена
**Этап:** 9 (Ops и модель данных) · **Область:** `internal/memory` (types, store, write, maint) + `internal/mcp`
**Зависимости:** нет.

## Контекст

Забывание сейчас только эвристическое: decay понижает вес неиспользуемых episodic,
консолидация сжимает старьё. Но у части фактов срок годности известен **заранее и
точно**: «токен деплоя действует до 1 августа», «до релиза 2.0 держим фичефлаг X»,
«встреча в пятницу». Такие записи после срока не просто малополезны — они **вредны**
(агент применит устаревший факт). Нужно детерминированное забывание по расписанию,
дополняющее (не заменяющее) decay.

## Что сделать

### Часть A — схема и store

- Колонка `expires_at INTEGER` (nullable, unix ts) в `memories` — `ALTER TABLE ADD
  COLUMN` миграцией при `Open` (по образцу существующих миграций; если механики нет —
  `PRAGMA user_version`, согласовать с 8.3, где тоже миграция).
- `Memory.ExpiresAt int64` (0 = вечная) в types.go; Put/Get/List/DTO — проброс поля.
- **Фильтр протухших в recall**: в `metaFilters` — `(m.expires_at IS NULL OR
  m.expires_at > ?now)`. Через metaFilters условие автоматически действует на оба
  источника (FTS и вектор) одинаково — требование §8. «Сейчас» — через существующий
  механизм `WithNow`/часы recall, если есть (тестируемость), иначе `time.Now` в
  одной точке.

### Часть B — write и MCP

- `SaveInput.TTL string` (Go duration, напр. `"72h"`, пусто = вечно) → write
  парсит и пишет `expires_at = now + ttl`; невалидная строка → ошибка (fail-fast).
  Duration, а не абсолютная дата — агенту почти всегда известно «сколько актуально»,
  а не «до какого unix ts»; для абсолютных дат агент сам посчитает разницу.
- `UpdateInput`: возможность продлить (`ttl`) или снять (`ttl: "0"` → вечная —
  задокументировать явно) срок.
- Схема `memory_save`/`memory_update`: поле `ttl` с русским описанием и примерами
  типовых значений («24h», «168h»); `buildInstructions` — одна строка: «факту с
  известным сроком годности задавай ttl».

### Часть C — maint

- Джоб `ExpireSweep` в `maint` (по образцу Decayer): записи с
  `0 < expires_at < now` и без superseded_by → тумстоун `Supersede(id, id)`
  (та же механика, что forget/архив decay — мягко, история цела). Нужна выборка
  `Store.ListExpired(ctx, now, limit)` (Tags/Links не грузить — как соседние
  List*-методы).
- Подключить в `Scheduler.RunOnce` (порядок: Expire ПЕРЕД Decay — протухшие не
  должны тратить прогон decay; параметров конфига не требует). Сводная строка лога
  прогона дополняется `expire(scanned=N archived=M)`.

Двойная защита осознанна: фильтр в recall скрывает протухшее **немедленно** (между
прогонами планировщика), sweep превращает скрытое в тумстоун (гигиена БД).

## Границы

- Decay/консолидацию не менять. Web read-only показ `expires_at` в карточке —
  только если сводится к выводу поля в DTO (иначе — вне задачи). CLI (7.1, если уже
  есть) — флаг `-ttl` по аналогии, одной строкой.

## Тесты

- store: миграция на существующей БД (старые записи → expires_at NULL, живы);
  metaFilters отсекает протухшие в ОБОИХ Search* (живой sqlite-vec); граница
  `expires_at == now`.
- write/mcp: ttl парсится, невалидный → ошибка; update продлевает и снимает.
- maint: sweep архивирует только протухшие, идемпотентен; scheduler-тест дополнен
  пятым джобом.
- recall e2e: запись с ttl «в прошлом» не выдаётся даже до прогона sweep.

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- e2e через живой бинарь: save с `ttl:"1s"` → через 2s recall её не возвращает;
  после прогона планировщика — тумстоун (виден в web-морде как superseded).
- DESIGN §4 (колонка), §11 (джоб), §12 (поле ttl) — синхронизированы.
