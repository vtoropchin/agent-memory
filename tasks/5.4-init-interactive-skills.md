# Задача 5.4 — `memoryd init`: генерация скила под агентское приложение + интерактивный сетап

**Этап:** 5 (Самоприменение), после 5.3. **Статус:** сделано (2026-07-11).

## Контекст

`memoryd init` (файл `cmd/memoryd/init.go`, задача 5.3) сейчас неинтерактивно раскладывает
в целевой каталог два файла: `.mcp.json` (MCP-сервер `agentmemory` поверх stdio) и
`agentmemory.toml` (полный конфиг, `project` = имя каталога). Флаги: `-project`, `-dir`,
`-force`. Ключ DeepSeek нигде не хранится — `.mcp.json` берёт его из env через
`${DEEPSEEK_API_KEY:-}`.

Нужно расширить `init` до полноценного установщика памяти в проект под **конкретное
агентское приложение**, с генерацией **скила** (инструкции для агента, как пользоваться
памятью) и интерактивным запросом параметров.

Решения пользователя (2026-07-11), обязательны к исполнению:
- **Скил** = «Протокол работы с памятью»: полноценная инструкция агенту — `memory_recall`
  в начале задачи, `memory_save`/`memory_update`/`memory_forget` по ходу, правила scope
  (save без scope → `project:<name>`, общие привычки → `user:*`). Обобщённая версия
  раздела «Память проекта» из скила `/dev`.
- **Ключ DeepSeek** пишется в `<dir>/.env` (`DEEPSEEK_API_KEY=...`), `.env` добавляется в
  `<dir>/.gitignore`. Чтобы ключ реально долетал до memoryd (Claude Code НЕ подгружает
  `.env` в env MCP-сервера автоматически), **memoryd при старте сам грузит `.env`** из
  каталога своего `-config`.
- **Интерактивно спрашиваются:** агентское приложение (обязательно), имя проекта, ollama
  (base_url + модель), путь к БД, ключ DeepSeek.

## Границы (за них не выходить)

- Только `cmd/memoryd/*` (init.go, main.go, тесты, новые файлы пакета `main`) и, при
  необходимости, минимальный хелпер загрузки `.env`. `internal/*` (config/store/mcp/
  recall/write/embed/reason/maint) — **не трогать по логике**; допускается лишь чтение.
- Не менять серверный флоу MCP (`run()` в main.go) кроме врезки загрузки `.env` до чтения
  `DEEPSEEK_API_KEY`.
- Только stdlib (без сторонних TUI/`.env`/`term`-библиотек). Парсеры простые, ручные —
  как `parseFrontMatter` в `cmd/memimport`.
- Обновить `DESIGN.md` (§13 конфигурация — про `.env`; §14/§5 — упоминание генерации скила)
  и `config.example.toml`/комментарии, если затрагивается формат.

## Часть A — memoryd грузит `.env` (серверная врезка)

1. Хелпер `loadDotEnv(path string)` (например, `cmd/memoryd/dotenv.go`): читает файл
   `KEY=VALUE` построчно (stdlib `bufio`), игнорирует пустые строки и `#`-комментарии,
   тримит пробелы, снимает опциональные кавычки со значения. Для каждого ключа —
   `os.Setenv` **только если переменная ещё не установлена** (`os.LookupEnv`): shell-env
   имеет приоритет над `.env`. Файла нет → тихий no-op (не ошибка). Ошибку чтения
   существующего файла — вернуть/залогировать в stderr, но НЕ падать (§15 деградация).
2. В `main.go` (`run()`): до создания reasoner (до чтения `DEEPSEEK_API_KEY`) вызвать
   `loadDotEnv` для файла `.env` в **каталоге `-config`** (если `-config` пуст — в текущем
   каталоге). Логировать факт подгрузки в stderr (без значения ключа!).
3. Контракт формата `.env` — общий с частью B: имя файла `.env`, строка
   `DEEPSEEK_API_KEY=<key>`.

**Критерий приёмки A:** memoryd, запущенный с `-config <dir>/agentmemory.toml`, где рядом
лежит `<dir>/.env` с `DEEPSEEK_API_KEY=...`, поднимает DeepSeek-reasoner (не Noop), если в
shell-env ключа нет. Значение ключа не попадает в stdout/stderr. Юнит-тест на `loadDotEnv`
(приоритет shell-env, комментарии, кавычки, отсутствие файла).

## Часть B — интерактив + генерация скила (init.go)

### B1. Абстракция агентского приложения (расширяемость под opencode/codex)

- Тип `agentTarget` c полями/методами, описывающими одно агентское приложение: ключ (`claude`),
  человекочитаемое имя, и как оно раскладывает артефакты — **MCP-конфиг** (путь + рендер) и
  **скил** (путь + рендер). Реестр `map[string]agentTarget` (или слайс) — сейчас **только
  `claude`**, но структура должна позволять добавить `opencode`/`codex` одной записью (их
  форматы НЕ реализуем, но оставляем очевидное место).
- Для `claude`:
  - MCP-конфиг: `<dir>/.mcp.json` (как сейчас, `renderMCPJSON`).
  - Скил: `<dir>/.claude/skills/agentmemory-memory/SKILL.md` (создать промежуточные каталоги).

### B2. Генерация скила «Протокол работы с памятью»

- Шаблон SKILL.md с валидным фронтматтером (`name`, `description`) и телом-инструкцией:
  когда звать `memory_recall` (в начале задачи, scope не указывать — инстанс подставит
  `project:<name>` + `user:*`), когда `memory_save` (атомарный факт, `scope:""` для
  проектного — из-за отсутствия omitempty в схеме передавать пустую строку, не опускать
  ключ; общие привычки — `scope:"user:*"`), `memory_update`/`memory_forget`. Имя проекта
  подставляется в текст. Держи скил кратким и практичным.
- Контент вынести в переиспользуемую форму (шаблон-строка/функция), чтобы под будущие
  opencode/codex переиспользовать тело, меняя только обёртку/путь.

### B3. Интерактивный сетап (TTY-aware)

- Ввести структуру `initConfig` (project, dir, agentApp, ollamaBaseURL, ollamaModel,
  storePath, deepseekKey, force). `doInit` перевести на приём этой структуры (текущие
  вызовы в тестах — обновить).
- Слой `promptInit`: спрашивает недостающие значения через stdin (stdlib `bufio.Scanner`),
  показывая дефолт в скобках; пустой ввод = дефолт. Для агентского приложения — выбор из
  списка (сейчас один пункт `claude`, но диалог рассчитан на несколько).
- **Флаги = преответы:** если значение задано флагом, промпт по нему пропускается. Добавить
  флаги: `-agent` (claude), `-ollama-url`, `-ollama-model`, `-store`, `-deepseek-key`
  (последний — с осторожностью, для не-интерактивного сценария). Существующие `-project`/
  `-dir`/`-force` сохранить.
- **Не-TTY:** если stdin не терминал (проверка через `os.Stdin.Stat()` и
  `ModeCharDevice`), **не** спрашивать ничего — брать флаги/дефолты. Это сохраняет
  тестируемость и скриптуемость. Флаг `-no-input`/`-yes` для явного отключения промптов
  тоже допустим.

### B4. Запись артефактов

- Рендерить и писать: MCP-конфиг, скил, `agentmemory.toml` (с введёнными ollama/store/
  project), `.env` (если ключ введён) + дополнение `.gitignore` строкой `.env`.
- `.env`: писать `DEEPSEEK_API_KEY=<key>` с правами `0o600` (секрет). Идемпотентность: если
  `.env` существует без `-force` — не перезатирать молча (предупредить), как `writeScaffoldFile`.
- `.gitignore`: если строки `.env` ещё нет — дописать (создать файл, если нет). Не дублировать.
- `agentmemory.toml`: `[embedder] base_url/model` и `[store] path` подставлять из initConfig
  (сейчас захардкожены в шаблоне) — параметризовать шаблон.
- Сохранить идемпотентность и `-force`-семантику существующего `writeScaffoldFile`.

## Критерий приёмки (общий)

- `CGO_ENABLED=1 go build/vet/test -tags sqlite_fts5 -count=1 ./...` — зелёное.
- Юнит-тесты: `loadDotEnv`; резолв initConfig (флаги vs дефолты); не-TTY не блокирует;
  рендер скила (валидный фронтматтер, имя проекта в теле); запись `.env` (0600) и
  дополнение `.gitignore` без дублей; идемпотентность (повторный init ничего не портит);
  агент-реестр (неизвестный `-agent` → внятная ошибка).
- e2e через живой бинарь: `memoryd init` в пустом каталоге (не-интерактивно, флагами) →
  появляются `.mcp.json`, `agentmemory.toml`, `.claude/skills/agentmemory-memory/SKILL.md`,
  `.env` (0600, с ключом), `.gitignore` (со строкой `.env`); затем `memoryd -config
  <dir>/agentmemory.toml` подхватывает ключ из `.env` (reasoner ≠ Noop), stdout — чистый
  JSON-RPC, ключ не светится в логах.
- Неизвестное агентское приложение → внятная ошибка со списком поддерживаемых.

## Заметки для реализации

- Секрет не логировать никогда (ни init, ни memoryd). В выводе init — только факт записи.
- Ввод ключа в терминале эхается (маскировка требует `x/term` — вне stdlib, не делаем);
  допустимо, т.к. ключ всё равно уходит в `.env`. Можно предупредить пользователя.
- Управляющие символы в имени проекта уже валидируются (`resolveProjectName`) — сохранить.
