# Задача 3.3 — Вектор в write path + отложенный досчёт

**Статус:** ⏳ ожидает 3.1, 3.2
**Этап:** 3 (Embedder + гибрид) · **Пакеты:** `internal/memory/write`, `internal/memory/store`
**Зависимости:** 3.2 (PutVector работает); интерфейс `Embedder` — уже в репо

## Контекст

DESIGN.md §7.4: FTS5 всегда; вектор — если `Embedder != noop`, иначе откладывается в
очередь на досчёт фоновым джобом. §9: ollama недоступен → save откладывает вектор.
«Очередь» — это просто записи без строки в `memories_vec` (отдельная таблица не нужна).

## Что сделать

1. `write.Writer` получает зависимость `embed.Embedder` (расширить конструктор; поправить
   все места вызова — тесты, `cmd/memoryd`, `maint` — передав существующий `embed.NewNoop()`).
2. В `Save` и в `Update` (когда меняется content): если `embedder.Dim() > 0` — посчитать
   `Embed(ctx, []string{content})` и `store.PutVector(id, vec)`. Любая ошибка эмбеддинга
   или PutVector → **запись всё равно сохранена**, ошибка только в лог stderr (вектор
   досчитает фоновый джоб). Noop (`Dim()==0`) → вектор не считается, это не ошибка.
3. Расширить интерфейс `Store` методом
   `ListMissingVectors(ctx context.Context, limit int) ([]Memory, error)` — записи без
   `superseded_by`, у которых нет строки в `memories_vec` (LEFT JOIN … IS NULL);
   если vec-таблица не существует → пустой список без ошибки. Реализация в sqlite.go +
   тест. Комментарий со ссылкой на DESIGN §7.4/§9 (очередь досчёта).
4. Тесты write: с фейковым Embedder (фиксированный вектор, счётчик вызовов) — Save кладёт
   вектор; ошибка Embed → Save успешен, вектора нет, запись видна в ListMissingVectors;
   Noop → Embed не вызывается; Update с новым content переэмбеддит.

## Границы

Не трогать: `recall`, `mcp`, `embed` (реализация ollama — 3.1), фоновый джоб досчёта —
задача 3.5. `cmd/memoryd` менять только в месте вызова конструктора Writer.

## Критерий приёмки

- Билд чист; `CGO_ENABLED=1 go test -tags sqlite_fts5 -count=1 ./...` зелёный целиком.
