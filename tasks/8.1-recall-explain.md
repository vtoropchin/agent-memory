# Задача 8.1 — Explain-трасса ранжирования в recall

**Статус:** ⬜ ожидает
**Этап:** 8 (Качество recall) · **Область:** `internal/memory/recall` + `internal/memory/types.go` + `internal/mcp`
**Зависимости:** нет.

## Контекст

Ранжирование recall — чёрный ящик: агент и пользователь видят итоговый бриф, но не
видят, **почему** запись попала в выдачу и почему именно на этом месте. Это мешает
тюнить веса `[recall].weights` из конфига и подрывает доверие («recall не нашёл — а
он вообще искал вектором?»). Нужен опциональный explain-режим: для каждой записи
брифа — источник кандидата и разложение итогового скора.

Формула (DESIGN §8): RRF по источникам (FTS/vector), затем
`final = w1·relevance + w2·importance + w3·recency_decay + w4·log(1+access_count)`.
Все слагаемые уже вычисляются внутри `recall` — задача в том, чтобы их **не выбрасывать**,
а донести до брифа.

## Что сделать

### Часть A — recall

- `Query.Explain bool` в `types.go`.
- Внутри `Recaller`: при `Explain` собирать для каждой выжившей записи структуру
  (предлагаемый вид, уточнить по фактическому коду ранжирования):

```go
// Explain — трасса ранжирования одной записи брифа (заполняется при Query.Explain).
type Explain struct {
    Sources   []string // "fts", "vector" — какие источники подняли кандидата
    RRF       float64  // слитый RRF-скор
    Relevance float64  // w1-слагаемое (после весов)
    Importance float64 // w2-слагаемое
    Recency   float64  // w3-слагаемое
    Access    float64  // w4-слагаемое
    Final     float64  // итог, по которому отсортирован бриф
}
```

- `Candidate.Source` уже несёт источник ("fts"/"vector") — при слиянии в fuseRRF
  сохранять **все** источники записи, не только первый (сейчас, вероятно,
  теряется — проверить и починить именно в explain-структуре, поведение самого
  ранжирования не менять).
- В Markdown-бриф при `Explain` — компактная строка-довесок под каждой записью:
  `  · via fts+vector · rrf 0.031 · rel 0.62 + imp 0.40 + rec 0.18 + acc 0.05 = 1.25`
  (формат: одна строка, округление до 2–3 знаков). Заголовок брифа получает пометку
  `(explain)`. При `Explain=false` — байт-в-байт прежний бриф (регрессий формата нет).

### Часть B — MCP

- Поле `explain` (bool, по умолчанию false) в схеме `memory_recall` (`schema.go`),
  описание на русском: «добавить к каждой записи трассу ранжирования: источники
  (fts/vector), RRF и разложение итогового скора — для отладки и тюнинга весов».
- Прокинуть в `Query.Explain` в `handleRecall`.

## Границы

- Логику ранжирования/отбора **не менять** — только собрать и показать уже
  вычисляемое. Никаких изменений store/write/embed. Summarize (Reasoner) с explain
  не пересекается: сводка строится по брифу без explain-строк.
- Web-морда — вне задачи (сможет переиспользовать позже).

## Тесты

`recall_test.go`: explain-бриф содержит строку `via` с корректными источниками
(запись, найденная обоими источниками → `fts+vector`; только лексикой → `fts`);
сумма слагаемых сходится с Final (допуск на округление); `Explain=false` → бриф
идентичен эталонному (снапшот-сравнение с существующим тестом формата);
`server_test.go`: поле `explain` доезжает от MCP-входа до Query.

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные; существующие тесты формата брифа
  не изменились.
- e2e через живой бинарь: `memory_recall` с `"explain": true` возвращает бриф с
  трассами; на записи, находимой только вектором (перефразировка), в трассе виден
  источник `vector`.
- DESIGN §8/§12 — по одному предложению про explain.
