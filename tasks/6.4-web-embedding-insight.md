# Задача 6.4 — Полезная эмбеддинг-информация в web-морде

**Статус:** ✅ выполнена (2026-07-12). Store: `VectorStatus`/`SemanticNeighbors` (+тип, k-before-filter
запас k+5, `Score`=честная дистанция). API: `/api/memories/{id}` обогащён `embedding`+`semanticNeighbors`.
Фронтенд: бейдж «вектор ✓ bge-m3·1024» + блок «Семантически близкие (по вектору)» с дистанциями.
Билд/vet/тесты `-tags sqlite_fts5` зелёные (11 пакетов); арх-ревью — соответствует; code review high — 0 багов.
e2e на живой БД (bge-m3/1024): карточка в браузере показывает бейдж вектора и 5 KNN-соседей с cosine-дистанциями.
**Этап:** 6 (Web-морда) · **Область:** `internal/memory/store` + `cmd/memoryd` (API) + `cmd/memoryd/web` (фронтенд)
**Зависимости:** 6.1/6.2/6.3 (морда, JSON API, фронтенд уже есть)

## Контекст

Морда (6.1–6.3) показывает записи, но никак не отражает **векторный слой** — а он ключевая
часть системы (DESIGN.md §8/§9). Задача: вывести в морде **полезную** информацию об эмбеддинге,
а НЕ сырой вектор.

Обоснование (проверено на реальной БД проекта, bge-m3/1024, 19 записей = 19 векторов):
- **Сырые 1024 float — бесполезны для человека:** оси пространства не подписаны, «измерения=темы»
  нет, разглядывать столбик чисел нечего.
- **Полезно — производное от вектора:**
  1. **Семантические соседи (KNN по cosine)** — «что модель считает близким по смыслу».
     Наглядно и отлаживаемо (пример на живой БД: у записи про «векторный слой» ближайшие —
     про DeepSeek/ollama-инфраструктуру и стек, без общих ключевых слов). Это главный вывод.
  2. **Статус вектора** — сэмбеджено ✓ / в очереди на досчёт; модель+dim (`bge-m3`, 1024).
     Ловит рассинхрон (reindex не той моделью) и записи, ждущие Embedder.
- Сырой вектор — максимум за спойлером «для отладки», низкий приоритет.

Read-only сохраняется: только новые SELECT'ы, никаких write-операций и мутаций.

## Что сделать

### Часть A — Store (`internal/memory/store`), foundational внутри задачи

Два read-метода (сигнатуры — в стиле существующих; типы в пакете `store`):

```go
// VectorStatus — состояние векторного слоя для одной записи (для морды).
type VectorStatus struct {
    Embedded bool   // есть строка в memories_vec
    Model    string // из embed_meta (пусто, если векторный индекс не создавался)
    Dim      int    // из embed_meta (0, если не создавался)
}

// VectorStatus возвращает состояние вектора записи id. Если векторный индекс ещё
// не создавался (Embedder всегда был noop) — Embedded=false, Model="", Dim=0 без
// ошибки (деградация §15). Дёшев (проверка наличия строки + чтение embed_meta).
VectorStatus(ctx context.Context, id string) (VectorStatus, error)

// SemanticNeighbors возвращает до k ближайших по cosine-дистанции ЖИВЫХ записей к
// записи id (исключая её саму и superseded), отсортированных по возрастанию
// дистанции. Candidate.Score = distance (не 1/(1+d) — морде нужна честная
// дистанция), Candidate.Source = "vector". Если у записи нет вектора ИЛИ индекс не
// создавался — пустой список без ошибки (деградация §15).
SemanticNeighbors(ctx context.Context, id string, k int) ([]memory.Candidate, error)
```

Реализация (`sqlite.go`):
- `VectorStatus`: `hasVecTable` (уже есть) → нет таблицы → нулевой статус; иначе
  `SELECT EXISTS(SELECT 1 FROM memories_vec WHERE memory_id=?)` + чтение `embed_meta`
  (переиспользовать существующий `EmbedMeta`).
- `SemanticNeighbors`: KNN через `embedding MATCH (SELECT embedding FROM memories_vec
  WHERE memory_id=?) AND k=?` (CTE, как в `SearchVector`). **Важно — k-before-filter**
  (известное ограничение sqlite-vec, см. [[scope-multiproject]] / tasks/3.2): фильтры
  (self, superseded) применяются ПОСЛЕ k, поэтому запрашивать `k = requested + запас`
  (напр. `k+5`), затем в Go отфильтровать `memory_id != id` и superseded, обрезать до k.
  Дистанцию (`v.distance`) класть в `Candidate.Score`. Tags/Links не грузить (лёгкий список).
  Нет вектора у якоря / нет таблицы → `nil, nil`.

### Часть B — API (`cmd/memoryd`, `web.go`)

Расширить ответ **`GET /api/memories/{id}`** (не плодить эндпоинт) двумя полями:
```json
{
  "memory": { ... },
  "neighbors": [ ... ],                        // графовые (уже есть, из 6.2)
  "embedding": { "embedded": true, "model": "bge-m3", "dim": 1024 },
  "semanticNeighbors": [ { "...memoryDTO": "", "distance": 0.3080 } ]
}
```
- `embedding` ← `Store.VectorStatus(id)`.
- `semanticNeighbors` ← `Store.SemanticNeighbors(id, N)` (N по умолчанию, напр. 5), каждый —
  `memoryDTO` + поле `distance` (float). Переиспользовать `toDTO`.
- Деградация: пустой векторный слой → `embedding.embedded=false`, `semanticNeighbors: []`
  (не ошибка). Никаких вызовов ollama — данные уже в БД.

### Часть C — Фронтенд (`cmd/memoryd/web`)

В **карточке записи** добавить:
- **Бейдж статуса вектора** рядом с kind/scope: `вектор ✓ bge-m3·1024` (embedded) либо
  `вектор: в очереди` (pending) либо ничего/`векторный слой выключен`, если `model==""`.
- Блок **«Семантически близкие (по вектору)»** — рядом с графовыми связями/соседями: список
  `semanticNeighbors`, у каждого дистанция (напр. `0.31`) + первые строки content, **кликабельно**
  → открывает карточку соседа (та же навигация, что у графовых соседей). Пустой список — короткая
  плашка «нет семантических соседей / векторный слой выключен».
- Опционально (низкий приоритет, за `<details>`-спойлером «сырой вектор для отладки») — можно
  НЕ делать в этой версии; если делать, то отдельным полем API, а не в основном ответе.

UI-подписи на русском; экранирование через `textContent` (как в 6.3).

## Границы

- `store` — только два новых read-метода + типы; схему БД не менять; существующие методы не
  трогать. `cmd/memoryd` — только обогащение хендлера `/api/memories/{id}` + DTO; write-путь,
  MCP, `init` не трогать. `web` — только карточка записи. Новых внешних зависимостей нет.
- Никаких вызовов Embedder/ollama из морды — только чтение уже сохранённых векторов из БД
  (морда остаётся оффлайн-читателем; при выключенном векторном слое всё деградирует, а не падает).

## Тесты

- **Store** (`store_test.go`, живой sqlite-vec): `VectorStatus` — embedded/не-embedded/нет
  индекса; `SemanticNeighbors` — исключает себя и superseded, сортировка по дистанции возрастанию,
  k-обрезание с запасом работает, нет вектора у якоря → пусто, нет vec-таблицы → пусто.
- **API** (`web_test.go`, httptest): `/api/memories/{id}` содержит `embedding` и
  `semanticNeighbors` (с `distance`); при noop-store (без векторов) — `embedded:false`,
  `semanticNeighbors:[]`, статус 200 (не 500).

## Критерий приёмки

- `CGO_ENABLED=1 go build/vet/test -tags sqlite_fts5 -count=1 ./...` — зелёное.
- На реальной БД (bge-m3): карточка записи показывает статус-бейдж вектора и список
  семантически близких записей с дистанциями, переход по соседу работает; при выключенном
  векторном слое морда деградирует (плашка), а не падает.
