# Задача 12.1 — `memo init` + postgres: проверка готовности базы и подсказка про `memo migrate`

**Статус:** ✅ выполнена
**Этап:** 12 (Общая память команды, DESIGN.md §14 Этап 12) · **Область:** `cmd/memo` (`init.go`, `wizard.go`)
**Зависимости:** выбор бэкенда хранилища в `memo init` (уже сделан: `-store-driver`,
`-postgres-*`, read-only проба подключения).

## Контекст

`memo init` теперь умеет настроить PostgreSQL-хранилище сам и перед записью файлов делает
**read-only** пробу подключения (`store.OpenPostgresReadOnlyContext` + `Health` — соединение,
`current_schema()`, `SELECT 1`/`SHOW server_version`/`pg_is_in_recovery`; накатывать
прод-схему памяти в общую командную базу «за компанию» с проверкой доступности он права не
имеет, DESIGN.md §15 и комментарий у `probeStoreConnectionLive`).

Отсюда три осознанно оставленных пробела:

1. **Проба проверяет доступность, но не готовность.** «Сервер отвечает и база открывается»
   не означает, что первый штатный старт `memo` пройдёт: у роли может не быть прав на
   `CREATE` в целевой схеме, а расширение `pgvector` может быть не установлено (тогда
   векторный слой молча не поднимется при первом `ResetVectorIndex`). Сейчас это выяснится
   не в `memo init`, а позже — при старте сервера или при reindex.
2. **Про перенос накопленной памяти init молчит.** Разработчик, у которого уже есть
   локальный SQLite с памятью, после `memo init -store-driver postgres` получает пустую
   общую базу и нигде в выводе не видит, что для переезда есть `memo migrate` (README,
   раздел «Общая база команды», шаг 3).
3. **`MEMO_POSTGRES_PASSWORD` не пробрасывается в MCP-конфиг.** Для ключей провайдеров
   `memo init` кладёт в `.mcp.json`/`opencode.json` плейсхолдеры (`${DEEPSEEK_API_KEY:-}`,
   `{env:OPENAI_API_KEY}` — см. `buildProviderEnv`), для пароля БД — нет. Сегодня это
   работает: memo сам подхватывает пароль из `.env` рядом с конфигом при старте
   (`loadDotEnv`). Добавлять плейсхолдер наугад не стали — сначала нужно проверить на
   живых харнессах, как Claude Code и opencode ведут себя с переменной, которой нет в
   окружении (пустой инжект против отсутствия ключа), и не перекроет ли пустое значение
   восстановление пароля из `.env` (в `loadDotEnv` пустое значение как раз перекрывается
   .env, но у opencode синтаксис интерполяции другой). Это отдельная задача с ручной
   проверкой обоих приложений, а не строчка в `buildProviderEnv`.

## Что сделать

- Расширить пробу read-only диагностикой готовности (всё — только `SELECT`, без DDL):
  наличие расширения `vector` (`pg_extension`) и права роли на создание объектов в текущей
  схеме (`has_schema_privilege(current_schema(), 'CREATE')`). Отсутствие — **предупреждение**
  в вывод с объяснением последствий, а не отказ (деградация, а не падение): база может
  готовиться администратором отдельно.
- Если целевое хранилище — postgres, а рядом (в `-dir` или по дефолтному
  `~/.agentmemory/memory.db`) есть непустой SQLite-файл, — напечатать в конце `memo init`
  готовую строку `memo migrate ...` для переноса. Только подсказка: сам перенос `init`
  делать не должен (это отдельная явная операция над чужими данными).
- Проверить на живых Claude Code и opencode поведение с плейсхолдером
  `MEMO_POSTGRES_PASSWORD` в MCP-конфиге (пункт 3) и, если оба харнесса ведут себя
  корректно, добавить его в `buildProviderEnv`/`buildOpencodeServerEntry`; если нет —
  зафиксировать в DESIGN.md §13, что пароль БД доезжает только через `.env`.
- Тесты — в стиле уже имеющихся: диагностика на подменяемой точке (`probeStoreConnection`),
  живая проверка — под `MEMO_TEST_POSTGRES_DSN` со `t.Skip` без него; общая база команды не
  чистится TRUNCATE/DROP, только read-only запросы.

## Границы

Не менять контракт `store.OpenPostgresReadOnly`/`OpenPostgresReadOnlyContext` (никакого DDL
из `init`/`doctor`), не менять сигнатуру `doInit(cfg, out)`, не трогать генерацию секций
TOML для остальных бэкендов.

## Критерий приёмки

`memo init -no-input -store-driver postgres ...` на базе без `pgvector`/без прав на CREATE
завершается успешно, но печатает внятное предупреждение о том, что именно не готово; при
наличии локального SQLite-файла в выводе есть готовая команда `memo migrate`; по пункту 3
принято и зафиксировано решение. `make build`, `make test` зелёные, в том числе с
`MEMO_TEST_POSTGRES_DSN`.

## Результат

1. **Диагностика готовности.** Проба read-only расширена: `storeReadinessWarnings`
   (`cmd/memo/init.go:620`) проверяет, резолвится ли тип `vector` по search_path текущего
   соединения (`to_regtype('vector') IS NOT NULL` — не через каталог `pg_extension`: тот
   фиксирует лишь, что расширение установлено ГДЕ-ТО в БД, а не что его видно по
   search_path именно этого соединения, см. `internal/memory/store/postgres_readiness.go`)
   и право роли на `CREATE` в схеме, зафиксированной при открытии соединения
   (`has_schema_privilege($1::text, 'CREATE')` — параметризованная форма от
   `pgStore.schema`/`current_schema()` в момент подключения, а не литеральный вызов
   `current_schema()` внутри самого запроса) через `store.PostgresReadinessChecker`,
   вызывается из `probeStoreConnectionLive` (`cmd/memo/init.go:588`) тем же read-only
   соединением, что и `Health`. Отсутствие любого из двух не проваливает `init` —
   печатается `warning: ...` с объяснением последствий (векторный слой не поднимется при
   первом `ResetVectorIndex` → recall деградирует до лексического; без `CREATE` — первый
   штатный старт `memo` не накатит схему); таймаут/отмена самого диагностического запроса
   печатает отдельную формулировку («сервер не ответил ... — диагностика пропущена»), а не
   общее «не удалось проверить». Тесты — `cmd/memo/init_readiness_test.go` (диагностика на
   подменяемом `fakeReadinessChecker`) и `cmd/memo/init_store_test.go`
   (`TestProbeStoreConnectionLive_RealServer` — живой сервер под `MEMO_TEST_POSTGRES_DSN`,
   включая изолированную схему без `public` в search_path для реального негативного случая).
2. **Подсказка `memo migrate`.** `findExistingSqliteMemory`/`nonEmptySQLiteFile`
   (`cmd/memo/init.go:712`, `:757`) ищут непустой локальный SQLite рядом (путь из
   `<dir>/agentmemory.toml` предыдущего sqlite-прогона, относительный резолвится
   относительно каталога конфига, а не cwd процесса — `resolveConfigRelativePath`, либо
   дефолтный `~/.agentmemory/memory.db`) при выборе `driver=postgres`; если найден,
   `doInit` печатает в конце готовую строку `memo migrate 'sqlite:<путь>'
   'postgres://user@host:port/dbname?sslmode=...'` (`cmd/memo/init.go:1230`) — аргументы в
   одинарных кавычках (`shellQuoteSingle`), не в Go-кавычках `%q`: путь может содержать `$`,
   обратные кавычки, `!` — всё это `%q` не экранирует, и шелл интерпретировал бы их при
   копировании подсказки. Рядом печатается, что пароль для этой команды `migrate` возьмёт
   сама — из `MEMO_POSTGRES_PASSWORD` или из `<dir>/.env`. Сам перенос `init` не делает.
   Подсчёт записей в файле (`store.SQLiteMemoryCountContext`) ограничен отдельным
   таймаутом (`sqliteMemoryCountTimeout`, `cmd/memo/init.go`) — тем же инвариантом
   «установка не виснет», что у пробы postgres. Тесты — `cmd/memo/init_migrate_hint_test.go`
   (включая относительный путь и путь с `$`/пробелом/одинарной кавычкой, разбираемый
   настоящим `sh`).
3. **`MEMO_POSTGRES_PASSWORD` в MCP-конфиг — решение «нет».** Проверено на живых
   Claude Code 2.1.191 и opencode 1.17.18: оба харнесса передают MCP-серверу
   унаследованное окружение, `env`/`environment` его лишь дополняют, поэтому
   экспортированный в шелле пароль доезжает до `memo` и без плейсхолдера в конфиге, а сам
   плейсхолдер (при отсутствии переменной) дал бы пустую строку, которую `loadDotEnv`
   штатно перекрывает значением из `.env` — то есть добавлять его было бы безопасно, но
   и бесполезно: секрет не должен светиться в конфиге даже именем переменной без
   практической выгоды. `buildProviderEnv`/`buildMCPServerEntry`/
   `buildOpencodeServerEntry` (`cmd/memo/init.go`) не тронуты — `MEMO_POSTGRES_PASSWORD`
   туда по-прежнему не кладётся. Решение зафиксировано в DESIGN.md §13, раздел «Пароль
   PostgreSQL и MCP-конфиги (задача 12.1)» (после абзаца про `.env`).

## Второй раунд правок (по итогам code review)

Кроме пунктов 1–3 выше, по результатам ревью первого раунда доработаны:

- `memo migrate` (`cmd/memo/migrate.go`) теперь тоже подхватывает `.env` (`loadDotEnvForConfig`
  с пустым `-config` — резолвится в текущий каталог) — раньше это была единственная
  подкоманда без этого, и напечатанная `memo init` подсказка `memo migrate ...` падала на
  аутентификации, если пароль лежал только в `.env`, а не в окружении шелла.
- Тесты, зовущие `doInit` со `StoreDriver: postgres` (`cmd/memo/init_store_test.go`,
  `init_readiness_test.go`), теперь подменяют `$HOME` (`isolateHomeForTest`) — без этого
  `findExistingSqliteMemory` при отсутствующем `<dir>/agentmemory.toml` уходил в реальный
  дефолтный `~/.agentmemory/memory.db` разработчика/CI-раннера.
- `TestPostgresDoctorReadOnly_SchemaUnchanged`/`_ReadinessDiagnostics` (`cmd/memo/doctor_test.go`)
  направляют тестовое соединение через `PGOPTIONS` в схему `<схема>,public` (не только
  `<схема>`) — иначе `to_regtype('vector')` не резолвится и тест ложно решает, что pgvector
  не установлен на сервере, где он есть в `public`.
- Несколько ложнозелёных тестов сделаны различающими: секция «БД» в `memo doctor`
  (`postgresDatabaseSection`) теперь печатает позитивный маркер `готовность: ok`, когда
  диагностика реально вызвана и всё чисто (раньше «диагностика вызвана и чисто» и
  «диагностика вырезана из кода» давали неотличимый вывод); `TestProbeStoreConnectionLive_RealServer`
  проверяет не только «на готовой базе предупреждений нет», но и реальный негативный случай
  (схема без `public` в search_path на живом сервере); в `TestStoreReadinessWarnings`
  маркер подстроки для случая «нет права CREATE» заменён с `"CREATE"` на `"GRANT"` — текст
  предупреждения про `vector` сам легитимно содержит `CREATE EXTENSION`, поэтому `"CREATE"`
  не отличал бы одно предупреждение от другого.
- Относительный `store.path` из уже существующего `<dir>/agentmemory.toml` теперь резолвится
  `findExistingSqliteMemory` относительно каталога конфига, а не cwd процесса `memo init`
  (`resolveConfigRelativePath`) — `config.Load` сам это не делает, и её контракт не менялся.
- Напечатанная команда `memo migrate` экранируется для шелла одинарными кавычками
  (`shellQuoteSingle`), а не Go-кавычками `%q`, которые не защищают от `$`/обратных
  кавычек/`!`.
- `store.SQLiteMemoryCount` получил ctx-форму (`SQLiteMemoryCountContext`, по образцу
  `OpenPostgresReadOnlyContext`), `findExistingSqliteMemory` ограничен по времени так же,
  как проба postgres.
- `storeReadinessWarnings` различает таймаут/отмену самого диагностического запроса
  (отдельная формулировка «сервер не ответил») от прочих ошибок диагностики.

## Третий раунд правок (симплификация)

По итогам ревью на переиспользование/упрощение (без изменения внешнего поведения,
кроме явно отмеченного):

- `store.SQLiteMemoryCount`/`SQLiteMemoryCountContext` заменены одной функцией
  `store.SQLiteHasMemoriesContext(ctx, path) (bool, error)` — `SELECT EXISTS(...)`
  вместо `SELECT COUNT(*)` (не сканирует таблицу целиком), числовой сентинел
  `count=1` для случая «непустой WAL» заменён честным `true`; форма без ctx убрана
  (единственный вызывающий, `nonEmptySQLiteFile`, всегда передаёт дедлайн).
- Общий внутренний хелпер `sqliteTableExists` (`internal/memory/store/sqlite.go`,
  принимает узкий интерфейс `sqliteQueryRowContexter` для `*sql.DB`/`*sql.Tx`) —
  один запрос к `sqlite_master` вместо трёх копий (`ftsTableExists`,
  `sqliteStore.hasVecTable`, бывший инлайн в `SQLiteMemoryCount`).
- `storeReadinessWarningsFor(ctx, store.Store) []string` (`cmd/memo/init.go`) —
  общая обёртка над type-assertion в `store.PostgresReadinessChecker`, вызывается и
  из `probeStoreConnectionLive`, и из `postgresDatabaseSection` (`doctor.go`) вместо
  дублирования одинаковой проверки и комментария в двух местах;
  `postgresDatabaseSection` заодно переписана на два `return` (по образцу соседней
  `databaseSection`) вместо мутируемых `detail`/`secStatus`, и её вызов диагностики
  готовности обёрнут в `context.WithTimeout(context.Background(), probeTimeout)` —
  раньше уходил с `context.Background()` без дедлайна.
- Формулировка таймаута диагностики в `storeReadinessWarnings` больше не называет
  конкретное значение (`probeStoreTimeout`) — оно неверно для вызова из
  `doctor.go` (там свой `probeTimeout`); текст «сервер не ответил вовремя …» без
  цифры.
- `nonEmptySQLiteFile`/`findExistingSqliteMemory` (`cmd/memo/init.go`) теперь
  возвращают второе значение — предупреждение, если сама проверка кандидата не
  завершилась (файл битый/недоступен/таймаут), а не только «данных нет» —
  симметрично тому, как диагностика готовности postgres не молчит при таймауте.
  `doInit` печатает его в общий поток `warning: ...`.
- `formatMigrateEndpoint(cfg config.StoreConfig) string` (`cmd/memo/migrate.go`) —
  обратная к `parseMigrateEndpoint`, используется подсказкой `memo migrate` в
  `doInit` вместо третьего независимого способа собрать ту же строку
  (`"sqlite:"+path` литералом / `DSN()` с обнулённым паролем).
- `resolveConfigRelativePath` избавлена от недостижимой ветки `path == ""` и от
  ручного дублирования предиката «начинается с `~`» — раскрытие делегировано
  `expandHomeLocal`.
- `internal/memory/store/postgres_readiness.go`: обоснование «готовность ≠
  доступность» и «`to_regtype`, а не `pg_extension`» оставлено каждое ровно в одном
  месте (пакетный комментарий и доккомментарий поля `VectorExtension`
  соответственно), без пересказа в доках типа/метода.
- Тесты: `isolateHomeForTest` теперь возвращает изолированный `$HOME`-каталог,
  используется во всех тестах пакета вместо ручного `t.Setenv("HOME", t.TempDir())`;
  добавлены `defaultHomeSQLitePath` (дефолтный `~/.agentmemory/memory.db` +
  `MkdirAll`) и параметризованный каталогом `writeMinimalConfig` — оба заменяют
  повторявшиеся литералы в `cmd/memo/init_migrate_hint_test.go`/`doctor_test.go`;
  `writeNonEmptySQLiteFile` переиспользует `putDoctorMemory` вместо собственной
  копии `memory.Memory{...}`; `errStub` заменён на `errors.New`; bootstrap
  изолированной схемы PostgreSQL для интеграционных тестов вынесен в
  `newTestPgSchema` (`cmd/memo/migrate_test.go`); `TestPostgresDoctorReadOnly_
  ReadinessDiagnostics` слит в `TestPostgresDoctorReadOnly_SchemaUnchanged` — оба
  теперь поднимали идентичный стенд после выноса хелпера.
