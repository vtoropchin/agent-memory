# Задача 8.3 — Русская морфология в лексическом поиске (FTS5)

**Статус:** ⬜ ожидает · **тип: спайк + реализация** (сначала короткое исследование,
решение зафиксировать в этом файле, потом код)
**Этап:** 8 (Качество recall) · **Область:** `internal/memory/store` (+ возможно `write`)
**Зависимости:** нет. Синергия с 8.1 (explain покажет, какой источник вытянул запись).

## Контекст

FTS5 с токенайзером `unicode61` не знает морфологии: «собирать» ≠ «сборка»,
«тестировать» ≠ «тесты». Зафиксированное ограничение (tasks/3.4, [[mvp-notes]]):
перефразировки на русском лексический слой не находит — спасает только вектор, но
вектор опционален (noop-конфиг, ollama лежит, reindex в процессе). Память проекта
преимущественно русскоязычна → на чистом FTS5 recall заметно слепнет. Цель — поднять
лексический слой до «находит по основе слова», не сломав поиск по английским
идентификаторам/путям (`sqlite_fts5`, `make build` должны матчиться как раньше).

## Спайк (полдня, результат — раздел «Решение» в этом файле)

Сравнить два подхода на реальной БД проекта (~20+ записей):

1. **Стемминг-колонка (рекомендуемый кандидат).** Go-стеммер snowball для русского
   (напр. `kljensen/snowball`, чистый Go). В FTS-таблицу добавляется колонка
   `content_stemmed`; при индексации и при запросе текст прогоняется через один и
   тот же нормализатор: кириллические токены — стеммятся, латиница/цифры/пути —
   как есть. MATCH идёт по `content OR content_stemmed` (оригинальная колонка
   сохраняет точный матч и ранжирование по нему).
   Плюсы: управляемо, точечно, англ. не деградирует. Минусы: новая зависимость,
   пересборка FTS-таблицы (миграция), нормализатор нужно звать в двух местах.
2. **Токенайзер `trigram`** (SQLite ≥3.34, в mattn забандлен): отдельная
   FTS-таблица/колонка с `tokenize='trigram'`. Плюсы: без зависимостей, ловит и
   опечатки. Минусы: шумные частичные совпадения, больший индекс, MATCH-семантика
   меняется (подстроки), короткие токены (<3) не ищутся.

Метрика сравнения: набор из ~10 пар «запрос-перефразировка → ожидаемая запись»
(взять реальные случаи из памяти проекта, включая англ. идентификаторы) — доля
найденного лексическим слоем до/после.

## Реализация (после выбора; описано для варианта 1)

- Нормализатор `normalizeForFTS(text) string` — единая функция (место: `store`,
  рядом с индексацией; если понадобится из write — экспорт, не копия).
- Миграция схемы: пересоздание `memories_fts` с новой колонкой + перегон контента
  (одноразово при `Open`, по версии схемы — посмотреть, как в проекте оформлены
  миграции; если версии схемы нет — ввести `PRAGMA user_version`).
- `SearchLexical`: запрос нормализуется тем же кодом; MATCH по обеим колонкам;
  скор — как раньше (bm25 уже учитывает обе колонки, веса при необходимости
  через `bm25(memories_fts, w_content, w_stemmed)` — точный матч чуть тяжелее).
- Триггеры/код синхронизации FTS при Put/Update/Supersede — дополнить новой колонкой.

## Границы

- Только лексический слой: вектор, RRF, ранжирование, MCP-схемы — не трогать.
- Recall-контракт не меняется (тот же Query) — задача целиком под капотом store.
- Новая Go-зависимость допустима только для варианта 1 и только чистый Go (без CGO
  сверх существующего sqlite).

## Тесты

- Таблица пар из спайка → тест: перефразировки находятся лексически (без вектора,
  embedder=noop); англ. идентификаторы и точные фразы находятся как раньше
  (регрессионный набор); миграция на существующей БД со старой FTS-схемой проходит
  и ничего не теряет (количество записей в FTS до/после).

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- На реальной БД: контрольная перефразировка (напр. «как компилировать проект» →
  запись про сборку) находится при `embedder=noop`, чего раньше не было.
- Раздел «Решение» в этом файле заполнен фактами спайка; DESIGN §8 — одно
  предложение про морфологию лексического слоя.
