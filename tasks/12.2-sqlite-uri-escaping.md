# Задача 12.2 — единое экранирование пути в `file:`-URI для SQLite

**Статус:** ⬜ ожидает
**Этап:** 12 (Общая память команды, DESIGN.md §14 Этап 12) · **Область:**
`internal/memory/store` (`sqlite.go`, `sqlite_readonly.go`)
**Зависимости:** задача 12.1 (доработки/симплификация) — в её рамках появилась
`escapeSQLiteURIPath` и её тест `TestSQLiteHasMemoriesContext_EscapesSpecialCharsInPath`.

## Контекст

В пакете `internal/memory/store` сейчас **два расходящихся правила** формирования
одного и того же `file:`-URI для SQLite:

- `OpenSQLite` (`sqlite.go`) подставляет раскрытый (`expandHome`) путь в DSN сырым,
  без экранирования:
  ```go
  dsn := fmt.Sprintf("file:%s?_foreign_keys=on&_journal_mode=WAL&_busy_timeout=5000", expanded)
  ```
- `SQLiteHasMemoriesContext` (`sqlite_readonly.go`, read-only диагностика для `memo
  init`/`memo migrate`, задача 12.1) использует `escapeSQLiteURIPath` — экранирует
  `%`, `?`, `#` по правилам `https://www.sqlite.org/uri.html` §3.1, прежде чем
  подставить путь в `file:`-URI:
  ```go
  dsn := fmt.Sprintf("file:%s?mode=ro&immutable=1&_busy_timeout=5000", escapeSQLiteURIPath(expanded))
  ```

Расхождение воспроизводится тем же приёмом, что уже есть в тесте
`TestSQLiteHasMemoriesContext_EscapesSpecialCharsInPath`
(`internal/memory/store/sqlite_readonly_test.go`) — комментарий там прямо
оговаривает, что `OpenSQLite` подвержена той же проблеме, но чинить её в рамках
задачи 12.1 не входило в объём работы: путь с `?`/`#`/`%` в файле, который открывает
`memo` при обычном старте (`store.path` из `agentmemory.toml`, дефолт
`~/.agentmemory/memory.db`), обрывается на первом спецсимволе или decode'ится не так,
как ожидалось — тот же класс бага, что чинился в read-only диагностике, но здесь
задевает **рабочую** БД, а не диагностику.

## Что сделать

- Свести оба места к одному правилу: либо `OpenSQLite` начинает использовать
  `escapeSQLiteURIPath` (самый прямой вариант — функция уже общая для пакета), либо,
  если появится причина для другого решения (например, замена ручной сборки DSN на
  `net/url.URL`/сторонний хелпер), обе точки формирования DSN должны использовать его
  одинаково.
- Убедиться, что после правки для путей БЕЗ спецсимволов (подавляющее большинство:
  обычные пути без `%`/`?`/`#`) DSN побайтово не меняется — regression существующих
  путей не нужен.
- Добавить для `OpenSQLite` тест по образцу
  `TestSQLiteHasMemoriesContext_EscapesSpecialCharsInPath` (файл-ловушка с именем,
  совпадающим с обрезанным по `?`/`#` путём; настоящий файл с `%`/`?` в имени) —
  сейчас у `OpenSQLite` такого покрытия нет вовсе.

## Границы

- Это правка **рабочего пути открытия БД** (`OpenSQLite`, используется при каждом
  старте `memo`), а не только диагностики — поэтому она осознанно выделена в
  отдельную задачу, а не сделана попутно в 12.1 (доработки/симплификация): там менять
  поведение открытия боевой БД было не в скоупе.
- Не трогать поведение `SQLiteHasMemoriesContext`/read-only диагностику — она уже
  использует `escapeSQLiteURIPath` корректно, менять там нечего.
- Не расширять `escapeSQLiteURIPath` новыми правилами экранирования без явной причины
  — набор символов (`%`, `?`, `#`) уже соответствует официальной рекомендации SQLite.

## Критерий приёмки

`CGO_ENABLED=1 go build -tags sqlite_fts5 ./...` и
`CGO_ENABLED=1 go test -tags sqlite_fts5 -count=1 ./...` зелёные; новый тест на
`OpenSQLite` с путём, содержащим `?`/`#`/`%`, открывает и находит именно тот файл,
что был указан, а не файл-ловушку с "обрезанным" именем; существующие тесты (в т.ч.
все живые sqlite-сценарии с обычными путями) не регрессируют.
