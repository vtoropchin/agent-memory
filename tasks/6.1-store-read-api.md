## Контекст

Мы добавляем **read-only web-морду** для просмотра содержимого памяти (DESIGN.md §12 —
«HTTP-слой — опция на будущее»; теперь реализуем как подкоманду `memoryd web`, задачи
6.2/6.3). Морда должна уметь: листать записи с фильтрами и пагинацией, показывать карточку
записи с tags/links/соседями по графу, искать по тексту, показывать сводную статистику.

Текущий `Store` (DESIGN.md §6, `internal/memory/store/store.go`) уже даёт всё для карточки
и поиска: `Get` (запись целиком с tags/links), `Neighbors` (соседи по графу), `SearchLexical`
(лексический поиск, возвращает `[]Candidate` со Score/Source). **Чего не хватает** именно для
морды: (1) пагинируемого browse-листинга с фильтрами по scope/kind/архивности, (2) счётчиков
для статистики. Эту задачу и закрываем — чистое расширение read-пути store, без изменения
write/recall/maint.

## Что сделать

Только пакет `internal/memory/store`: интерфейс `Store` + реализация `sqlite.go` (+ тесты
`store_test.go`). Домены `write`/`recall`/`maint`/`mcp` не трогать.

### 1. Типы фильтра и результата (в пакете `store`)

```go
// BrowseFilter — параметры пагинируемого листинга памяти для read-only-морды.
type BrowseFilter struct {
    Scopes            []string // фильтр scope (m.scope IN (...)); пусто — все scope
    Kinds             []string // фильтр kind; пусто — все типы
    IncludeSuperseded bool     // false (дефолт) — только живые (superseded_by IS NULL)
    Limit             int      // размер страницы; <=0 → дефолт (напр. 50)
    Offset            int      // смещение для пагинации; <0 трактовать как 0
}

// Stats — сводные счётчики памяти для дашборда морды.
type Stats struct {
    Total      int            // живых записей (superseded_by IS NULL)
    Superseded int            // архивных (superseded_by IS NOT NULL)
    ByScope    map[string]int // живые записи по scope
    ByKind     map[string]int // живые записи по kind
}
```

`BrowseFilter`/`Stats` — концерн read-пути store, поэтому живут в пакете `store` (как
`Store`-интерфейс), а не в доменном `memory`. `memory.Query` не переиспользуем: у него
другая семантика (кандидаты поиска, TokenBudget, Summarize).

### 2. Методы интерфейса `Store`

```go
// List возвращает страницу записей под фильтр (для browse-морды), отсортированную
// по created_at DESC (новые первыми), и total — общее число записей под тот же
// фильтр БЕЗ учёта Limit/Offset (для пагинации). Заполняет Tags (для чипов в
// списке); Links НЕ грузит (тяжело для листинга — детальная карточка берёт их
// через Get). limit<=0 → дефолт listDefaultLimit (50); offset<0 → 0.
List(ctx context.Context, f BrowseFilter) (items []memory.Memory, total int, err error)

// Stats возвращает сводные счётчики (DESIGN.md §12, дашборд морды): всего живых,
// архивных, разбивки живых по scope и kind. Дёшево (агрегатные COUNT/GROUP BY).
Stats(ctx context.Context) (Stats, error)
```

### 3. Реализация (`sqlite.go`)

- **`List`:** SELECT из `memories` c WHERE-предикатами:
  - scope — переиспользовать существующий `scopePredicate(scopes, "")` (уже применяется в
    `SearchLexical`/`SearchVector`; НЕ дублировать `m.scope IN (...)`);
  - kind — `m.kind IN (...)` при непустом `Kinds` (по образцу того, как kind-фильтр строится
    в существующих Search-методах — переиспользовать `metaFilters`/хелпер, если он это уже
    умеет; иначе локальный предикат в том же стиле);
  - архивность — `m.superseded_by IS NULL`, если `!IncludeSuperseded`.
  - `ORDER BY created_at DESC, id DESC` (id как тай-брейк — ULID сортируем).
  - `LIMIT ? OFFSET ?`.
  - `total` — отдельный `SELECT COUNT(*)` с теми же WHERE (без LIMIT/OFFSET). Выполнить в
    одной транзакции/на одном соединении для консистентности пары (items,total).
  - Tags грузить батчем для страницы (как это делают методы, отдающие Tags — напр.
    `AllForReindex`), НЕ N+1 по одной записи. Links не грузить.
- **`Stats`:** агрегаты одним-двумя запросами:
  - `Total`/`Superseded` — `COUNT(*) ... WHERE superseded_by IS NULL` и `IS NOT NULL`;
  - `ByScope` — `SELECT scope, COUNT(*) ... WHERE superseded_by IS NULL GROUP BY scope`;
  - `ByKind` — аналогично `GROUP BY kind`.
  - Пустые карты инициализировать (`map[string]int{}`), не nil.
- Деградация (DESIGN.md §15): для read-методов достаточно вернуть ошибку наверх (морда покажет
  её) — тихих обрезаний быть не должно; total всегда точный.

## Тесты (`store_test.go`, поверх живого sqlite)

- `List` без фильтров: пагинация (Limit/Offset), порядок created_at DESC, total не зависит от
  страницы; Tags заполнены, Links пусты.
- `List` с фильтром по scope (набор из двух) — только эти scope; по kind — только эти типы;
  комбинация scope+kind.
- `List` архивность: по умолчанию superseded-записи исключены; `IncludeSuperseded=true` —
  включены, total растёт соответственно.
- `List` граничные: `Limit<=0` → дефолт; `Offset` за пределами total → пустой items, total
  корректный.
- `Stats`: Total/Superseded, ByScope/ByKind считают только живые; после `Supersede` живой
  счётчик падает, Superseded растёт; пустая БД → нули и пустые карты.
