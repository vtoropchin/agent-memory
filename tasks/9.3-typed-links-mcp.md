# Задача 9.3 — Типизированные связи в MCP + links в `memory_update`

**Статус:** ⬜ ожидает
**Этап:** 9 (Ops и модель данных) · **Область:** `internal/mcp` + `internal/memory/write`
**Зависимости:** нет. Закрывает зафиксированный тех-долг задачи 5.1.

## Контекст

Модель данных с самого начала богаче, чем API. Таблица `links` знает типы рёбер
(`rel`: related | supersedes | causes | part_of — DESIGN §4), `Store.Neighbors`
обходит граф, но:

1. `memory_save` принимает `links: []string` и всегда пишет `rel='related'` — агент
   не может выразить «этот факт — следствие того» или «часть той процедуры»;
2. `memory_update` вообще **не принимает links** — при том что `write.UpdateInput.Links`
   и аддитивная семантика слияния (`mergeLinks`, дедуп по паре Dst+Rel, self-link
   guard) реализованы ещё в 5.1 и покрыты тестами. Асимметрия §12, зафиксированная
   как тех-долг в отчёте 5.1.

## Что сделать

### Часть A — типизированные links в схеме (`schema.go`)

Обратная совместимость обязательна: элемент массива `links` — **либо строка** (id,
rel=related, как сейчас), **либо объект** `{"id": "01J...", "rel": "causes"}`.
В JSON-схеме — `oneOf` строки и объекта; в описании на русском перечислить типы
рёбер с одним примером («supersedes — новая версия факта; causes — следствие;
part_of — часть процедуры/темы»).

- Разбор входа: нормализация обеих форм в единый внутренний вид до передачи в write.
- Валидация `rel` ∈ {related, supersedes, causes, part_of} — неизвестный тип →
  ошибка инструмента с перечнем допустимых (fail-fast на опечатке, не молчаливый
  фолбэк в related).

### Часть B — write

Посмотреть фактические типы: если `SaveInput.Links`/`UpdateInput.Links` — `[]string`,
расширить до `[]LinkInput{Dst string; Rel string}` (пустой Rel → related — дефолт в
одном месте, в write). `resolveLinks`/`mergeLinks`/self-link guard уже оперируют
парой (Dst, Rel) на уровне store-модели — правка ожидается точечной. Семантика
остаётся **аддитивной** (инвариант из 5.1 — не стирать существующие рёбра).

`rel=supersedes` через links — просто ребро графа: НЕ подменяет поле
`superseded_by`/механику forget (это разные вещи: ребро — знание о связи,
superseded_by — исключение из recall). Явно отразить в godoc и в описании схемы.

### Часть C — `memory_update` (`update.go`, `schema.go`)

Добавить поле `links` (тот же формат, что в save) → `UpdateInput.Links`.
Существующая семантика Update по остальным полям не меняется.

### Часть D — instructions

`buildInstructions`: одна строка про типы связей (агенты видят server-level
instructions даже без скила).

## Границы

- `store` не трогать (типы рёбер уже в схеме БД). `recall` не трогать (обход графа
  в выдаче — отдельная возможная задача, сюда не тянуть). Web не трогать (морда
  уже показывает соседей; отображение rel — копеечное улучшение, можно захватить
  ТОЛЬКО если правка сводится к выводу уже приходящего поля).
- Никакой автоклассификации связей через LLM — типы задаёт агент (§7).

## Тесты

- `server_test.go`: save со строковыми links (back-compat, rel=related); save с
  объектными links (rel доезжает до БД — проверить через Neighbors); смешанный
  массив; невалидный rel → ошибка с перечнем; update добавляет links аддитивно
  (существующие рёбра целы), self-link отсекается (существующий guard).
- `write`: расширенные типы — дедуп по (Dst, Rel): related и causes между той же
  парой записей — два разных ребра.

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- e2e через живой бинарь: save двух связанных фактов с `rel:"causes"` → в web-морде
  (карточка → соседи) связь видна; memory_update добавляет ссылку к старой записи.
- DESIGN §12 — примеры save/update с типизированными links; тех-долг 5.1 закрыт
  (отметить в этом файле и в отчёте).
