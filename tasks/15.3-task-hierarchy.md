# Задача 15.3 — Иерархия epic/story/task: Links у соседей, родитель и дети в `memory_get`

**Статус:** ✅ выполнена (2026-09-20, ветка `feat/15.3-task-hierarchy`)
**Этап:** 15 (Kanban-доска задач, DESIGN.md §14 Этап 15) · **Область:**
`internal/memory` (`types.go` — хелперы графа), `internal/memory/store` (sqlite +
postgres: `Neighbors` грузит Links), `internal/mcp` (`get.go`), `cmd/memo/web.go`
(карточка записи: родитель/дети — только DTO)
**Зависимости:** 15.1 (`Type`). Независима от 15.2 (инструкции/скиллы про
`part_of` пишет 15.2; здесь — механика).

## Контекст

Тип задачи (`epic|story|task`) появился в 15.1, а иерархия — существующие связи
`rel=part_of` с **зафиксированным направлением «дочь → родитель»** (задача
`part_of` истории, история `part_of` эпика; DESIGN.md §14 Этап 15). Чтобы
показать «дети эпика» и «что блокирует эта задача» (15.4), нужен обратный
обход графа: у кого есть ребро на этот id. Сейчас `Store.Neighbors` возвращает
соседей в обе стороны, но **без Links** (грузит только Tags), поэтому ни
направление, ни `rel` из результата не восстановить.

Решение (по итогам арх-ревью дизайна): **не заводить `IncomingLinks`**, а
догрузить Links в `Neighbors` — множества соседей малы, карточка морды тоже
выиграет. «Входящие с `rel=X`» = соседи `n`, у которых `n.Links ∋ {Dst: id,
Rel: X}`. Отдельный обратный запрос — только когда `Neighbors` станет дорогим
(признак пересмотра).

Ретроактивно перевёрнутые рёбра в старых данных **не чинятся** (направление из
данных не выводится надёжно) — только конвенция для новых записей.

## Что сделать

### A — ядро: хелперы графа в `internal/memory`

- Новый файл `internal/memory/graph.go` (stdlib only): чистые функции над
  `[]Memory`/`Links`, без I/O:
  - `ParentOf(m Memory) (id string, ok bool)` — первый `Link` с `Rel ==
    RelPartOf` (у задачи один родитель; несколько — берётся первый, порядок
    Links стабилен по (Dst, Rel) из store);
  - `ChildrenOf(id string, neighbors []Memory) []Memory` — соседи с ребром
    `{Dst: id, Rel: RelPartOf}`;
  - `Progress(children []Memory) (done, total int)` — по `Status == StatusDone`
    среди живых (`SupersededBy == nil`).
  Годок каждой — про направление «дочь → родитель». Тесты табличные.

### B — store: `Neighbors` с Links

- SQLite `Neighbors`: после загрузки соседей — батч Links (аналог
  `loadTagsBatch`, новый `loadLinksBatch(ctx, tx, ids)` одним `SELECT src, dst,
  rel FROM links WHERE src IN (...)`), не N+1. Годок `Store.Neighbors` в
  `store.go`: «Tags и Links соседей загружены» (сейчас сказано иначе — поправить).
- PostgreSQL `Neighbors`: то же.
- Проверить, что `Get` по-прежнему грузит Links записи (да) — обратный обход
  = `Get(id)` + `Neighbors(id)`.

### C — MCP `memory_get`

- `get.go`: после метаданных — секции (пустые не выводятся):
  - `Родитель:` `- [status] (type) Заголовок (id)` — по `ParentOf` + `Get`
    родителя;
  - `Дети (n, готово k):` список по `ChildrenOf(id, Neighbors(id))`, каждая
    строка `- [status] (type) Заголовок (id)`, отсортировано по статусу в
    порядке `memory.Statuses`, затем по `Importance` ↓.
  Не-задачи: секции не выводятся (у них `part_of` — тематическая связь, а не
  иерархия).

### D — карточка морды (минимум)

- `cmd/memo/web.go` `GET /api/memories/{id}`: в ответ карточки — `parent`
  (`{id, summary, status, type}` или `null`) и `children` (массив тех же
  полей + `progress {done,total}`) для `kind=task`. Фронт (`app.js`) — секция
  «Родитель / Дети» в модалке карточки, read-only, ссылки открывают карточку.
  Доска и редактирование родителя — 15.5/15.6.

## Границы

## Сделано (2026-09-20)

- **A — ядро.** `internal/memory/graph.go` (stdlib only): `ParentOf` (первое
  ребро `part_of`), `ChildrenOf` (соседи с ребром `{Dst: id, Rel: part_of}`),
  `Progress` (done/total по живым детям, тумстоуны не считаются) и
  `SortByStage` (порядок `memory.Statuses`, затем `Importance` ↓, затем `Id`) —
  общее правило порядка детей для MCP и морды, чтобы не дублировать его в двух
  адаптерах. Годоки фиксируют направление «дочь → родитель».
  **Уточнение к букве задачи:** `ChildrenOf` учитывает только соседей
  `Kind == task` — у прочих kind `part_of` тематическая связь (то же
  обоснование, по которому `memory_get` не выводит секции для не-задач), и в
  прогресс родителя факт-«часть темы» попадать не должен.
- **B — store.** `Neighbors` в SQLite и PostgreSQL грузит Tags и Links соседей
  батчем: в `sqlite.go` появился `loadLinksBatch(ctx, q dbQueryer, ids)`
  (`SELECT src, dst, rel … WHERE src IN (…) ORDER BY src, dst, rel`), а
  `loadTagsBatch` принимает `dbQueryer` (уже объявлен в `postgres_crud.go`)
  вместо `*sql.Tx`, чтобы работать и вне транзакции; PG переиспользует
  `loadTagsAndLinksBatch`. Итого 3 запроса на вызов независимо от числа
  соседей. Годок `Store.Neighbors` в `store.go` и листинг §6 DESIGN.md
  обновлены. `Get` Links грузил и грузит.
- **C — MCP `memory_get`.** Новый файл `internal/mcp/hierarchy.go`:
  `(*Server).hierarchySections` (для `kind=task`; «Родитель:» через
  `ParentOf`+`Get`, «Дети (n, готово k):» через `ChildrenOf(Neighbors)`;
  строка `- [status] (type) Заголовок (id)`; висячий родитель (`ErrNotFound`)
  опускается, прочие ошибки store — наружу). В `get.go` — только вставка
  секций между метаданными и текстом (`formatMemory(m, sections)`), блок
  метаданных не тронут (15.2).
- **D — карточка морды.** `GET /api/memories/{id}` отдаёт `parent`
  (`{id, summary, status, type}` | null), `children` (массив тех же полей в
  порядке доски) и `progress {done, total}` (null у не-задач); `taskHierarchy`
  в `web.go` работает поверх уже загруженных `Neighbors`. `app.js`:
  секции «Родитель» / «Дети (n, готово k)» в модалке (после сводки, до
  тегов), read-only, бейджи стадии/типа, клик открывает карточку. Tailwind
  не пересобирался — использованы только уже присутствующие в `tailwind.css`
  классы.

## Арх-ревью (agent architecture-reviewer)

Правило зависимостей не нарушено (ядро импортирует только `sort`,
`TestDependencyRule` без правки базовой линии), N+1 в store устранён (3 запроса
на вызов `Neighbors` в обоих драйверах), web переиспользует уже загруженных
соседей; решение «`ChildrenOf` только для `kind=task`» признано уместным.
Находки: **major** — политика иерархии (гейт «только задачи», висячий
родитель, `ChildrenOf → SortByStage → Progress`) продублирована в
`mcp.hierarchySections` и `web.taskHierarchy`; кроме того `Store.Get` не
фильтрует тумстоуны — забытый эпик показывается как родитель в обоих местах
→ **осознанно отложено**: долг в memo (`01M2XVWAC8GBS2DC2YYKHEX745`) с
условием закрытия «15.5 вводит `board` → обе копии переводятся на него».
**minor** (закрыты): `SortByStage` расходился с DESIGN §14 (порядок внутри
колонки — importance, затем `updated_at`) → второй ключ `UpdatedAt ↓`, `Id` —
финальный тай-брейк; DESIGN.md §14 в одном месте всё ещё предписывал
`Store.IncomingLinks` для блокеров → заменено на `Neighbors` с Links; ветка
`ErrNotFound` родителя не была покрыта → `TestGetDanglingParentSkipped`
(подмена порта: через store висячее ребро не создать — FOREIGN KEY на `links`
в обеих схемах, ветка защитная).
