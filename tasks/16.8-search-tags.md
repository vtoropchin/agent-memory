# Задача 16.8 — `tags` в выдаче `/api/search`

**Статус:** ⬜ ожидает
**Этап:** 16 · **Область:** `internal/memory/store` (`sqlite.go`, `postgres_search.go`),
при необходимости `internal/memory/recall`, `cmd/memo/web.go`.
**Зависимости:** 16.1 (API морды), 16.4 (экран «Память»).

## Проблема (найдено приёмкой 16.7)

Строка результата поиска по спецификации §2.2 несёт теги записи, но `/api/search` их не
отдаёт: `Store.SearchLexical` и `recall.Recaller.Candidates` осознанно не грузят
tags/links — это read-hot-path (комментарии в `internal/memory/store/sqlite.go:1089,1201`,
`postgres_search.go:39`). В листинге `GET /api/memories` теги есть, в результатах поиска
чипы пропадают — расхождение выглядит как баг фронта, фронтом не лечится.

## Что сделать

Принять решение и реализовать один из вариантов:

1. Догружать теги для страницы выдачи (≤ limit записей) отдельным запросом в
   `handleSearch` — `attachTagsAndLinks`-подобный добор только по tags, hot-path recall
   не трогается (MCP-бриф теги не показывает). Предпочтительный вариант: цена — один
   запрос `WHERE memory_id IN (…)` на поиск, граница ядра не меняется.
2. Грузить теги в самом `SearchLexical`/`Candidates` — проще, но платит весь recall,
   включая MCP-путь, которому теги не нужны.
3. Оставить как есть и убрать теги из строки результата — тогда правится спецификация §2.2.

Границы: `links` в выдаче поиска не нужны; DTO не расширять новыми полями.

## Проверка

`make build`, `make test`; тест в `cmd/memo/web_test.go` на непустые `tags` в ответе
`/api/search` (SQLite) + паритет PostgreSQL по прежней схеме проверки; глазами — чипы
тегов в результатах поиска на живой базе.

## Критерий приёмки

Результат поиска показывает теги так же, как строка листинга; recall-путь MCP не стал
дороже (или решение 3 задокументировано в спецификации и DESIGN §12).
