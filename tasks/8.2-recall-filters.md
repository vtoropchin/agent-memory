# Задача 8.2 — Фильтры recall по тегам и датам

**Статус:** ✅ выполнена
**Этап:** 8 (Качество recall) · **Область:** `internal/memory/types.go` + `internal/memory/store` + `internal/mcp`
**Зависимости:** нет.

## Контекст

Recall фильтрует кандидатов только по `scope`/`kind` (+свежесть внутри ранжирования).
Теги пишутся при save и индексируются в FTS, но **адресно спросить память по тегу
нельзя**; временные срезы («что решали за последнюю неделю») тоже недоступны.
Оба фильтра — прямые SQL-условия, точка врезки уже готова: общий хелпер
`metaFilters(q)` в `store/sqlite.go`, который переиспользуют `SearchLexical` и
`SearchVector` — фильтрация обоих источников останется идентичной (требование §8)
автоматически.

## Что сделать

### Часть A — типы и store

- В `Query` (types.go): `Tags []string` (запись проходит, если имеет **хотя бы один**
  из тегов — OR-семантика; AND не делать, для точечных запросов OR достаточен и
  дешевле), `CreatedAfter int64`, `CreatedBefore int64` (unix ts; 0 = фильтр выключен).
- В `metaFilters`:
  - теги: `EXISTS (SELECT 1 FROM tags t WHERE t.memory_id = m.id AND t.tag IN (...))`;
  - даты: `m.created_at >= ?` / `m.created_at <= ?` при ненулевых значениях.
- Помнить про **k-before-filter** в sqlite-vec (известное ограничение, tasks/3.2):
  векторный KNN режет k ДО метафильтров — при узком фильтре по тегу вектор может
  вернуть меньше кандидатов, чем мог бы. В рамках задачи достаточно поднять запас k
  в `SearchVector` при активных Tags-фильтрах (по образцу `SemanticNeighbors` из 6.4:
  запрашивать больше, фильтровать в Go) — выбрать по месту, зафиксировать решение
  в отчёте.

### Часть B — MCP

- Схема `memory_recall` (`schema.go`): `tags []string` («вернуть только записи хотя бы
  с одним из этих тегов»), `created_after` / `created_before` (string, формат либо
  RFC3339-дата, либо относительная длительность `"168h"` — распарсить в `handleRecall`;
  выбрать ОДИН формат и задокументировать в описании поля; рекомендация — длительность
  назад от «сейчас», это типичный запрос агента: «за последнюю неделю»).
- `handleRecall` заполняет новые поля Query. `buildInstructions` (server-level
  instructions) — упомянуть фильтры одной строкой.

## Границы

- Ранжирование, RRF, бриф — не трогать (фильтры сужают кандидатов до ранжирования).
- `write`/`recall`(пакет)/`maint`/web — не трогать (recall-пакет пробрасывает Query
  в store как есть — проверить, что `candQuery := q` копирует новые поля, это
  единственное возможное касание).
- Без изменений схемы БД.

## Тесты

- `store_test.go`: фильтр по одному тегу / по нескольким (OR) / по несуществующему
  (пусто); created_after/before отсекают граничные записи; **оба Search\*** уважают
  фильтры (лексический и векторный, поверх живого sqlite-vec); комбинация
  scope+kind+tag+даты.
- `server_test.go`: парсинг форматов дат (валидный, невалидный → внятная ошибка),
  прокидывание в Query.

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- e2e через живой бинарь: recall с `tags:["стек"]` возвращает только тегированные
  записи; с `created_after:"24h"` — только свежие.
- DESIGN §12 — пример recall дополнен новыми полями.
