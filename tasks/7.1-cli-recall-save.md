# Задача 7.1 — CLI-подкоманды `memoryd recall` / `memoryd save`

**Статус:** ✅ выполнена
**Этап:** 7 (Ambient memory — хуки) · **Область:** `cmd/memoryd` (новые подкоманды)
**Зависимости:** нет (всё нужное в internal-пакетах уже есть). **Foundational для 7.2** —
хукам харнесса нечем дёргать память без CLI.

## Контекст

Сейчас память доступна только через MCP (stdio, живёт внутри сессии агента) и read-only
web-морду. Нет способа обратиться к памяти **одноразовой командой из терминала/скрипта**:
быстрый recall для отладки, save из shell-скрипта, и главное — вызов из хуков агентского
харнесса (SessionStart/UserPromptSubmit в Claude Code, задача 7.2).

Паттерн уже есть в проекте: `cmd/memimport` — one-shot CLI поверх `store.Open` +
`write.Writer`. Здесь то же самое, но внутри `memoryd` (у него уже есть подкоманды
`init`/`web`) и с обоими путями — write и read.

## Что сделать

Новый файл `cmd/memoryd/cli.go` (+ `cli_test.go`) с двумя подкомандами.

### `memoryd recall "<запрос>"`

Флаги: `-config` (как у остальных подкоманд), `-scopes` (список через запятую,
пусто → дефолт инстанса из `[scope]`, как в MCP), `-kinds` (через запятую),
`-budget` (int, 0 → дефолт из `[recall]`), `-json` (сырой JSON вместо Markdown),
`-quiet` (при пустой выдаче — пустой stdout и exit 0, для хуков).

Поведение:
1. `config.Load` → `store.Open` → фабрики `newEmbedder`/`newReasoner`
   (переиспользовать существующие из `main.go`; деградация до Noop — как в MCP-режиме,
   предупреждения в **stderr**).
2. Собрать `recall.Recaller` и выполнить один `Recall` с `Query{Text, Scopes, Kinds,
   TokenBudget}`. Разрешение scopes — той же логикой, что `resolveRecallScopes` в mcp
   (не дублировать: либо вызвать метод `config.ScopeConfig.RecallScopes()`, либо
   вынести общий хелпер — решить по месту, дублирование правила запрещено).
3. Markdown-бриф — в **stdout** (единственное, что туда пишется). Логи — stderr.
4. Summarize через Reasoner в CLI по умолчанию **выключен** (латентность хука);
   флаг `-summarize` включает.

### `memoryd save`

Флаги: `-kind` (semantic|episodic|procedural, обязателен), `-content` (обязателен;
`-` → читать из stdin), `-importance` (0 → дефолт через `write.ClampImportance`),
`-tags` (через запятую), `-scope` (пусто → `ScopeConfig.SaveScope()`, а если и он
пуст — ошибка, как `write.ErrEmptyScope`), `-source` (пусто → `"cli"`).

Поведение: `config.Load` → `store.Open` → `write.New(s, embedder)` → `Save`.
Embedder — реальный из фабрики (вектор пишется сразу; при недоступной ollama —
штатная деградация write path, вектор досчитает планировщик). Вывод: одна строка
в stdout — `saved <id>` либо `merged <id>` (дедуп), по образцу вывода memimport.

### Общее

- Роутинг подкоманд — там же, где разбираются `init`/`web` (`main.go`), тем же стилем.
- Один прогон = открыть БД → выполнить → `Close`. Планировщик maint в CLI-режиме
  **не запускается** (это one-shot, не демон).
- Exit-коды: 0 успех (в т.ч. пустой recall), 1 — ошибка конфига/БД/валидации.
- `--help` для обеих подкоманд — на русском, в стиле существующей справки memoryd.

## Границы

- Только `cmd/memoryd` (новые файлы + роутинг в `main.go` + справка). Пакеты
  `internal/*` не трогать, **кроме** случая выноса общего хелпера разрешения scopes
  (если понадобится — минимальный метод в `config`, mcp переключить на него).
- Никаких новых внешних зависимостей (flag из stdlib, как в memimport).

## Тесты

`cli_test.go`: recall на подготовленной scratch-БД возвращает бриф с сохранённым
фактом; `-scopes` фильтрует (чужой project не виден); save+recall round-trip;
save без scope при пустом `[scope]` → ошибка; `-content -` читает stdin; повторный
save того же факта → `merged` (дедуп); stdout recall не содержит логов (проверить,
что предупреждение деградации ушло в stderr).
