# Задача 15.1 — Модель задачи v2: стадии-колонки, `type`/`branch`/`workflow`, миграция `3 → 4`

**Статус:** ⬜ ожидает
**Этап:** 15 (Kanban-доска задач, DESIGN.md §14 Этап 15) · **Область:**
`internal/memory` (`types.go`), `internal/memory/write`, `internal/memory/recall`,
`internal/memory/store` (sqlite + postgres), `cmd/memo` (`export.go`, `import.go`,
`web.go` — только DTO и бейдж стадии), `cmd/memo/web/app.js` (только `STATUS_LABEL`)
**Зависимости:** нет — foundational для всего Этапа 15. Выполнять первой.

## Контекст

Задача (`kind=task`, задача 14.1) имеет статус `todo|doing|blocked|done`. Для
kanban-доски (Этап 15) этого мало: нужны стадии-колонки, тип задачи (эпик/история/
задача — сейчас агенты помечают их вразнобой тегами `epic`/`эпик`/`История` и
префиксом «ЭПИК» в заголовке), привязка к git-ветке и к процессу выполнения.
Все решения зафиксированы в DESIGN.md §4 (схема), §12 (описание `kind: "task"`),
§14 Этап 15 — читать перед началом, это источник истины.

Ключевые решения (✱ — выбор пользователя):

- ✱ **Стадии = колонки:** `status ∈ {backlog, todo, doing, review, testing,
  release, done}` в порядке жизненного цикла. Дефолт при сохранении остаётся
  `todo`. Переходы **не ограничены** порядком — карточку можно вернуть назад.
- ✱ **`blocked` удаляется из перечня статусов.** Блокировка становится
  вычисляемым свойством из связей `blocked_by` (реализуется в 15.4); в этой
  задаче — только миграция значений `blocked → todo` и удаление константы.
- ✱ **Тип задачи — поле `task_type` (`epic|story|task`, дефолт `task`)**, не тег.
  Разовый backfill в миграции: живая задача с тегом `epic`/`эпик` → `epic`, с
  тегом `story`/`История` → `story`, остальные `kind=task` → `task`. Сами теги
  не трогаются.
- ✱ **`branch` и `workflow` — свободные строки**, без валидации: имя git-ветки и
  имя процесса (`dev`, `ultracode`, `code-review`…), не id запуска.
- **Хранение — три nullable-колонки `memories`** (`task_type`, `branch`,
  `workflow`) по образцу `status`; пусто хранится как SQL NULL. Одна миграция
  `3 → 4` на весь этап — следующие задачи схему не меняют.
- Все четыре поля применимы ТОЛЬКО к `kind=task`: у остальных типов непустое
  значение — ошибка (как `ErrStatusNotApplicable`), не молчаливое отбрасывание.
- Ранжирование, дедуп (`SkipDedup`), maint — не трогать; правило «`done` скрыт
  из дефолтного recall» — без изменений.

## Что сделать

### A — ядро: `internal/memory/types.go`

- `Status`: константы `StatusBacklog`, `StatusTodo`, `StatusDoing`, `StatusReview`,
  `StatusTesting`, `StatusRelease`, `StatusDone`; `StatusBlocked` **удалить**
  (компилятор покажет все места использования — каждое переписать, не
  подменять на `todo` молча: там, где имелась в виду блокировка, оставить
  комментарий-ссылку на 15.4). `Statuses` — в порядке колонок; годок: это
  порядок колонок доски.
- Новый тип `TaskType string` с константами `TaskTypeEpic`, `TaskTypeStory`,
  `TaskTypeTask`, перечень `TaskTypes` (единственный источник для enum MCP/
  валидации, как `Statuses`).
- `Memory`: поля `Type TaskType`, `Branch string`, `Workflow string` — с годоком
  «только у Kind == KindTask, у остальных пусто; в БД nullable».
- `Query`: поле `Types []string` — фильтр по типу задачи (OR, пусто = без
  фильтра; прочие kind не затрагивает — как `Statuses`).
- Обновить годок `KindTask` и `Status` (стадия доски, блокировка — не стадия).

### B — write path: `internal/memory/write`

- `SaveInput`: `Type`, `Branch`, `Workflow string`. `UpdateInput`: `Type`,
  `Branch`, `Workflow *string` (nil — не трогать; пустая строка у `Branch`/
  `Workflow` — очистить; пустая строка у `Type` — вернуть дефолт `task`).
- Единая точка правил `normalizeTaskFields` рядом с `normalizeStatus` (или
  расширить её): `Status` вне `memory.Statuses` → `ErrUnknownStatus`; `Type` вне
  `memory.TaskTypes` → новая `ErrUnknownTaskType`; любое из `Type`/`Branch`/
  `Workflow` у `kind != task` → новая `ErrTaskFieldNotApplicable` (одна ошибка
  на три поля, с именем поля в тексте через `%w`-обёртку). Дефолты для
  `kind=task`: `Status=todo`, `Type=task`.
- `Save` и `Update` кладут поля в `memory.Memory`; `Update` при смене `Kind`
  не поддерживается (как сейчас) — проверка применимости идёт по `Kind`
  записи.
- `write.SkipDedup`, `ClampImportance`, links — без изменений.

### C — store: SQLite и PostgreSQL

- SQLite (`sqlite.go`): `schemaVersion = 4`, `migrations[3] = migrateTaskModel`
  (`3 → 4`, одна транзакция): `ALTER TABLE memories ADD COLUMN task_type TEXT`,
  `... branch TEXT`, `... workflow TEXT` — **каждая колонка со своей проверкой
  наличия** через `PRAGMA table_info` (как `migrateStatus`): обрыв между первой
  и второй колонкой при повторном Open иначе даст `duplicate column`; затем
  data-шаги: `UPDATE memories SET status='todo' WHERE kind='task' AND
  status='blocked'`; backfill `task_type` по тегам (`epic`/`эпик` → `epic`,
  `story`/`История` → `story`, `WHERE kind='task' AND task_type IS NULL`), затем
  `UPDATE ... SET task_type='task' WHERE kind='task' AND task_type IS NULL`.
- Список колонок `SELECT id, kind, …, status` продублирован в ~8 запросах на
  драйвер — вынести в константу (`memoryColumns`) и подставлять в
  `Get`/`List`/`Neighbors`/`Search*`/`AllFor*`/`ListMissingVectors`/…; +3
  колонки без этого = молчаливая потеря `branch` на одном из путей. `Put`,
  `scanMemory` — новые поля; `typePredicate` в `metaFilters` (как
  `statusPredicate`) для `Query.Types`. `BrowseFilter`/`List` НЕ трогать
  (доска в 15.5 получит свой `ListTasks`, см. DESIGN §14).
- PostgreSQL (`postgres*.go`): это **первый версионный шаг** — `pgMigrations[0]`
  (`0 → 1`, `pgSchemaVersion = 1`, механизм `migrate` уже есть и ждёт первого
  шага; годок про «нумерация SQLite 4 ≠ PG 1 намеренно»): `ALTER TABLE memories
  ADD COLUMN IF NOT EXISTS task_type text` (+ `branch`, `workflow`) и те же
  data-`UPDATE`. В базовую схему (`baseSchema`, накатывается при каждом Open)
  data-шаги НЕ класть — `UPDATE` по всей таблице на каждом старте недопустим,
  даже идемпотентный. Свежая PG-база: `baseSchema` без новых колонок +
  `pgMigrations[0]` добавляет их — либо колонки и в `baseSchema` (`IF NOT
  EXISTS`), а шаг миграции тогда только data; выбрать одно и описать в годоке.
  Колонки в запросах/`Put`/scan через ту же константу-список,
  `typePredicatePG` в `metaFiltersPG`.
- `PRAGMA user_version` у существующих БД версии 3 поднимается до 4; свежая БД
  проходит все четыре шага. Для PG — `schema_version` 0 → 1.

### D — recall: `internal/memory/recall`

- `Query.Types` пробрасывается в `candQuery` (store фильтрует).
- `formatLine` для задачи: `- [doing] (epic) Заголовок [★4]` — тип в скобках
  показывается только для `epic`/`story` (для `task` — как сейчас); `branch`,
  если задан, хвостом: `· ветка feat/x`. Маркер блокировки — 15.4.

### E — export/import и морда (минимум)

- `cmd/memo/export.go`/`import.go`: аддитивные поля `type`, `branch`, `workflow`
  (`omitempty`, `exportVersion` не меняется). Импорт обязан маппить `status:
  "blocked"` старого бэкапа → `todo` с предупреждением в stderr — иначе после

## Тесты

- `write/task_test.go`: дефолты `todo`/`task`; каждая из 7 стадий принимается;
  `blocked` → `ErrUnknownStatus`; `type` вне перечня → `ErrUnknownTaskType`;
  `type`/`branch`/`workflow` у `semantic` → `ErrTaskFieldNotApplicable`;
  `Update` с `Branch=""` очищает поле, `Type=""` возвращает `task`.
- `store/task_status_test.go` (+ аналог для postgres, если есть тест-обвязка
  с живым PG — иначе только sqlite): round-trip всех четырёх полей и NULL для
  прочих kind; фильтры `Types`/`Statuses` в `SearchLexical` и `List`;
  миграция `3 → 4` на воспроизведённой legacy-схеме версии 3: задача со
  `status='blocked'` стала `todo`, задача с тегом `эпик` получила
  `task_type='epic'`, с тегом `История` — `story`, прочие — `task`, теги целы,
  данные и FTS работают; повторное открытие БД не меняет данных (идемпотентность);
  для PG (если есть тест-обвязка с живым сервером) — `schema_version` 0 → 1 и те
  же data-проверки, иначе — только компиляция и ревью SQL.
- `recall/task_test.go`: строка брифа с `(epic)` и веткой; фильтр `Types`.
- `cmd/memo/export_test.go`/`import_test.go`: round-trip новых полей; импорт
  бэкапа со `status: "blocked"` → `todo` + предупреждение.
- Арх-тест `TestDependencyRule` — базовая линия не растёт.
