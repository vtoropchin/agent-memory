# Задача 10.1 — Семантический (гибридный) поиск в web-морде

**Статус:** ⬜ ожидает
**Этап:** 10 (Web v2) · **Область:** `internal/memory/recall` (малый рефактор) + `cmd/memoryd` (web.go) + `cmd/memoryd/web` (фронтенд)
**Зависимости:** Этап 6 выполнен. Синергия с 8.1 (explain в выдаче поиска).

## Контекст

`/api/search` — только FTS5 (лексика): DESIGN §12 явно помечает вектор в морде как
«вне этой версии». При этом векторы уже в БД, KNN-соседи на карточке работают.
Перефразировка («как компилировать проект») в морде не находит запись про сборку —
хотя MCP-recall её находит вектором. Это делает поиск в морде заметно тупее памяти,
которую он показывает.

**Отступление от инварианта 6.x, требует явного решения в реализации:** морда была
«оффлайн-читателем» (никаких вызовов Embedder). Для семантического поиска нужно
эмбеддить **запрос пользователя** — один вызов ollama на поиск. Инвариант сужается:
«морда не пишет в БД и не эмбеддит записи; эмбеддинг поискового запроса — допустим,
с полной деградацией до FTS при недоступности Embedder». Зафиксировать это в DESIGN §12.

## Что сделать

### Часть A — переиспользование гибридного пути (recall)

Гибрид (два Search* + RRF) уже реализован внутри `Recaller.Recall`, но тот возвращает
Markdown-бриф — морде нужен список. Не копировать логику: выделить в `recall`
публичный метод

```go
// Candidates выполняет гибридный поиск (FTS + вектор при доступном Embedder, RRF,
// бизнес-ранжирование) и возвращает отранжированных кандидатов без сборки брифа.
func (r *Recaller) Candidates(ctx context.Context, q memory.Query) ([]memory.Candidate, error)
```

и переключить `Recall` на него внутри (бриф = Candidates + сборка). Поведение
`Recall` не меняется байт-в-байт — это чистая экстракция.

### Часть B — web-сервер (`cmd/memoryd/web.go`)

- В конструкцию web-режима добавить `recall.Recaller` (собирается из уже имеющихся
  store + фабрика `newEmbedder`; Reasoner в морде НЕ нужен — передать Noop).
- `/api/search?q=...&mode=lexical|semantic` (дефолт `semantic` = гибрид; `lexical` —
  прежнее поведение, полезно для сравнения глазами). Гибрид → `Candidates` с Query
  из параметров (scope/kind-фильтры морды уже есть — пробросить).
- Ответ дополняется полем `source` на записи ("fts"/"vector"/"fts+vector") — морде
  дёшево показать, чем найдено (см. 8.1; если 8.1 ещё не сделана — хотя бы
  `Candidate.Source`).
- Деградация: Embedder недоступен/noop → гибрид молча работает как FTS (это
  штатный путь recall), HTTP 200, в ответе флаг `"vector": false` — фронт покажет
  плашку «поиск по смыслу недоступен (векторный слой выключен)».

### Часть C — фронтенд (`cmd/memoryd/web/`)

- Переключатель у строки поиска: «по смыслу» (дефолт) / «по словам»; бейдж
  источника на результате (`fts`, `vec`, `fts+vec`); плашка деградации.
- UI-подписи на русском; экранирование через `textContent` (как в 6.3);
  пересборка Tailwind-бандла — тем же способом, что в 6.3 (см. Makefile).

## Границы

- `store`/`write`/`maint`/`mcp` — не трогать. В `recall` — только экстракция
  `Candidates` (поведение Recall неизменно, существующие тесты recall проходят без
  правок ожиданий формата).
- Морда по-прежнему слушает только 127.0.0.1; write-операций не добавляется.

## Тесты

- `recall_test.go`: `Candidates` возвращает тот же набор/порядок, что виден в брифе
  `Recall` (связующий тест экстракции).
- `web_test.go` (httptest): mode=semantic с fakeEmbedder находит перефразировку,
  которую mode=lexical не находит (перенести паттерн из `TestRecall_FoundOnlyByVector`);
  noop-embedder → 200 + `"vector": false`; mode=lexical идентичен прежнему поведению.

## Критерий приёмки

- Билд/vet/тесты `-tags sqlite_fts5` зелёные.
- e2e на реальной БД с живой ollama: контрольная перефразировка находится в морде
  «по смыслу» и не находится «по словам»; при остановленной ollama морда ищет
  лексически с плашкой, без 500-х.
- DESIGN §12: снята пометка «вне этой версии», зафиксирован суженный инвариант
  оффлайновости.
